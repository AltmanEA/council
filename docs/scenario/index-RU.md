## Обзор

**Сценарий** определяет набор активных Ролей и параметризацию базового пятифазного протокола взаимодействия (§Основной протокол) для решения проблем определённого рода. Это декларативный рецепт, а не экземпляр выполнения: Сценарий — это то, что выбирается; Сессия — это то, что создаётся, когда Сценарий выполняется против Задачи.

Сценарии не заменяют и не расширяют базовую структуру протокола. Они выбирают роли, настраивают параметры и опционально определяют подготовительные прешаги, которые передают входные данные в Фазу 1 (Подача задачи). Модификации на уровне протокола (другие последовательности фаз, другая логика консенсуса) обрабатываются отдельными вариантами протокола, а не сценариями.

---

## Иерархия моделей

Слои концептуальной модели:

| Уровень | Концепция | Роль |
|---------|-----------|------|
| Рецепт | **Сценарий** | Объявляет роли, параметры, прешаги |
| Входные данные | **Задача** | Описание проблемы, представленное пользователем |
| Выполнение | **Сессия** | Конкретный запуск, объединяющий Сценарий и Задачу |
| Участники | **Роли** | Ёмкости, управляемые перспективой, активируемые Сценарием |

Сценарий выбирает Роли из набора, определённого в `protocol-core`. Сценарий параметризует базовый протокол (лимиты раундов обсуждения, критерии допуска темы и т.д.), но не изменяет его последовательность фаз или логику консенсуса.

## Схема

Каждое объявление Сценария содержит следующие поля:

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| name | string | yes | Человекочитаемый идентификатор |
| problem_type | string | yes | Свободное описание предметной области проблемы, которую решает данный сценарий |
| roles | array of role identifiers | yes | Роли для активации; должен включать Специалиста по надёжности и безопасности, если он явно не исключён с документированным обоснованием оператора |
| pre_phases | array of objects | no | Подготовительные шаги до Фазы 1. Каждый объект содержит: name, description, max_rounds, output_contract |
| phase_overrides | mapping | no | Переопределения параметров для каждой фазы (напр., max_discussion_rounds, severity_filter). Не должны изменять структурную логику фаз |
| version | semantic version string | yes | Независимая версия сценария |
| composed_of | reserved | no (blocked) | Зарезервировано для поддержки композиции в будущем. Проверки отклоняют схемы с заполненным полем на стадии MVP |

## Ограничения

### Неотменяемые неизменяемые требования (invariant)

1. **Неизменность структуры протокола.** Сценарии могут параметризовать базовый пятифазный протокол, но никогда не вставляют, не удаляют и не переставляют фазы. Каноническая последовательность (Подача задачи → Индивидуальный обзор → Раунд обсуждения → Проверка консенсуса → Формирование резолюции) является незыблемой.

2. **Пути эскалации сохранены.** Ни один сценарий не может отключить или ослабить каналы эскалации (информационный пробел, неразрешимый конфликт, превышение порога риска).

3. **Вычисление консенсуса без изменений.** Детерминированные правила консенсуса (оценка agree/concerns/blocked-in-scope/blocked-escalation) не могут быть переопределены конфигурацией сценария.

### Ограждения безопасности

4. **Включение специалиста R&S.** Роль Специалиста по надёжности и безопасности должна присутствовать в каждом сценарии по умолчанию. Явное исключение требует одобренной человеком причины, хранящейся в записи сессии, и документированного обоснования в Фазе 1.

5. **Фиксированный каталог при запуске.** Сценарии разрабатываются исключительно сопровождающими фреймворка. Авторство операторов откладывается до существования модели управления.

6. **Без композиционности на MVP.** Сценарии ссылаются на другие сценарии через зарезервированное поле, но не могут компоновать их при запуске. Семантика проверки композиций будет определена в более позднем мильстоне.

## Взаимоотношения

- **Сценарий vs Задача:** Задача описывает *что* нужно решить. Сценарий описывает, *как* система структурно подходит к этому типу проблемы.
- **Сценарий vs Сессия:** Сценарий — это шаблон/рекомендация; Сессия — конкретный экземпляр выполнения с единственным Сценарием, связанным с единственной Задачей.
- **Сценарий vs Роли:** Сценарий выбирает Роли из доступного набора. Он не переопределяет их и их обязанности. Настройка промптов в рамках Сценария ограничена акцентом/внедрением контекста, а не поведенческой подменой.
- **Сценарий vs Основной протокол:** Сценарий наследует базовую пятифазную структуру протокола из `protocol-core/index.md` и параметризует её. Новые варианты протокола будут отдельными артефактами, ссылками на которые производятся независимо.
- **Сценарий vs Уровни активации ролей:** Модель уровней (Core / Extended) в `protocol-core` (§Правила активации ролей) служит механизмом резервного значения по умолчанию. Сценарии предоставляют декларативные оверлей-слои, которые заменяют ручное обоснование после полного внедрения. До этого времени применяются уровневые значения по умолчанию, когда Сценарий не указан.

## Примеры сценариев (иллюстративные)

Эти сценарии предлагаются как иллюстративные примеры. Они НЕ являются частью начальной реализации — начальная реализация состоит из документирования самого абстрактного уровня Сценариев. Будущие итерации наполнят курируемый каталог на основе наблюдаемых паттернов использования.

- **Brainstorming** — Многоперспективная мозговая штурм-сессия, сосредоточенная на генерации вариантов без преждевременного схождения. Вероятно, включает расширенные раунды обсуждения.
- **Grill** — Интенсивный адверсиальный режим уточнения. Многоразовые вопросы для выявления скрытых предположений и требований перед началом формального обзора. Может использовать более высокие лимиты прешаг и более строгие пороги критического обоснования.
- **Specification Generation** — Преобразует детальное описание задачи в структурированную спецификацию. Минимальные прешаги, возможно ноль раундов обсуждения для чётко определённых входных данных.
- **Implementation Planning** — Преобразует спецификацию в пошаговый план выполнения. Активирует Роли, которые покрывают архитектурную декомпозицию, операционные аспекты и зависимости последовательности.
