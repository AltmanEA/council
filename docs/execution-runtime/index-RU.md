## Область определения

Определяет Слой 1 как среду исполнения: границы модулей, детерминированную управляющую плоскость, конечный автомат фаз, сборку артефактов, сохранение сессии, маршрутизацию эскалации и правило именованного пространства между fallback и code-Модератором. Поля артефактов определены в `service-contract/index.md`; доставка для оператора — в `operator-surface/index.md`.

## Границы Слоя 1

Слой 1 — это среда исполнения. Он содержит детерминированный Модератор и недетерминированные блоки исполнения (Ролевые агенты и Вспомогательные агенты). Слой 2 — Внешние интерфейсы / Адаптеры; он вызывает Слой 1 и никогда не вызывает Слой 0. Правило Слоя 0 без изменений: только Слой 1 вызывает Слой 0.

| Модуль | Ответственность | Может импортировать |
|--------|------------------|---------------------|
| `orchestrator/` | Конечный автомат фаз, Модератор, маршрутизация консенсуса и эскалации | `agents/`, `scenario/`, `persistence/`, Слой 0 |
| `agents/` | Ролевые агенты, Вспомогательные агенты, `RoleAgentFactory`, `get_model()` | `scenario/`, типы парсера Слоя 0 |
| `scenario/` | `ScenarioLoader`, валидация сценария | типы каталога Слоя 0 |
| `persistence/` | Manifest, файлы фаз, атомарные записи, блоки | — |

Правила импорта: `orchestrator/` может импортировать другие модули; `agents/` НЕ ДОЛЖЕН импортировать `orchestrator/`; только `agents/` может вызывать `get_model()`; `orchestrator/` НЕ ДОЛЖЕН вызывать его напрямую; Слой 1 НЕ ДОЛЖЕН импортировать Слой 2.

## Детерминированная управляющая плоскость

Управляющий поток Модератора и каждое решение по фазе, консенсусу и эскалации — детерминированные функции проверенных выводов ролей. Ни одна LLM не участвует в управляющем потоке или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария использует `default-council-session` (см. `scenario/default-council-session.yaml`) по умолчанию, когда в манифесте сессии не указан явный `scenario_id`.

## Конечный автомат фаз

Состояния: `1` — подача задачи, `2` — индивидуальный обзор, `3` — обсуждение, `4` — проверка консенсуса, `5` — разрешение, плюс `awaiting-operator`, `resolved`, `failed`.

| От | До | Ограничение |
|----|----|-------------|
| 1 | 2 | Задача проверена; сценарий загружен; `locked_roles` сопоставлен с `operator_approval` согласно `service-contract/index.md` §Session Manifest |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствует роль Core |
| 3 | 4 | Лимит раундов достигнут, или нет новых `blocked-in-scope` |
| 3 | 3 | По крайней мере одна `blocked-in-scope` и остаётся бюджет целевых раундов |
| 4 | 5 | Согласно таблице §Outcome-to-Transition protocol-core: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице §Outcome-to-Transition protocol-core: `no-consensus` при наличии оставшегося бюджета → повторное вхождение в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице §Outcome-to-Transition protocol-core: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Конечный артефакт сохранён; manifest обновлён последним |
| awaiting-operator | `resume_phase` | Разрешение оператора привязано к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Останавливается немедленно при обнаружении high/critical ошибки Documenter (проверка не пройдена). Precheck недоступен → переопределение разрешено через council.override_precheck (событие precheck.overridden). Переопределение записывается в manifest как pre_check_override; разрешает ровно один переход, после чего требуется новая проверка или новое переопределение. |
| any | failed | Невосстанавливаемая ошибка IO или нарушение протокола |

Только `orchestrator/` переводит фазу вперёд. Оператор никогда не редактирует состояние фазы напрямую; разрешение поступает через поверхность оператора. Хук апгрейда быстрого обзора `SUBJ-007` зарезервирован, но не реализован на этапе MVP.

## Обработка статуса роли

`extract_role_status()` — единственный источник истины для консенсуса. Извлечение с `invalid-format` — блокирующая ошибка протокола: сессия переходит в `blocked-escalation` с `escalation_reason = information-gap`, созданной структурно конвейером извлечения; сырой обзор сохраняется, и роль никогда не считается `agree`. Критическое обнаружение с недействительным обоснованием следует тому же принципу не-отклонения (согласно `service-contract/error-management/index.md` §Critical Finding Validation Process): оно понижается до `high` с сохранением исходного текста, вместо outright отклонения обзора. Отсутствующая роль Core — это `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Присутствие роли Core проверяется на каждом пути, а не только перед упрощением. Вентиль pre_check работает независимо от извлечения статуса роли, но должен быть успешным перед любым продвижением протокола.

## Порядок сборки артефактов

1. Фаза 2: сохранить по одному `RoleReview` для каждой активной роли.
2. Фаза 3: сохранить по одному `RoleReview` для каждой активной роли за раунд.
3. Фаза 4: сохранить `ConsensusVerdict`.
4. Фаза 5: сохранить документ консенсуса или `EscalationRecord`.
5. Обновить `manifest.json` последним.
6. Выдавать события только после успешной устойчивой записи.

Провал шага прерывает оставшиеся шаги. Сессия остаётся на последней полной границе фазы.

## Маршрутизация эскалации

Эскалация — стоп-и-возобновление. Среда исполнения записывает `EscalationRecord`, устанавливает `phase_state = awaiting-operator`, выдаёт `escalation.opened` и возвращает управление оператору. На MVP нет блокирующего stdin или фоновой программы ожидания: среда исполнения проверяет `timeout_at` при каждом последующем вызове сессии. Когда текущее время превышает `timeout_at`, среда исполнения автоматически применяет `fallback_strategy`, определённую в `EscalationRecord`, и переводит фазу вперёд. При ручном вызове до истечения таймаута поверхность оператора владеет часами; оператор также может переопределить через явное одобрение.

Возобновление требует аутентифицированного разрешения, привязанного к `escalation_id` и `operator_id`. При возобновлении среда исполнения применяет решение, устанавливает `current_phase = resume_phase`, записывает разрешение в запись эскалации и журнал событий, и продолжает. Отклонённая или заменённая эскалация следует своей `fallback_strategy`.

## Контракт директории сессии

```
sessions/<session_id>/
  manifest.json      # SessionManifest (service-contract)
  task.md            # задача, описанная оператором
  phase-1.json       # по одному файлу на фазу, перезаписывается атомарно
  phase-2.json
  phase-3.json
  phase-4.json
  phase-5.json
  events.jsonl       # журнал событий (только добавление)
  .lock              # блокировка single-writer
```

Каждый файл фазы — `{schema_version, phase_id, status: complete|partial, artifacts: string[], updated_at}`. Файлы фаз содержат локальные для сессии тексты обзоров; `manifest.json` и `events.jsonl` содержат только замаскированные сводки, хэши и идентификаторы. Состояние среды исполнения — локальное и НЕ ДОЛЖНО коммититься в git; версируются только конфигурация и схемы.

## Манифест сессии

`manifest.json` следует `SessionManifest` из `service-contract/index.md`. Дополнительные правила жизненного цикла:

- `manifest_hash` — это `sha256` канонического JSON (отсортированные ключи, без пробелов) с опущенным `manifest_hash`.
- `previous_manifest_hash` связывает каждую запись с предыдущим manifest; первая запись использует `null`.
- `role_agent_config` записывает точные параметры, использованные для каждой роли, обеспечивая соответствие ADR-002 provenance.
- `pending_operator_action` — проекция открытой эскалации для оператора.

## Механика сохранения

- Записи используют temp file → `fsync` → атомарный `rename`.
- Единичная блокировка advisory (`flock` exclusive) на `.lock` покрывает всю сессию; таймаут получения — 30 секунд.
- Записи manifest сериализованы и хэш-сцеплены. Разрыв цепи — `IO.002`.
- Читатели могут осмотреть сессию без блокировки; они ДОЛЖНЫ tolerировать отсутствующий последний файл фазы и fallback к предыдущей полной границе.

## Семантика аварий

MVP обеспечивает возобновление на границах фаз, а не checkpoint посреди фазы (ADR-004 отложен).

1. При запуске проверить цепь хэшей manifest.
2. Найти наивысший непрерывный файл фазы с `status: complete`.
3. Удалить оставшиеся `.tmp` файлы.
4. Возобновить на границе этой фазы; перезапустить неполную фазу.
5. Если manifest недействителен, пометить сессию как `failed`; оператор должен начать новую сессию.

Перезапуск фазы вызывает LLM снова и может породить иные выводы. Журнал событий записывает новую попытку; предыдущие полные артефакты остаются доказательством до тех пор, пока перезапуск не commits.

## Правило именованного пространства

Оба режима разделяют структуру директории сессии (`sessions/<session_id>/`), но различаются внутренними артефактами:

- **Режим Модератора:** Использует каноническую схему — `manifest.json` (SessionManifest), файлы `phase-*.json`, `events.jsonl` и `.lock` (см. §Контракт директории сессии). Все фазы порождают структурированные JSON-артефакты.
- **Режим fallback (изъят):** Использует текстовые Markdown-файлы (`task-brief.md`, `review-*.md`, `consensus-doc.md`). Fallback-сессии НЕ требуют `SessionManifest` или структурированных файлов фаз; они следуют структуре, определённой в `fallback/index.md`, §Session workspace convention. Это изъятие существует, потому что code-Модератор ещё не реализован (§1.5 Project Stage in AGENTS.md). Когда Модератор будет доступен, адаптер МОЖЕТ преобразовать выходные данные fallback в каноническую схему.

## Правило вспомогательных сервисов (D3)

Documenter, режим fallback и JSON-сохранение — вспомогательные сервисы вне цепи слоёв. Documenter вызывается поверхностью оператора Слоя 2 и использует порт исполнения Слоя 1 для записей на базе LLM (Documentation Worker). Вспомогательные сервисы никогда не вызывают Слой 2 или Слой 0 напрямую. Слой 2 не содержит прямых вызовов LLM.

## Проекция статуса оператора

Среда исполнения обеспечивает только-для-чтения проекцию, отвечающую на три вопроса:

| Вопрос | Поля |
|--------|------|
| Где я? | `session_id`, `mode`, `current_phase`, `phase_state` |
| Что нужно мне? | `pending_operator_action`, открытый `escalation_id`, `resume_phase` |
| Что изменилось с прошлого взгляда? | `last_event_id`, `changed_since_last_view`, `artifacts` |

Хэш-цепь доказывает целостность, а не полноту понимания. Эта проекция обязательна и рендерится поверхностью оператора.

## Путь миграции

Если оркестровка превосходит возможности Слоя 1, извлечь Orchestration Core за публичным интерфейсом Слоя 1 (вариант B). Границы слоёв, правило Слоя 0 и контракт сессии остаются без изменений.
