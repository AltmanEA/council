## 2. Организация документации

### 2.1 Расхождение на диске

Документы хранятся в каталоге `docs/` в двуязычной структуре: оригиналы на английском языке находятся в `docs/en/<id>/`, переводы на русский язык (при наличии) — в `docs/ru/<id>/`, с идентичной вложенностью каталогов в обеих ветвях. Основной документ — `index.md` в английской папке; перевод на русский язык, если он присутствует, — `index-RU.md` в зеркальном пути в `docs/ru/`. Файл журнала изменений `CHANGELOGS/<id>.changes.md` хранит историю версий отдельно от контента (журналы изменений остаются в корне репозитория как **Операционный** артефакты).

Примеры: `docs/en/protocol-core/index.md` (английский источник), `docs/ru/protocol-core/index-RU.md` (русский перевод), `docs/en/glossary/index.md`. Документы в корне репозитория — такие как `AGENTS.md` и `docs-manifest.yaml` — служат **Операционный** правилами и самим индексом манифеста.

Новые документы создаются путём добавления новой папки в `docs/en/<id>/` и файла `index.md`; манифест необходимо обновлять одновременно для английского пути и русского пути (если перевод существует).

Исключения для нескольких документов: следующие существующие папки содержат дополнительные документы помимо `index.md`. Их неперицифические пути к файлам явно зафиксированы в манифесте и не устанавливают прецедент для новых документов: `documenter-service/*` (configuration-guide, policy-reference, остаётся в корне как операционный файл), `docs/en/planned-architecture/*` (layer-0, layer-1, layer-2, decisions/index).

### 2.2 Вид ИИ (Манифест)

Файл **manifest** (`docs-manifest.yaml` или эквивалентный индекс) представляет собой **сгенерированный индекс**: frontmatter является источником истины, а manifest — его выводом. Единственным автором manifest выступает генератор (`tools/gen_manifest.py`, этап A); до внедрения этапа A единственным автором является навык Documentation Worker. Ручное редактирование `docs-manifest.yaml` запрещено; исправление неверного manifest означает исправление frontmatter документа и его повторную генерацию. Поля `version` в manifest производны от frontmatter документов; соответствие обеспечивается процедурой «regenerate-and-diff»: повторная генерация и сравнение с manifest на диске. Агенты НЕ ДОЛЖНЫ вслепую сканировать файловую систему. В manifest перечисляются все документы со следующими данными: путь к файлу (указывающий на `index.md` в `docs/en/`), заголовок, версия, статус (active / draft / deprecated), уровень абстракции, а также опциональное поле `has_translation`, указывающее на наличие русской версии. В manifest **не** включаются отдельные записи для русских переводов — они отслеживаются встроено через поле `has_translation`, которое содержит относительный путь от расположения manifest до русского файла (например, `docs/ru/glossary/index-RU.md`). Для каждой записи документа также отсутствует поле `language`; английский язык подразумевается самим фактом наличия документа в manifest. Вопросы авторства контента в случае конфликтов документов см. в правилах Content Precedence в `service-contract/index.md`. Таблица происхождения полей manifest является нормативной в `documenter-service/configuration-guide.md`, §Manifest Field Provenance.

### 2.3 Правила отношений

- Документы ссылаются друг на друга по каноническому идентификатору (имя файла без расширения).
- Перекрёстные ссылки используют стабильные якоря (заголовки), а не номера строк.
- Создание нового документа требует обновления манифеста и перекрёстных ссылок в соответствующих существующих документах.

### 2.4 Операционный резервный режим

Когда основанный на коде **Модератор** еще не реализован, файл `fallback/index.md` (**Операционный** файл в корне репозитория, замороженный согласно §1.5 `AGENTS.md`) определяет процедуру-заменитель с использованием именованных субагентов, запускаемых через данный каркас агента. Он охватывает назначение **Роли**, структуру вывода, последовательность **Фаз** и правила агрегации конфликтов. Ссылайтесь на него при выполнении **Сессии** Совета без поддержки инструментов.

Файлы рабочей области сессии, созданные во время сессий в режиме отката (`task-brief`, обзоры, документы консенсуса, протоколы обсуждений), находятся в `sessions/<id>/` и не входят в область действия Документатора; очистка и архивирование являются ответственностью оператора (см. `fallback/index.md`, §Конвенция рабочей области сессии).

### 2.5 Хранилище журнала изменений

Файлы журнала изменений хранят историю версий отдельно от содержимого документа в `CHANGELOGS/<id>.changes.md`. Заголовок каждого документа содержит единственную строку-ссылку, указывающую на файл журнала изменений (`changelog-path: CHANGELOGS/<id>.changes.md`). Агенты загружают журнал изменений по мере необходимости при редактировании документа; они добавляют новые записи в соответствующий файл журнала изменений, а не встраивают блоки CHANGES непосредственно в тело документа.

## 3. Языковая политика

### 3.1 Основной язык

Вся документация по проекту написана на **техническом английском языке**. Английская версия является авторитетной — источником истины.

### 3.2 Русские переводы

Русские варианты файлов находятся в `docs/ru/<id>/index-RU.md` (повторяя структуру английских файлов в `docs/en/`). Они предоставляются исключительно для удобства пользователей. Это вторичные/производные копии, которые **не** являются машиночитаемыми источниками. Наличие русского перевода отслеживается в манифесте через поле `has_translation`, которое содержит полный относительный путь от расположения манифеста до русского файла (например, `docs/ru/glossary/index-RU.md`). Отдельной записи в манифесте для русского файла не существует.

### 3.3 Процесс перевода

При изменении английского документа: сначала внесите изменение в `docs/en/<id>/index.md` → найдите соответствующий путь RU в поле манифеста `has_translation` → выполните быструю проверку версии (сравните количество разделов, структуры заголовков, позиции абзацев) → если обнаружено структурное несовпадение, переведите изменённые фрагменты на русский язык и обновите русский файл в `docs/ru/<id>/index-RU.md` → добавьте краткую запись в журнал, фиксирующую выполненное действие (раздел обновлён, перевод согласован или проверена согласованность).

Перевод не применяется к коду, конфигурациям или артефактам, не являющимся документами.

**Исключение текущей фазы — условие синхронизации RU условно снято (ADR-012).** Автоматическая русская синхронизация разрешена только как **действие после Approve**: после шага (5) Approve в §5.2, подтверждающего changeset, охватывающий английское изменение, Documentation Worker может автоматически перевести и записать `index-RU.md` по пути `has_translation` в манифесте, при условии прохождения всех Гейт записи фазы 4 (полнота перевода, паритет строк, сканирование EN-идентичности, соответствие глоссарию). Любой сбой gate блокирует запись и переводит её на ручной обзор оператором полного перевода. Документ может отказаться от автоматического перевода, указав `no_auto_translation: true` в frontmatter; такие документы переходят к аудиту дрейфа только в режиме отчёта. Когда локальный бэкенд перевода недоступен, облачный фоллбэк требует явного согласия оператора на каждый запуск (ADR-012). Это правило заменяет предыдущее полное приостановление от 2026-11-12.

## 4. Управление глоссарием

### 4.1 Структура

Глоссарий находится в файле `docs/en/glossary/index.md`. Каждая запись термина включает: название термина (каноническая форма), определение (на английском), русский эквивалент (если применимо) и необязательный тег категории (например, `[roles]`, `[protocol]`).

### 4.2 Обязанности агента

Прочитать перед использованием (дословно), создать при отсутствии многократно используемого термина, обновить при существенном изменении замечания (не просто перефразировании), а также проверить наличие всех терминов области перед выдачей результата (определить их в тексте или добавить в глоссарий в противном случае).

### 4.3 Машиночитаемый вариант

Только английская часть файла `docs/glossary/index.md` является основной (машиночитаемой) версией. Русские эквиваленты — это аннотации. Агенты работают исключительно с английскими определениями.

## 5. Рабочий процесс

### 5.1 Разделение ответственности

Структура документа, форматирование, подготовка контента, обновление манифеста, перекрестные ссылки и увеличение версии → **Навык Документационного рабочего** (/.agents/skills/documentation/SKILL.md). Согласование русского перевода → Документационный рабочий в соответствии с определением его навыка. Стратегические решения, разрешение неоднозначностей, утверждение объема работ и подтверждение плана изменений → **Основной агент**. Все механические операции записи выполняются через навык; чтение файлов (манифест, документы, глоссарий, журналы изменений) осуществляется непосредственно основным агентом. Агент НЕ ДОЛЖЕН изменять ни один файл документа, манифест или журнал изменений до тех пор, пока шаг (5) «Утвердить» не будет подтвержден человеком-оператором. Это правило не имеет исключений — даже исправление опечаток требует явного разрешения после этапа предложения. Все механические операции используют навык Документационного рабочего; на данном этапе не задействуются другие автоматизированные инструменты. Параметризованные скрипты записи в `tools/` (при наличии) передаются исключительно навыком Документационного рабочего и только после шага (5) «Утвердить»; скрипты обеспечивают атомарность, а не полномочия. Порядок записи изменений: содержимое документа → журнал изменений → манифест (манифест последним).

### 5.2 Процесс обработки документа

Каждая задача проходит через три фазы, контролируемые основным агентом. Подробные шаги выполняются с помощью навыка Documentation Worker в соответствии с его контрактом на выполнение рабочей задачи (/.agents/skills/documentation/SKILL.md).

**Фаза 1 — Понимание:** Основной агент читает манифест, целевые документы, связанные документы и глоссарий. Навык выполняет отчет UNDERSTAND/ANALYZE.
**Фаза 2 — Согласование:** Основной агент уточняет неоднозначности с человеком (см. §6), предлагает изменения на основе вывода PROPOSE навыка, ожидает явного одобрения на шаге (5).
**Фаза 3 — Выполнение:** Основной агент делегирует выполнение навыку (уровень доверия определяется масштабом изменений). Навык запускает EXECUTE/VERIFY, производит diff + отчет о соответствии. Основной агент проверяет результаты, затем REPORTs человеку.

### 5.3 Одновременная работа

Агенты, работающие с различными документами, должны координировать свои действия через манифест. Два агента не могут одновременно изменять один и тот же файл, если это явно не согласовано. Навык Documentation Worker обеспечивает защиту от одновременных записей (обнаружение состояния гонки TOCTOU) в соответствии со своим протоколом безопасности (/.agents/skills/documentation/SKILL.md).

### 5.4 Бюджет делегирования Подагента

Перед запуском подагента основной агент обязан оценить предполагаемый объем задачи (приблизительный бюджет токенов). Если оценка превышает 40 000 токенов, основной агент обязан рассмотреть возможность разделения работы на более мелкие подзадачи и делегировать каждую из них отдельно, а не запускать один чрезмерно объемный процесс. Оценка фиксируется в брифе делегирования. Это обеспечивает возможность проверки результатов подагента и предотвращает исчерпание контекста в ходе выполнения задачи.

**Лимит параллелизма.** Количество подагентов, которые основной агент может запускать одновременно, зависит от модели подагента, настроенной в `.opencode/opencode.jsonc` (см. блок комментариев там для переключения): локальная модель — не более **1** одновременного подагента (очередь последовательно); облачная модель — не более **2**. Лимит носит поведенческий характер (выполняется основным агентом); конфигурация не содержит механического ограничения. Задачи должны быть упорядочены для его соблюдения.

## 6. Обработка неоднозначности

Неопределённость возникает, когда существует более одного разумного подхода при отсутствии предварительных указаний, включая противоречивое использование терминов в разных документах, неструктурированные решения, вопросы предметной области, требующие фактических данных, выходящих за рамки сопоставления по шаблонам, или изменения, затрагивающие другие документы. Чётко опишите ситуацию, предложите 2–3 варианта с указанием последствий и дайте рекомендацию, дождитесь выбора человека. Если человек не отвечает и работа блокируется, фиксируйте нерешённые вопросы как открытые вопросы, а не делайте предположений.

## 7. Соглашения по файлам

### 7.1 Именование и макет

Используйте kebab-case для имён папок в `docs/en/` и `docs/ru/`; основной документ — `index.md`; русский перевод — `index-RU.md` в соответствующей зеркальной папке в `docs/ru/`. Черновые файлы временно имеют суффикс `.draft`. Файлы журнала изменений используют формат `CHANGELOGS/<id>.changes.md`.

### 7.2 Метаданные и соглашения о форматах

Заголовки метаданных следуют формату в стиле YAML; язык английский подразумевается наличием записи в манифесте, поле `Language` отсутствует. Обязательные поля frontmatter: `id`, `Version`, `Status`, `Abstraction`, `changelog-path`; необязательные: `has_translation`, `references`, `allow_non_index_paths`. Поле `Last Modified` удаляется из заголовков авторских документов (вычисляется из git в момент отображения при необходимости). Документы ссылаются на другие по каноническому идентификатору (имя файла без расширения). Перекрёстные ссылки используют стабильные якоря (заголовки), а не номера строк. Создание нового документа требует обновления манифеста и перекрёстных ссылок в соответствующих существующих документах.

### 7.3 Ограничения на размер документа

Каждый документ не должен превышать **200 строк** контента (без учёта метаданных и записей в журнале изменений). При превышении этого лимита необходимо приостановить процесс и предложить оператору варианты `Split` (разделение на поддокументы со стабильными идентификаторами и перекрёстными ссылками) или `Condense` (удаление деталей из разделов с низким приоритетом). Эскалация для oversized-документов обрабатывается с помощью навыка Documentation Worker (/.agents/skills/documentation/SKILL.md).

### 7.4 Уровни абстракции

Запрещается смешивать в одном документе широкие концепции и конкретные форматы/подписи. Уровни абстракции: `Conceptual` (принципы, цели, обоснование), `Protocol` (процедуры, фазы, логика принятия решений), `Format` (определения полей, схемы, подписи), `Reference` (глоссарии, контрольные списки, примеры конфигураций). Черновики, охватывающие несколько уровней, должны быть разделены по уровням. После утверждения поле `Abstraction:` становится постоянным.

### 7.5 Согласие о версионировании

Патч-версия (X.Y.**Z**) для исправления опечаток и форматирования, минорная версия (X.**Y**.Z) для добавления контента или структурных изменений, мажорная версия (**X**.Y.Z) для фундаментальных переписываний.

### 7.6 Хранилище журнала изменений

История версий документа в файле журнала изменений (changelog) оформляется в формате `<!-- CHANGES vX.Y.Z: description of change. -->`. Записи в журнале изменений хранятся отдельно от текстов документов — каждый документ ссылается на свой журнал изменений через параметр `changelog-path:` в метаданных.

## 8. Проверка соответствия

В конце любой **сессии**, изменяющей файлы документации, выполните финальную проверку соответствия: манифест актуален, русская локализация проверена согласно §3.3, все термины присутствуют в глоссарии, все перекрестные ссылки разрешаются, записи в журнале изменений добавлены. Пока действует приостановка по §3.3, русская локализация работает в режиме только для отчетов: фиксируйте расхождения, если существует файл RU, но не обновляйте его. Навык Documentation Worker выполняет эти проверки автоматически согласно своему чек-листу соответствия (/.agents/skills/documentation/SKILL.md); **Основной агент** проверяет результат перед сообщением о завершении. Запустите `tools/check_all` (детерминированный набор правил) в рамках проверки соответствия в конце **сессии**. Правила аудита «термины глоссария» и «согласованность абстракций» (правила 3 и 5 в `mvp-interfaces.md`) остаются зарезервированными для навыка/ИИ; инструмент НЕ ДОЛЖЕН утверждать, что реализует «правила аудита 1–6».
