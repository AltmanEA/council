## Техническая реализация

**Принцип:** всё, что несложно реализовать в коде, делается в коде; всё остальное делегируется ИИ.
Код обеспечивает предсказуемость протокола; ИИ обеспечивает содержание решений.

**Стек:** Python + LangChain. LangChain предоставляет абстракции для вызовов LLM, цепочек, агентов и памяти — всё, что необходимо для оркестровки многоагентной системы.

**Архитектурные решения:**

• **Оркестрация** — LangGraph (граф состояния LangChain). Фаза за фазой переходы управляются статус роли ролей. Готовая основа для будущего параллельного выполнения (Фаза разработки 2).

• **Состояние** — JSON-файлы в директории сессии (`sessions/<id>/`). Каждая фаза — это отдельный файл. Никакой лишней сложности: задачи имеют короткий срок жизни, а данные не передаются между обсуждениями.

• **Абстракция LLM** — единая функция `get_model()`. На начальном этапе (MVP) используется один провайдер, замена которого при масштабировании тривиальна.

Фазы протокола → компоненты: Модератор (оркестратор StateGraph), Ролевые агенты (один экземпляр на роль с промптом и контекстом), API оператора человека (точка входа для эскалации).

## Артефакты проекта

Протокол основан на трёх артефактах. Каждый из них имеет фиксированный набор элементов, и все переходы протокола вычисляются из этих элементов в коде; точный формат сериализации (структура файла, имена полей, синтаксис схемы) является вопросом реализации и здесь не специфицируется.

**Отзыв роли** — формируется каждой ролью в каждом раунде. Должен содержать: одно предложение, выражающее позицию; список выводов, где каждый вывод имеет уровень серьёзности (низкий / средний / высокий / критический), ссылку на объект из списка объектов задачи, необязательную позицию (поддержка / возражение), если вывод касается предложенного решения по этому объекту, и — только для критического уровня серьёзности — обоснование, указывающее на конкретный режим отказа или сценарий атаки; а также рекомендованные действия, открытые вопросы и статус роли из фиксированного набора (согласие / замечания / заблокировано в рамках области / заблокировано из-за эскалации), при этом последний статус сопровождается причиной эскалации, когда это применимо.

Три правила связывают элементы обзора и применяются механически: блокирующий статус требует наличия как минимум одного вывода с уровнем серьёзности «средний» или выше; статус «заблокированная эскалация» требует указания причины эскалации; критический вывод без обоснования, соответствующего формату, обрабатывается как вывод с уровнем серьёзности «высокий», при этом его первоначальная оценка сохраняется и сообщается оператору.

**Документ консенсуса** — основной результат, формируемый по завершении задачи. Должен содержать: принятое решение и обоснование; объекты обсуждения задачи с их результатами (согласовано или согласовано на условиях); замечания ролей, которые их высказали, каждое из которых привязано к соответствующему объекту обсуждения; открытые вопросы; пункты действий, возникшие в ходе обсуждения; ссылки на любые эскалации, которые были разрешены в процессе; а также, для обеспечения прозрачности, список критических оценок, которые были снижены из-за отсутствия обоснованного оправдания, как это было указано их первоначальными оценщиками.

**Запись эскалации** — формируется каждый раз, когда система передаёт проблему оператору. Должна содержать: тип эскалации (информационный пробел / неразрешимый конфликт / превышение порога риска), роль инициатора, уровень серьёзности, описание блокирующего фактора, позиции сторон в случае конфликта, конкретный запрос к оператору, опциональную стратегию отката с указанием времени ожидания ответа, результат резолюции (решение оператора / отложенный откат / частичное продолжение) и фазу, с которой возобновляется работа после разрешения.

Каждый из перечисленных выше элементов существует, потому что правило протокола его использует. Элемент, на который не ссылается ни одно правило, не должен присутствовать в артефакте; если правило не может быть выражено через элементы, это означает, что определение артефакта является неполным.

## Дорожная карта

Консилиум начинает свою работу с минимального состава и развивается органично.

Фаза 1 — три начальные роли, последовательный протокол, три типа эскалации.

Фаза 2 — расширение набора ролей (например, добавление эксперта по предметной области), внедрение параллельного режима проверки задач.

Фаза 3 — внедрение механизма взвешенного голосования для разрешения разногласий, разработка автоматизированного инструмента для формирования рекомендаций от различных ролей.

Фаза N — полная поддержка вложенных сессий, кросс-сессионных зависимостей и автоматизированных журналов аудита.
