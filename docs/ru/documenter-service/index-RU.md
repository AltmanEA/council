## Примечание о миграции (v1.0.0)

Эта спецификация полностью заменяет пакет Документатор версии v0.x. Предыдущий дизайн — уровни доверия, механизм политик, двойная блокировка, поверхность одобрения, терминал согласия, шлюз предварительной проверки, Хранилище хэшей, записи намерений — достиг тупика: механизмы контроля множились, не улучшая качество документации. Он был упразднён 19 ноября 2026 года по Консенсусу `sess-documenter-concept-revision` (решение оператора) и архивирован в `docs/en/archive/documenter-service/`. Этот документ представляет собой всю систему; архив устаревших версий — это история, а не источник авторитета.

## Принципы (нормативные)

- **OP-1 — Мгновенное утверждение оператором.** Один оператор может утвердить любое изменение документации в любой момент. Никакого ожидания, никаких барьеров: нет уровней, политических барьеров, блокировок, сигналов готовности, внеканальных потоков утверждения или блокирующих предварительных проверок. Акт утверждения — это один оборот разговора: оператор отвечает `approve` на предложенный набор изменений.
- **OP-2 — Максимальная простота.** Каждый сохранённый механизм должен обосновывать своё существование; по умолчанию — удаление. Жёсткий потолок: не более 12 файлов и около 3 100–3 600 строк кода инструментов документации (исполняемые инструменты только; `tools/README.md` — это документация и не учитывается), одна команда, видимая оператору, без демонов, без файлов состояния, без файлов конфигурации. Превышение потолка требует явного утверждения оператора.
- **OP-3 — Аудит коммитов как основной контроль ошибок.** Ошибки контролируются постфактум: коммиты проверяются на соответствие правилам документации, и плохой коммит откатывается с помощью git. Аудит никогда не блокирует никаких действий.
- **Позиция эволюции.** Детерминированные действия (полностью определённые входными данными и правилами, без участия суждений) должны в конечном итоге делегироваться скриптам в `tools/`, запускаемым навыком в рамках набора изменений, утверждённого оператором; скрипты никогда не обладают самостоятельной властью записи. Каждый продвинутый скрипт должен соблюдать потолок OP-2 за счёт вытеснения — замещением, а не добавлением. Эта позиция не разрешает новых гейтов одобрения, новые инструменты или новые файлы состояния. Отложенные элементы записываются в документ консенсуса сессии, породившей их; детальная разработка откладывается на будущую отдельную сессию.

## Операционная модель

Цикл на изменение:

1. Агент (или оператор) предлагает набор изменений; навык Documentation Worker подготавливает его и упаковывает **все файлы одного логического обновления в один коммит** (инвариант одного коммита — основа, обеспечивающая возможность отката как жизнеспособного восстановления).
2. Агент запускает инструмент аудита на изменении (рекомендательный проход перед коммитом). Результат добавляется к сводке одобрения: **тихо, если всё чисто**; замечания выводятся в виде краткого списка с однострочными подсказками по исправлению. Аудит никогда не блокирует — замечания информируют оператора, оператор принимает решение.
3. Оператор просматривает итог (затронутые файлы, категория изменения, разница по строкам, флаг механического/семантического характера) и отвечает `approve`. Для **семантического** изменения (существенного переосмысления смысла) необходимо указать объект: `approve: rewrite of the Safety section`. Механическое изменение принимает просто `approve`. Агент предлагает классификацию механического/семантического характера; оператор может её изменить.
4. Навык Documentation Worker записывает файлы (его вызовы `tools/` поддерживают порядок: содержимое документа → changelog → manifest), и изменение фиксируется в виде одного атомарного коммита.
5. Позже, по запросу, оператор запускает аудит по недавним коммитам; при обнаружении проблемного коммита оператор откатывает его. Решение об откате полностью зависит от суждения оператора.

Навык Documentation Worker (`.agents/skills/documentation/SKILL.md`) остаётся единственным автором `docs/`, `docs-manifest.yaml` и `CHANGELOGS/`. Сервиса Документатор, интерфейса MCP и промежуточной инстанции между предложением и согласием оператора не существует.

### Сложные правки

Для сложных обновлений, охватывающих несколько этапов, навык может выполнять промежуточные правки перед сборкой итогового пакета. Промежуточные состояния не являются коммитами и не нарушают инвариант единственного коммита (который применяется только к финальному коммиту). Одобрение `approve` оператора привязывается к итоговому собранному состоянию на Карточке согласования — план является внутренним рабочим контекстом агента, а не объектом одобрения. Проверка аудита выполняется только на собранном пакете. Промежуточные файлы находятся в области, ограниченной рамками сессии, вне дерева `docs/`; `sessions/` исключён из отслеживания git по соглашению репозитория.

## Архив

Архив — это папка, содержащая устаревшие документы, которые больше не обладают авторитетом, но сохраняются для чтения, чтобы обоснование прошлых решений оставалось доступным. Конвенция: `docs/en/archive/<id>/` с русскими зеркалами в `docs/ru/archive/<id>/`; корневой guard-файл `docs/en/archive/index.md` фиксирует конвенцию (только история, никогда не авторитет; никогда не удалять — история git является путём восстановления).

Архивированные документы сохраняют `Status: archive` в своём frontmatter и остаются под контролем манифеста, так что агенты обнаруживают их через манифест (согласно `documentation-rules` §2.2), а не слепым сканированием. Распознавание двухслойное: поле `Status: archive` во frontmatter — это истина, которую печатает манифест, тогда как префикс пути `docs/en/archive/` (и `docs/ru/archive/`) — маркер, по которому его определяет механизм аудита. Два слоя служат разным целям — обнаруживаемость и исключение, — и никакого чекера согласованности их не связывает (OP-2); расхождение между ними выявляется неформально и никогда не блокируется.

Архивированные документы доступны только для чтения в силу дисциплины, а не гейта (OP-1): навык Documentation Worker рассматривает архивную цель как не подлежащую правке и отображает любую запись, которая привела бы к попаданию в архив, в строке `Archive:` Карточки согласования в момент одобрения, тогда как `git revert` (OP-3) исправляет ошибку. Плановая обязанность перевода к архивам не применяется; устаревшее RU-зеркало внутри архива ожидаемо и не является дефектом.

## Контроль ошибок

### Инструмент аудита

`tools/check_all.py` — единственный механизм аудита. Он работает только для чтения, детерминирован и никогда не блокирует: ни один вызывающий не обязан ожидать его завершения как условия работы. Он выполняется в двух контекстах вызова: в качестве рекомендательной проверки перед коммитом (обязательная, запускается агентом, не выводит сообщений, если всё чисто) и после коммита (запускается оператором **по требованию**; например, перед точками выпуска или при возникновении подозрений).

Набор проверок:

| Проверка | Область | Обнаруживает |
|-------|-------|---------|
| Соответствие контента (правила 1–2, 4, 6, именование, схема согласно `documentation-rules` §8) | изменённые файлы | структура, changelog, перекрёстные ссылки, дефекты подсчёта строк |
| Согласованность манифеста | всё дерево | `docs-manifest.yaml` расхождения с фактическими данными frontmatter |
| Устаревание перевода EN↔RU | всё дерево | отсутствие или структурные отклонения RU-зеркал |
| Удаление контролируемых файлов | всё дерево | удаление документов, отслеживаемых манифестом |

Коды выхода — это информационные метаданные, которые никогда не являются блокирующими: `0` — чисто, `1` — обнаружены замечания, `2` — обнаружены критические замечания. Отображение для человека: в случае «чисто» вывод отсутствует; в остальных случаях `⚠ findings: N` или `🚨 critical: N` плюс однострочные подсказки по исправлению, сгруппированные и отсортированные по уровню серьёзности. `--severity` задаёт минимальную **отчётную** серьёзность (по умолчанию `low`; `--strict` ≡ выводить всё); внутренняя ошибка и неверный токен `--rule` также дают код `2`, но отличаются по выводу (`check_all: INTERNAL ERROR` / `ERROR:`), а не маркером `🚨`. (Статус реализации: указанный замороженный контракт поставляется в `tools/check_all.py` после переписывания фазы 0; хук pre-commit и прозаические контракты были синхронизированы в том же измененияемом наборе.)

Документы под префиксом пути архива (`docs/en/archive/`, `docs/ru/archive/`) отфильтровываются перед каждым проходом проверок: устаревшие документы не обязываются соблюдать правила, которым следуют живые документы. Каждый будущий участник набора проверок ОБЯЗАН наследовать это исключение. Исключение молчаливо в отображении (указанный контракт «чисто — значит тихо» не затронут); прозрачность архива отображается на Карточке согласования.

### Восстановление

`git revert` — это путь восстановления для любого ошибочного коммита. Поскольку каждое логическое обновление точно соответствует одному атомарному коммиту, revert всегда является жизнеспособной единичной операцией. Если логическое обновление было разбито на несколько коммитов (ручной обход), система эвристически выдает предупреждение, а восстановление требует ручной сортировки и анализа.

### Принятые риски

Эти риски осознанно принимаются в соответствии с OP-3:

1. **Семантическая слепота.** Механический аудит проверяет структуру, а не смысл; неверное, но синтаксически корректное изменение проходит аудит. Мера защиты: суждение оператора в момент одобрения (одобрения с указанием объекта для семантических изменений).
2. **Разделение ручных коммитов.** Обход группировки навыков снижает надёжность отката; смягчается только предупреждениями аудита.
3. **Усталость от одобрений.** Оператор может ставить «штамп»; смягчения имеют форму UX-решений, а не контрольных точек.
4. **Задержка аудита при масштабировании.** Проверка всего дерева занимает несколько секунд; корректность важнее скорости.
5. **Устаревание RU.** Перевод выполняется, когда оператор запускает его; задержки накапливают дрейф без автоматического принуждения.
6. **Заброшенная промежуточная работа.** Если агент прерван во время поэтапной работы, промежуточные файлы могут сохраняться в областях рабочей среды, игнорируемых git. Ничего не коммитится; закоммиченное состояние остаётся неизменным. Очистка — обязанность оператора в соответствии с жизненным циклом рабочей среды сессии. Восстановление не требуется.
7. **Слепое пятно архива.** Размещение живого документа под путём архива делает его невидимым для аудита (контрабанда). Мера защиты: строка `Archive:` Карточки согласования в момент одобрения перехватывает попадание в архив — самый рискованный момент, — а `git revert` обеспечивает восстановление. Это контроль на основе суждения, а не гейт (OP-1).

## Сохранённые инструменты

Сохранены: `tools/gen_manifest.py` (единственный генератор манифестов), `tools/check_all.py` (движок аудита), `tools/check_drift.py` (структурное сравнение EN↔RU и write-гейты перевода `--phase4`), `tools/docmeta.py`, `tools/bump_version.py`, `tools/classify_bump.py`, `tools/translation_status.py`, `tools/sync_translator.sh`, `tools/tests_helpers.py`, а также хук `hooks/pre-commit`, работающий только в режиме предупреждений. `tools/check_parity.py` вытеснен гейт-правилами `phase4-*` (impl-guide, фаза 1, 19.11.2026). Удалены в рамках дизайна v0: пакет `documenter_service/`, `documenter_policy.yml`, наложения активации, сентинел готовности operator-ingress, терминалы согласия, записи намерений, хэш-хранилища и журналы аудита.
