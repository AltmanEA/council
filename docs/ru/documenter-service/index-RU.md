## Примечание о миграции (v1.0.0)

Эта спецификация полностью заменяет пакет Документатор версии v0.x. Предыдущий дизайн — уровни доверия, механизм политик, двойная блокировка, поверхность одобрения, терминал согласия, шлюз предварительного аудита, Хранилище хэшей, записи намерений — достиг тупика: механизмы контроля множились, не улучшая качество документирования. Он был упразднён 19 ноября 2026 года по Консенсусу `sess-documenter-concept-revision` (решение оператора) и архивирован в `docs/en/documenter-service/legacy/`. Этот документ представляет собой всю систему; архив устаревших версий — это история, а не источник авторитета.

## Принципы (нормативные)

- **OP-1 — Мгновенное одобрение оператором.** Один оператор может одобрить любое изменение документации в любой момент. Никаких задержек, никаких барьеров: нет уровней, политических фильтров, блокировок, индикаторов готовности, внеканальных потоков одобрения или блокирующих предварительных проверок. Акт одобрения занимает один ход диалога: оператор отвечает `approve` на предложенный набор изменений.
- **OP-2 — Максимальная простота.** Каждый сохранённый механизм должен обосновывать своё существование; по умолчанию применяется удаление. Жёсткий потолок: не более 12 файлов и около 3 100–3 600 строк кода инструментов документации, одна команда для оператора, без демонов, файлов состояния и файлов конфигурации. Превышение потолка требует явного одобрения оператора.
- **OP-3 — Аудит коммитов как основной контроль ошибок.** Ошибки контролируются постфактум: коммиты проверяются на соответствие правилам документации, а ошибочный коммит откатывается с помощью git. Аудит никогда не блокирует никаких действий.

## Операционная модель

Цикл на изменение:

1. Агент (или оператор) предлагает набор изменений; навык Documentation Worker готовит его и упаковывает **все файлы одного логического обновления в один коммит** (инвариант одного коммита — основа, обеспечивающая возможность отката как жизнеспособного восстановления).
2. Агент запускает инструмент аудита для изменения (рекомендательная проверка перед коммитом). Результат добавляется к сводке одобрения: **тихо, если всё чисто**; замечания выводятся в виде короткого списка с однострочными подсказками по исправлению. Аудит никогда не блокирует — замечания информируют оператора, оператор принимает решение.
3. Оператор просматривает итог (затронутые файлы, категория изменения, дельта строк, флаг механического/семантического характера) и отвечает `approve`. Для **семантического** изменения (существенной переписки смысла) необходимо указать объект: `approve: rewrite of the Safety section`. Механическое изменение принимает просто `approve`. Агент предлагает классификацию механического/семантического характера; оператор может её изменить.
4. Навык Documentation Worker записывает файлы (его вызовы `tools/` сохраняют порядок: содержимое документа → changelog → manifest), и изменение фиксируется в виде одного атомарного коммита.
5. Позже, по запросу, оператор запускает аудит по недавним коммитам; при обнаружении проблемного коммита оператор откатывает его. Решение об откате полностью зависит от суждения оператора.

Навык Documentation Worker (`.agents/skills/documentation/SKILL.md`) остаётся единственным автором `docs/`, `docs-manifest.yaml` и `CHANGELOGS/`. Нет службы Документатор, нет интерфейса MCP и нет промежуточной инстанции между предложением и согласием оператора.

## Контроль ошибок

### Инструмент аудита

`tools/check_all.py` — единственный механизм аудита. Он работает только для чтения, детерминирован и никогда не блокирует: ни один вызывающий не обязан ожидать его завершения как условия работы. Он выполняется в двух контекстах вызова: в качестве рекомендательной проверки перед коммитом (обязательная, запускается агентом, не выводит сообщения при отсутствии замечаний) и после коммита (запускается оператором **по требованию**; например, перед точками выпуска или при возникновении подозрений).

Набор проверок:

| Проверка | Область | Обнаруживает |
|-------|-------|---------|
| Соответствие контента (правила 1–2, 4, 6, именование, схема согласно `documentation-rules` §8) | изменённые файлы | структура, changelog, кросс-ссылки, дефекты подсчёта строк |
| Согласованность манифеста | всё дерево | `docs-manifest.yaml` расходится с данными frontmatter |
| Устаревание перевода EN↔RU | всё дерево | отсутствуют или структурно расходятся RU-зеркала |
| Удаление контролируемых файлов | всё дерево | удаление документов, отслеживаемых манифестом |

Коды выхода — это информационные метаданные, которые никогда не являются блокирующими: `0` — чисто, `1` — обнаружены замечания, `2` — обнаружены критические замечания. Отображение для человека: в случае «чисто» вывод отсутствует; в противном случае `⚠ findings: N` или `🚨 critical: N` плюс однострочные подсказки по исправлению, сгруппированные и отсортированные по уровню серьёзности. (Статус реализации: поставляемый `check_all.py` всё ещё использует устаревшие коды: 0 — чисто / 1 — замечания высокой важности и выше / 2 — внутренняя ошибка; переход к описанному выше контракту является частью ожидаемого переписывания check_all.)

### Восстановление

`git revert` — это путь восстановления для любого ошибочного коммита. Поскольку каждое логическое обновление представляет собой ровно один атомарный коммит, откат всегда является жизнеспособной единичной операцией. Если логическое обновление было разбито на несколько коммитов (ручное обходное решение), система аудита эвристически выдаёт предупреждение, а восстановление требует ручной сортировки и анализа.

### Принятые риски

Эти риски осознанно принимаются в соответствии с OP-3:

1. **Семантическая слепота.** Механическая проверка аудита проверяет структуру, а не смысл; ошибочное, но корректно оформленное изменение проходит аудит. Мера защиты: суждение оператора в момент одобрения (одобрения с указанием объекта для семантических изменений).
2. **Разделение коммитов вручную.** Обход группировки навыков снижает надёжность отката; смягчается только предупреждениями аудита.
3. **Усталость от одобрений.** Оператор может ставить «штамп»; меры смягчения имеют форму UX, а не являются барьерами.
4. **Задержка аудита при масштабировании.** Полная проверка дерева занимает несколько секунд; правильность важнее скорости.
5. **Устаревание RU.** Перевод выполняется, когда оператор запускает его; задержки накапливают расхождения без автоматического принуждения.
