## Назначение

Документатор — это **вспомогательный сервис**, находящийся вне трёхслойной цепочки и поддерживающий качество документации согласно правилам `AGENTS.md`. Он работает как **утилита по требованию** — все функции запускаются только по явному вызову оператора; фоновые процессы и наблюдатели за файлами не действуют автономно. Он предоставляет два интерфейса: `audit()` для отчётов только на чтение и `delegate()` для операций записи через навык Documentation Worker. Четырёхуровневая модель доверия управляет возможностями записи delegate(). Схемы параметров интерфейсов авторитетны в разделе §Интерфейсы; поля конфигурации определены в Справочнике политик (`documenter-service/policy-reference.md`), а структуры данных во время выполнения — в Руководстве по конфигурации (`documenter-service/configuration-guide.md`).

Граница области: Документатор работает исключительно с документационными артефактами, отслеживаемыми в манифесте, и с собственным операционным состоянием (каталог `documenter/`). Файлы вне этих пространств — рабочие файлы сессий (`sessions/<id>/`), выходы архивирования и любые иные артефакты вне манифеста — явно исключены из области Документатора. Интерфейсы `audit()` и `delegate()` принимают только значения `target_id` из манифеста; любой вызов, ссылающийся на файлы вне манифеста, отклоняется с `error_category: unknown`.

## Позиция в архитектуре

Документатор — это **вспомогательный сервис** вне трёхслойной цепочки. Его вызывает операторская поверхность Слоя 2 (явный вызов MCP-инструмента), а для записей с опорой на LLM он использует **порт исполнения Слоя 1**, чтобы достичь Documentation Worker. Он никогда не обращается к Слою 2 или Слою 0 напрямую, и Слой 2 никогда не вызывает LLM от имени Документатора. События и вердикты возвращаются вызывающей поверхности синхронно; Документатор не держит цикла событий, не имеет подписок и не имеет наблюдателя за файловой системой.

Он не является частью пути ролевого агента Слоя 1: ScenarioLoader и RoleAgentFactory принадлежат Слою 1 (`planned-architecture/layer-1.md`), поэтому отношений равного или подчинённого с ScenarioLoader не существует. Документатор не оркестрирует сессии Консилиума и не имеет причинной зависимости от потока оркестрации. Каждый вызов явный и исходит от оператора. **Исключение:** операции только на чтение (`audit()`) доступны Оператору, Агенту и Сервису в пределах разрешённой области согласно матрице авторизации (§Caller Identity and Authorization, operator-surface); операции записи (`delegate()`) исходят от оператора или от делегированного агента. Намерение записать требует проверки ступени по политике `allowed_operations`; вызовы предварительного просмотра (`preview: true`) полностью обходят проверки ступени (§Preview Exemption).

Синхронный режим (`pre_check`, см. §Интерфейсы) — это внутри-сессонный шлюз целостности. Запрос шлюза поступает через операторскую поверхность Слоя 2, вызывает Документатора и возвращает синхронный вердикт этой поверхности. Документатор никогда не принимает вызовы от Слоя 0 или Слоя 1; синхронный режим сохраняет семантику «простаивает до вызова». Все режимы выполняют независимое полное сканирование целевых документов. Когда Документатор недоступен (сбой сети, тайм-аут, сервис остановлен), вызов аудита синхронно возвращает `unavailable`; поверхность испускает событие `precheck.unavailable` и откладывает переход до переопределения через `council.override_precheck`.

## Интерфейсы

### audit() — Диагностика только на чтение

Возвращает структурированный отчёт, не затрагивая никакого пути записи. Сканирует документы на соответствие правилам, используя данные манифеста и глоссария. Приведённая ниже таблица — авторитетная схема параметров этого интерфейса.

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста, либо `"*"` для всех |
| severity_min | enum | Минимальная серьёзность для включения: `low`, `medium`, `high`, `critical`. По умолчанию: `low` |
| pre_check | bool | Флаг шлюза целостности внутри сессии, устанавливаемый операторской поверхностью Слоя 2 на границах фаз (см. `operator-surface/index.md`, §pre_check Gate). Семантика сканирования идентична; отчёт дополнительно возвращается вызывающему как синхронный вердикт шлюза. Путь записи не задействован. По умолчанию: `false` |
| scan_cursor | string \| null | Токен продолжения от предыдущего частичного сканирования (когда `has_remaining` было `true`). Заставляет `audit()` возобновить сканирование с сохранённой позиции. Отсутствие или `null` означает начало нового полного сканирования. |

| Возвращает | Тип | Описание |
|---------|------|-------------|
| audit_id | string | Уникальный идентификатор этого вызова аудита (UUIDv4). Сохраняется в реестре аудита (`documenter-service/configuration-guide.md`, §Audit Registry) вместе с меткой времени, областью, выводами, `scanned_ids`, `has_remaining` и `scan_cursor`. Используется шлюзом предварительного аудита `delegate()` для проверки свежести, покрытия области, отсутствия блокирующих выводов и завершённости сканирования. |
| report | dict | Структурированный список выводов с полями severity, subject, document_id, description, suggested_action |
| has_remaining | boolean | `true`, когда сканирование приостановлено из-за `rescan_batch_ceiling`; вызывающему следует повторно обратиться `audit(scan_cursor=<значение>)` с возвращённым `scan_cursor`, чтобы продолжить. |
| scan_cursor | string \| null | Токен продолжения для возобновлённых сканирований. Присутствует только когда `has_remaining` равно `true`. Непрозрачное значение, кодирующее позицию последнего обработанного документа. |

Уровни серьёзности (единые для всех интерфейсов и схемы событий):

| Уровень | Описание | Влияние на оператора |
|-------|-----------|-----------------|
| `low` | Косметическая проблема, без влияния на данные | Только след в журнале аудита |
| `medium` | Потенциальное несоответствие, низкий риск | Отображается в отчёте; событие сохраняется в журнал только для добавления. Запись может быть выполнена только при явном одобрении оператора (не автоматически). |
| `high` | Подтверждённая проблема, умеренный риск | Блокирует запись по умолчанию; требует явного одобрения оператора перед продолжением. |
| `critical` | Нарушение целостности данных, непосредственный риск | Блокирует запись + обязательная фиксация постмортема (§Протокол безопасности #8); путь автоприменения отсутствует на любой ступени |

### Семантика одобрения

Одобрение — это явное действие оператора посредством внеполосного вызова инструмента `documenter.approve(approval_id, operator_id)` (§Documenter Integration, operator-surface). Документатор не отслеживает зависящие от времени состояния между вызовами и не одобряет выводы автоматически: таймера и фонового процесса не существует (см. §Назначение, «простаивает до вызова»). Единственный путь автовыполнения — автоприменение по паттерну на Ступени 3, обусловленное предшествующей авторизацией паттернов оператором, но никогда истечением времени.

Внеполосный поток одобрения: (1) на Ступени 2+ `delegate()` возвращает `approval_required` с `approval_id` и хешем diff, но не выполняет записи; (2) оператор независимо вызывает `documenter.approve(approval_id, operator_id)` (это ДОЛЖЕН быть отдельный вызов, отличный от вносящего предложение); (3) одобряющий `operator_id` ДОЛЖЕН отличаться от идентификатора актора вносящего вызов, чтобы предотвратить самоодобрение; (4) после успешного одобрения система выполняет запись, используя тот же хеш diff для привязки; (5) изменившийся diff аннулирует ожидающие одобрения.

Одобрение истекает по прошествии настроенного окна (`approval_expiry_window`, по умолчанию 30 минут согласно policy-reference.md §Field Reference). Истёкшее одобрение нужно получить заново, прежде чем diff сможет быть применён. Новый хеш diff аннулирует любое ещё действующее одобрение.

Устаревшие соответствия из предыдущих версий: `info` → `low`, `warning` → `medium`, `error` → `high`. Все инструменты отображения ДОЛЖНЫ сопоставлять: `critical`→красный, `high`→оранжевый, `medium`→жёлтый, `low`→серый.

### delegate() — Запись через навык Documentation Worker

Вызывает определённую операцию над документом с управлением уровнем доверия. Вызов возможен только после прохождения оператором шлюза политики. Приведённая ниже таблица — авторитетная схема параметров этого интерфейса; потребляемые им поля политики определены в Справочнике политик (§Перекрёстные ссылки).

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста |
| change_type | enum | Один из: `update`, `split`, `create_ru`, `custom` |
| trust_level | enum | *Запрос* вызывающего, а не фактическое значение: `safe` или `review`. Документатор выводит требуемый базовый уровень по §Классификация доверия и принимает запрос, только если он равен этому базовому уровню или строже его (`requested >= derived`); запрос ниже базового уровня отклоняется с `error_category: trust_mismatch`. Фактический уровень — запрошенный. |
| diff | string (base64-encoded) | Машиночитаемый diff для предпросмотра оператором, закодированный в base64 для обеспечения JSON-безопасной передачи согласно ограничениям UTF-8 JSON (§Common Conventions, service-contract). Обязателен для всех ступеней. |
| audit_id | string | Идентификатор из предыдущего возврата `audit()`. Проверяется по политике `audit_freshness`. Опускается только когда шлюз явно отключён в файле политики. |
| preview | boolean | Когда `true`, вызов возвращает только diff без намерения записать и освобождается от проверок `allowed_operations` на всех ступенях (§Preview Exemption). Когда опущен или `false`, вызов несёт намерение записать и подчиняется обычным ограничениям ступени (Ступени 0–1 всегда запрещают запись независимо от прочего; Ступень 2+ требует явного одобрения; Ступень 3 может автоприменять на основе паттернов). |

Поток выполнения: `аудит → вычислить diff → представить оператору → ждать approve/reject → применить при одобрении → зафиксировать по Протоколу многофайловой фиксации (§Протокол безопасности #9) → записать в журнал аудита`. Запись в каждый файл использует системный вызов temp-file + rename (см. §Протокол безопасности #5), гарантируя атомарный переход от подготовленного состояния к зафиксированному содержимому для одного файла. Межфайловая атомарность самим переименованием НЕ обеспечивается — см. §Семантика отказа.

**Шлюз предварительного аудита:** По умолчанию `delegate()` требует действительный `audit_id` из предыдущего вызова `audit()`. Проверка выполняется по реестру аудита (`documenter-service/configuration-guide.md`, §Audit Registry): (1) `audit_id` должен существовать; (2) его `issued_at` должен попадать в окно `audit_freshness` (поле политики, по умолчанию 30 минут; схема: `documenter-service/policy-reference.md`, §Field Reference); (3) его `scope` должен полностью покрывать `target_id` (`*` совпадает с любым, иначе точное совпадение); (4) для `target_id` в реестре не должно быть вывода уровня `high` или `critical`; (5) если `has_remaining` было `true` для зарегистрированного сканирования, делегирование отклоняется до выполнения завершённого пересканирования (продолжение через курсор `audit(scan_cursor=<значение>)`). Отклонение по правилам (1–3) использует `error_category: audit_mismatch`; по (4) или (5) — `error_category: blocking_finding`. Предлагаемое действие в обоих случаях: заново выполнить `audit()` для цели и повторить попытку. Когда реестр аудита отсутствует, повреждён или нечитаем, шлюз ЗАКРЫВАЕТСЯ ОТКАЗОМ — все операции записи запрещены до явного переопределения оператором. Переопределение требует аутентифицированного действия через `documenter.override_gate(reason, operator_id)`, которое протоколирует инцидент и разрешает ровно один последующий вызов `delegate()` без нового аудита. Повторные переопределения требуют одобрения Ступени 2+. Шлюз настраивается полем политики `audit_freshness`, но по умолчанию действует принудительно.

**Классификация доверия:** Фактический уровень доверия назначает Документатор, а не вызывающий. Параметр вызывающего `trust_level` может равняться выводимому базовому уровню или ужесточать его, но никогда не ослабляет: на шкале `safe < review` инвариант — `requested >= derived`, а фактический уровень — `requested`. Если `requested < derived`, `delegate()` отклоняет вызов с `error_category: trust_mismatch` ещё до этапа одобрения оператором. Тихого повышения не происходит. Когда классификация неоднозначна, применяется `review`. Справочник политик (`documenter-service/policy-reference.md`) может поднять базовый уровень над табличным, но НЕ ДОЛЖЕН понижать его (§Policy File, §Authority rule). `suggested_trust_level` в §Event Schema — это выход того же классификатора.

| change_type | Статический базовый уровень (загрузка политики) | Динамический вывод (вызов) | `safe` разрешён |
|-------------|---------------------------|--------------------------------|------------------|
| `update`      | `safe`                    | `safe`, если каждый фрагмент механический; иначе `review` | Да, только для полностью механического diff |
| `split`       | `review`                  | `review`                         | Никогда |
| `create_ru`   | `review`                  | `review`                         | Никогда (авто-исправление RU запрещено в MVP) |
| `custom`      | `review`                  | `review`                         | Никогда (значение по умолчанию при неопределённости) |

Статический базовый уровень для `update` равен `safe` ради проверки политики при загрузке (валидатор видит только `change_type`). Динамический вывод выполняется во время вызова: полностью механический diff выводит `safe`, любой смысловой фрагмент выводит `review`. Запись политики, называющая `update` + `safe`, проходит проверку при загрузке; немеханический diff по-прежнему выводит `review` и отклоняет запрос `safe` с `trust_mismatch`.

**Семантика отказа:** При прерывании или сбое во время выполнения `delegate()` операция должна следовать модели «всё или ничего» — частичные записи не сохраняются для отдельного файла (гарантируется системным вызовом temp-file + rename). Частичные фиксации между файлами возможны лишь в промежутках между переименованиями разных файлов; это не предотвращается ни атомарностью переименования, ни журналируемыми файловыми системами (журналирование гарантирует внутреннюю согласованность файловой системы, а не межфайловую атомарность или доставку журнала аудита). Протокол многофайловой фиксации (§Протокол безопасности #9) обеспечивает восстанавливаемую окончательную согласованность: сбой в середине последовательности оставляет обнаружимое частичное состояние с оставшимися подготовленными файлами и записью намерения, которая сверяется следующей проверкой на холодном старте (§Configuration Guide, Intent Record). Восстановление без вмешательства оператора происходит автоматически, когда внешних изменений не было; в противном случае испускается структурированное событие об ошибке и восстановление требует явного повторного вызова. Это превращает незаметную порчу в задокументированное ограничение с явным путём смягчения. Будущие версии (Phase 2+) введут checkpoint/resume через атомарные снимки состояния на основе WAL; до тех пор операторы ДОЛЖНЫ считать каждую границу фазы точкой фиксации.

События, испускаемые во время delegate(), используют Схему событий, определённую в §Configuration Guide. Каждая ошибка delegate() испускает событие по §Event Schema с `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`).

## Ступени доверия

Четыре уровня развёртывания, дающие прогрессивно бо́льшие возможности записи. Переход на каждую следующую ступень требует явной команды оператора.

| Ступень | Возможность | Автовыполнение | Diff обязателен | Область |
|------|-----------|----------------|---------------|-------|
| 0 | Только аудит (MVP) | Отсутствует | Н/П (записей нет) | Чтение манифеста + документов, формирование отчёта |
| 1 | Предпросмотр diff | Отсутствует | Да | Формирование diff, без записи в файловую систему |
| 2 | Подтверждение на каждое изменение | Нет | Да, поэлементно | Применяет изменения только после поштучного одобрения |
| 3 | Пакетное одобрение | По паттернам | Да, на пакет со сводками по группам | Авторизованные паттерны применяются автоматически; критические элементы требуют поэлементного расширенного просмотра |

Ступени 0–1 поставляются в составе MVP. Ступень 2+ попадает в эксплуатацию только после появления задокументированного файла политики, авторизующего конкретные сочетания `change_type` + `trust_level`. Ступень 2+ дополнительно взаимосвязана на уровне архитектуры: ни один вызов Ступени 2+ не принимается, пока спецификация Operator Surface & Escalation не определит аутентифицированный внеполосный канал одобрения. Самого файла политики недостаточно. Продвижение на Ступень 2+ требует: (a) составленного файла политики по `documenter-service/policy-reference.md` И (b) заархивированного брифинга оператора, на который ссылается файл политики (поле `briefing_ref`). Оба условия ДОЛЖНЫ быть выполнены до первого вызова Ступени 2+. Пошаговую процедуру см. в §Рабочий процесс авторизации. Автоприменение по паттернам на Ступени 3 — единственный путь автовыполнения в системе; оно проистекает из предшествующей авторизации паттернов оператором, а не из истечения времени (см. §Семантика одобрения).

### Руководство по выбору ступени

| Ступень | Рекомендуемый случай применения | Предпосылка |
|------|---------------------|---------------|
| 0 | Начальное развёртывание, изучение поведения системы | Отсутствует |
| 1 | Проверка точности без риска изменений | Отсутствует |
| 2 | Активное сопровождение, выборочные исправления | Файл политики (`documenter-service/policy-reference.md`), авторизующий операции Ступени 2 |
| 3 | Крупномасштабная расчистка, сезонная реструктуризация | История эксплуатации с долей одобрения ≥90% на Ступени 2 в течение 2 недель |

### Рабочий процесс авторизации

Процедура, посредством которой оператор предоставляет возможность записи. Документатор не выполняет ни один из этих шагов самостоятельно; каждый — явное действие оператора, а подробный контрольный список со способами отказа проверки находится в `documenter-service/policy-reference.md`, §Authorization Workflow.

1. **Аудит** — устраните выводы `high` и `critical` на текущей ступени. Продвижение ступени над несоответствующим корпусом автоматизирует дрейф, а не расчистку.
2. **Составление** — напишите файл политики: записи `allowed_operations` для предполагаемых сочетаний `change_type` + `trust_level` + `targets`, плюс поля операционной настройки.
3. **Проверка** — загрузите файл-кандидат в режиме только проверки. Загрузка падает на непустом `allowed_operations` ниже Ступени 2, на `trust_level` ниже выводимого базового уровня из §Классификация доверия либо на нераспознанном значении политики.
4. **Брифинг** — заархивируйте брифинг оператора (делегированная область, максимальное число документов, которые может затронуть один вызов, процедура отката) и направьте на него `briefing_ref`. Задавайте `active_tier` и `briefing_ref` одной правкой, чтобы частичная правка не оставила Ступень 2+ без брифинга.
5. **Продвижение** — следующий вызов выполняется на новой ступени. Первый `delegate()` на новой ступени нацелен на один документ с низким риском; diff просматривается поэлементно независимо от ступени.
6. **Оценка** — Ступень 3 требует задокументированных свидетельств (доля одобрения ≥90% на Ступени 2 за предшествующие две недели журнала событий) и явного перечисления авторизованных паттернов; ни один паттерн не выводится.

Откат симметричен: понижение `active_tier` вступает в силу при следующем вызове; выполняющийся `delegate()` завершается на той ступени, на которой был принят.

## Протокол безопасности

1. **Снимок перед изменением**: зафиксировать состояние git и коммит HEAD до начала изменений.
2. **Рекомендательная блокировка**: перед любой записью `delegate()` захватить эксклюзивную рекомендательную блокировку (`flock --exclusive`) на файле блокировки уровня операции (`documenter/.delegate.lock`), покрывающем весь набор изменений — целевой документ, `index-RU.md`, changelog, `docs-manifest.yaml`, хранилище хешей — для однохостовых развёртываний. Одна блокировка уровня операции заменяет пофайловые блокировки и по построению свободна от тупиков; поэтому порядок блокировок между файлами не требуется. Если захват блокировки не удался — выдать ошибку с контекстом: «Другой агент удерживает рекомендательную блокировку на [ресурс]. Владелец блокировки: [PID/IP], захвачена в [метка времени]. Ждать? (да/нет) — по умолчанию: нет после 30 с». Распределённая межхостовая блокировка (например, POSIX flock на общем NFS) вне области MVP; отложена на Phase 2+.
3. **Чтение перед записью**: непосредственно перед записью любого файла перечитать его, чтобы обнаружить одновременные изменения в той же области блокировки. Прервать, если файл изменился.
4. **Diff обязателен**: каждая операция записи предваряется машиночитаемым diff, показанным оператору. Никаких незаметных автоизменений.
5. **Атомарность операции**: рассматривать полный цикл выполнения как логическую единицу. При сбое прерывать оставшиеся шаги. Операции записи ДОЛЖНЫ использовать шаблон temp-file + rename (запись во временный путь `.tmp`, затем атомарный `os.rename`), чтобы предотвратить частичные записи. Это гарантирует атомарность только в пределах одного файла; многофайловые наборы изменений ДОЛЖНЫ дополнительно следовать Протоколу многофайловой фиксации (#9).
6. **Без автокоммита**: изменяет файлы, но никогда их не коммитит. Контроль версий ведёт оператор.
7. **Структурированные ошибки**: каждая ошибка delegate() испускает событие по §Event Schema с `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`). Процедуры восстановления ссылаются на категорию в `suggested_action`.
8. **Фиксация постмортема**: при выводах уровня critical, вызванных сбоем delegate(), Документатор фиксирует полный трассировочный след операции (все предпринятые шаги, промежуточные состояния, метки времени) для просмотра оператором.
9. **Протокол многофайловой фиксации**: для наборов изменений, охватывающих несколько файлов (документ, `index-RU.md`, changelog, манифест, хранилище хешей), обеспечивать двухфазную фиксацию только средствами файловых операций — без фоновых процессов и демонов.
  a. **Подготовка**: записать всё новое содержимое во временные пути `.tmp` в их целевых каталогах. Проверить все временные файлы перед переходом к фазе 2.
  b. **Запись намерения**: до первого переименования записать запись намерения в `documenter/intent/<tx_id>.json` (см. §Configuration Guide, Intent Record), идентифицирующую каждый файл набора изменений. Эта запись переживает сбои и позволяет выполнить реконструкцию. Запись ДОЛЖНА использовать шаблон temp-file + rename (тот же, что в §Протокол безопасности #5), чтобы предотвратить частичную запись намерения при сбое посреди записи; холодный старт проверяет целостность намерения перед его использованием. Записи записи намерения ДОЛЖНЫ ссылаться только на пути файлов, отслеживаемых манифестом. Любая попытка подготовить путь вне манифеста в ходе набора изменений приводит к тому, что `delegate()` отклоняет вызов с `error_category: unknown`, и никакие записи не выполняются.
  c. **Упорядоченные переименования**: выполнить переименования в фиксированном порядке — содержимое документа → `index-RU.md` → changelog → `docs-manifest.yaml` → `documenter/hashes.json`. Манифест фиксируется последним среди документов, чтобы сбой до манифеста оставлял осиротевшие, но читаемые файлы (безопасно и аудируемо), а не висячие перекрёстные ссылки (ломающее состояние).
  d. **Очистка**: после всех переименований испустить события аудита в журнал аудита только для добавления, обновить содержимое хранилища хешей (этот файл уже был переименован на шаге 9c), затем удалить запись намерения. Запись намерения ДОЛЖНА удаляться последней — это единственный долговременный резерв для реконструкции событий после сбоя.
  Восстановление: на холодном старте, если остались незакрытые записи намерения, сравнить `before_hash` и `after_hash` каждой записи с фактическим содержимым файла. Три ветви: (1) если файлы совпадают с `after_hash` — уже зафиксировано предыдущим успешным запуском, пропустить; (2) если файлы совпадают с `before_hash` — внешних изменений после сбоя не было, автоматически выполнить прямую докатку из подготовленных файлов `.tmp`; (3) если не совпадает ни то ни другое — обнаружено внешнее изменение, прервать и эскалировать оператору с `error_category: unknown` и постмортем-трассировкой (§8). Запись намерения хранит структурные метаданные (tx_id, target_id, created_at, entries[path, before_hash, after_hash]), достаточные, чтобы реконструировать, какие файлы были изменены, но НЕ содержит решений событий, позиций оператора или полной полезной нагрузки протокольных событий. Утверждение о том, что «утраченные события аудита реконструируются», неверно для MVP — восстановимо лишь происхождение изменений файлов; истинная реконструкция событий требует журнала аудита только для добавления (§Delivery Semantics, configuration-guide).
