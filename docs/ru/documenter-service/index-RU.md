## Назначение

Документатор — это **Вспомогательный сервис**, находящийся за пределами трёхуровневой цепочки, обеспечивающий качество документации в соответствии с правилами `documentation-rules`. Он функционирует как **утилита по запросу** — все функции запускаются только при явном вызове оператором; фоновые процессы или наблюдатели за файлами не работают автономно. Он предоставляет два интерфейса: `audit()` для отчётов только для чтения и `delegate()` для операций записи через навык Работника документации. Четырёхуровневая модель доверия регулирует возможности записи в delegate(). Схемы параметров интерфейсов являются авторитетными в §Interfaces; поля конфигурации определены в Справочнике политик (`documenter-service/policy-reference.md`), а структуры данных времени выполнения — в Руководстве по конфигурации (`documenter-service/configuration-guide.md`).

Граница области видимости: Документатор работает исключительно с артефактами документации, отслеживаемыми в манифесте, и собственным операционным состоянием (каталог `documenter/`). Файлы вне этих пространств имен — файлы рабочей области сессии (`sessions/<id>/`), выходные данные архивов и любые другие артефакты, не отслеживаемые в манифесте, — явно исключены из области видимости Документатора. Интерфейсы `audit()` и `delegate()` принимают только замечания `target_id` из манифеста; любой вызов, ссылающийся на файлы, не указанные в манифесте, отклоняется с `error_category: unknown`. Манифест (`docs-manifest.yaml`) генерируется скриптом `tools/gen_manifest.py` — единственным источником записи (`docs/en/documentation-rules/index.md` §2.2) — и Документатор потребляет его только для чтения через порт `ManifestSource` (`documenter-service/mvp-contract.md` §1). Движок перевода является внешним согласно ADR-014; `create_ru` в границе области видимости обозначает делегированный вызов CLI Проекта перевода через навык Работника документации — RU-записи остаются только в рамках навыка.

## Позиция архитектора

Документатор — это **Вспомогательный сервис**, находящийся вне трёхуровневой цепочки. Он вызывается через поверхность оператора уровня 2 (явный вызов инструмента MCP) и, для записей, основанных на LLM, использует **Порт исполнения уровня 1** для взаимодействия с Работником документации. Он никогда не вызывает напрямую уровень 2 или уровень 0, а уровень 2 никогда не инициирует вызов LLM от имени Документатора. События и вердикты возвращаются синхронно вызывающей поверхности; Документатор не поддерживает цикл обработки событий, подписки и не использует наблюдатель за файловой системой.

Это не входит в путь роли-агента уровня 1: ScenarioLoader и RoleAgentFactory относятся к уровню 1 (`planned-architecture/layer-1.md`), поэтому отсутствует ни равноправные, ни подчинённые отношения с ScenarioLoader. Documenter не осуществляет **Оркестрацию** сессий Совета и не имеет причинно-следственной зависимости от потока **Оркестрации**. Каждое вызов является явным и инициируется оператором. **Исключение:** операции только для чтения (`audit()`) доступны Оператору, Агенту и Сервису в пределах допустимой области согласно матрице авторизации (§Идентификация и авторизация вызывающего субъекта, операторная поверхность); операции записи (`delegate()`) инициируются оператором или делегированным агентом. Намерение записи требует проверки уровня в соответствии с политикой `allowed_operations`; вызовы предварительного просмотра (`preview: true`) полностью обходят проверки уровня (§Освобождение от проверок для предварительного просмотра).

Режим синхронизации (`pre_check`, см. §Interfaces) является контрольной точкой целостности в течение сессии. Запрос на проверку поступает через поверхность оператора уровня 2, вызывает Документатор и возвращает синхронное решение на эту поверхность. Документатор никогда не принимает вызовы от уровня 0 или уровня 1; режим синхронизации сохраняет семантику «ожидание до вызова». Все режимы выполняют независимое полное сканирование целевых документов. Когда Документатор недоступен (сбой сети, тайм-аут, недоступность сервиса), вызов аудита возвращает `unavailable` синхронно; поверхность генерирует событие `precheck.unavailable` и откладывает переход до отмены через `council.override_precheck`.

## Интерфейсы

### audit() — Диагностика только для чтения

Возвращает структурированный отчет, не затрагивая пути записи. Сканирует документы на соответствие правилам комплаенса, используя информацию из манифеста и глоссария. Ниже приведена авторитетная схема параметров для данного интерфейса.

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста или `"*"` для всех |
| severity_min | enum | Минимальный **Уровень серьёзности** для включения: `low`, `medium`, `high`, `critical`. По умолчанию: `low` |
| pre_check | bool | Флаг контроля целостности в середине **Сессии**, устанавливаемый поверхностью оператора уровня 2 на границах **Фаз** (см. `operator-surface/index.md`, §pre_check Gate). Семантика сканирования идентична; отчёт дополнительно возвращается как синхронное решение шлюза вызывающей стороне. Путь записи не задействован. По умолчанию: `false` |
| scan_cursor | string \| null | Токен продолжения от предыдущего частичного сканирования (когда `has_remaining` было `true`). Заставляет `audit()` продолжить сканирование с сохранённой позиции. Отсутствие или `null` означает начало нового полного сканирования. |

| Возвращает | Тип | Описание |
|---------|------|-------------|
| audit_id | string | Уникальный идентификатор данного вызова аудита (UUIDv4). Сохраняется в реестре аудита (`documenter-service/configuration-guide.md`, §Audit Registry) вместе с меткой времени, областью применения, выводами, `scanned_ids`, `has_remaining` и `scan_cursor`. Используется вратарём пред-аудита `delegate()` для проверки свежести, покрытия области применения, отсутствия блокирующих выводов и завершения сканирования. |
| report | dict | Структурированный список выводов с уровнем серьёзности, объектом обсуждения, document_id, описанием, предлагаемым действием |
| has_remaining | boolean | `true`, когда сканирование было приостановлено из-за `rescan_batch_ceiling`; вызывающая сторона должна повторно вызвать `audit(scan_cursor=<value>)` с возвращённым `scan_cursor` для продолжения. |
| scan_cursor | string \| null | Токен продолжения для возобновлённых сканирований. Присутствует только тогда, когда `has_remaining` равно `true`. Непрозрачное значение, кодирующее позицию последнего обработанного документа. |

Уровни серьёзности (единые для всех интерфейсов и схемы событий):

| Уровень | Описание | Эффект оператора |
|-------|-----------|-----------------|
| `low` | Косметическая проблема, нет влияния на данные | Только аудиторский журнал |
| `medium` | Потенциальное несоответствие, низкий риск | Отображается в отчёте; событие сохраняется в журнал только для записи. Запись может быть выполнена только при явном согласии оператора (не автоматически). |
| `high` | Подтверждённая проблема, умеренный риск | По умолчанию блокирует запись; требуется явное согласие оператора перед продолжением. |
| `critical` | Нарушение целостности данных, немедленный риск | Блокирует запись + обязательное фиксирование пост-фактум (§Протокол безопасности #8); путь автоматического применения отсутствует на любом уровне |

### Семантика одобрения

Утверждение — это явное действие оператора посредством вызова инструмента `documenter.approve(approval_id, operator_id)` вне основного канала связи (канонический источник: `documenter-service/mvp-contract.md` §4). Документатор не отслеживает состояние, зависящее от времени, между вызовами и не утверждает результаты автоматически: таймер или фоновый процесс отсутствуют (см. §Purpose, idle-until-invoked). Единственный путь автоматического выполнения — это автоматическое применение на основе шаблонов уровня 3, управляемое предварительным разрешением оператора на использование шаблонов, — а не прошедшим временем.

Поток согласования вне канала: (1) на уровне Tier 2 и выше `delegate()` возвращает `approval_required` с `approval_id` и хэшем разницы, но не выполняет запись; (2) оператор независимо вызывает `documenter.approve(approval_id, operator_id)` (ДОЛЖНО быть отдельным вызовом от вызова предложения); (3) `operator_id`, осуществляющий согласование, ДОЛЖЕН отличаться от идентификатора актора вызова предложения, чтобы предотвратить само-согласование; (4) после успешного согласования система продолжает выполнение записи, используя тот же хэш разницы для привязки; (5) изменённые разницы аннулируют ожидающие согласования.

Срок действия подтверждения истекает по истечении настроенного временного окна (`approval_expiry_window`, по умолчанию 30 минут согласно разделу «Справочник по полям» документа policy-reference.md §). Истекшее подтверждение необходимо получить заново, прежде чем можно будет применить изменения (diff). Новый хеш изменений аннулирует любые ещё действительные подтверждения.

Устаревшие сопоставления из предыдущих версий: `info` → `low`, `warning` → `medium`, `error` → `high`. Все инструменты рендеринга ДОЛЖНЫ выполнять сопоставление: `critical` → красный, `high` → оранжевый, `medium` → жёлтый, `low` → серый.

### delegate() — Написать через Документацию Рабочий навык

Выполняет конкретную операцию над документом с контролем уровня доверия. Вызов возможен только после прохождения проверки операторской политики. Приведённая ниже таблица является авторитетной схемой параметров для данного интерфейса; поля политики, которые она использует, определены в Справочнике по политикам (§Перекрёстные ссылки).

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста |
| change_type | enum | Один из: `update`, `split`, `create_ru`, `custom` |
| trust_level | enum | *Запрос* вызывающей стороны, а не эффективное значение: `safe` или `review`. Документатор выводит требуемый уровень согласно §Trust Classification и принимает запрос только если он равен или строже этого уровня (`requested >= derived`); запрос ниже уровня отклоняется с `error_category: trust_mismatch`. Эффективный уровень — это запрошенный уровень. |
| diff | string (base64-encoded) | Машинно-читаемая разница для предварительного просмотра оператором, закодированная как base64 для обеспечения безопасной передачи JSON согласно ограничениям UTF-8 JSON (§Common Conventions, service-contract). Обязательно для всех уровней. |
| audit_id | string | Идентификатор из предыдущего возврата `audit()`. Проверяется на соответствие политике `audit_freshness`. Пропускается только тогда, когда шлюз явно отключен в файле политики. |
| preview | boolean | Когда `true`, вызов возвращает только разницу без намерения записи и освобождается от проверок `allowed_operations` на всех уровнях (§Preview Exemption). Когда опущено или `false`, вызов несет намерение записи и подчиняется обычным ограничениям уровней (Уровень 0–1 всегда отказывает в записи независимо; Уровень 2+ требует явного одобрения; Уровень 3 может автоматически применять на основе шаблонов). |

Поток выполнения: `audit → compute diff → present to operator → wait for approve/reject → apply if approved → commit per Multi-file Commit Protocol (§Safety Protocol #9) → log to audit trail`. Запись файлов использует временный файл и системный вызов rename (см. §Safety Protocol #5), что гарантирует атомарный переход от подготовленного состояния к зафиксированному содержимому для одного файла. Атомарность в пределах нескольких файлов НЕ обеспечивается только rename — см. §Failure semantics.

**Ворота предаудита:** По умолчанию `delegate()` требует действительный `audit_id` от предыдущего вызова `audit()`. Проверка осуществляется по реестру аудитов (`documenter-service/configuration-guide.md`, §Реестр аудитов): (1) `audit_id` должен существовать; (2) его `issued_at` должен попадать в окно `audit_freshness` (поле политики, по умолчанию 30 минут; схема: `documenter-service/policy-reference.md`, §Справочник по полям); (3) его `scope` должен полностью покрывать `target_id` (`*` совпадает с любым, в противном случае требуется точное совпадение); (4) в реестре не должно существовать `high` или `critical` **Вывод** для `target_id`; (5) если для зарегистрированного сканирования `has_remaining` было `true`, делегирование отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение по правилам (1–3) использует `error_category: audit_mismatch`; по (4) или (5) — `error_category: blocking_finding`. Рекомендуемое действие в обоих случаях: повторно запустить `audit()` для цели и повторить попытку. Когда реестр аудитов отсутствует, повреждён или недоступен для чтения, ворота FAIL CLOSED — все операции записи запрещены до явного переопределения оператором. Переопределение требует аутентифицированного действия через `documenter.override_gate(reason, operator_id)`, которое фиксирует инцидент и разрешает ровно один последующий вызов `delegate()` без свежего аудита. Повторные переопределения требуют одобрения уровня Tier 2+. Ворота настраиваются через поле политики `audit_freshness`, но по умолчанию enforced.

**Классификация доверия:** Фактический уровень доверия устанавливается Документатором, а не вызывающей стороной. Параметр `trust_level` вызывающей стороны может быть равен или ужесточать вычисленный нижний предел, но никогда не ослаблять его: на шкале `safe < review` инвариант имеет вид `requested >= derived`, а фактический уровень равен `requested`. Если `requested < derived`, функция `delegate()` отклоняет вызов с кодом `error_category: trust_mismatch` до этапа одобрения оператором. Тихого повышения уровня не происходит. В случае неопределённости классификации применяется уровень `review`. Справочник политики (`documenter-service/policy-reference.md`) может повысить нижний предел выше указанного в таблице, но НЕ ДОЛЖЕН понижать его (§Файл политики, §Правило авторитета). Значение `suggested_trust_level` в §Схема событий является результатом работы того же классификатора.

| change_type | Статический пол (загрузка политики) | Динамический вывод (вызов) | `safe` разрешён |
|-------------|---------------------------|--------------------------------|------------------|
| `update` | `safe` | `safe`, если каждый ханк механический; в противном случае `review` | Да, только для полностью механических диффов |
| `split` | `review` | `review` | Никогда |
| `create_ru` | `review` | `review` | Никогда (автофикс RU запрещён в MVP) |
| `custom` | `review` | `review` | Никогда (по умолчанию при неопределённости) |

Статический пол «`update`» является `safe` для проверки политики на этапе загрузки (валидатор видит только `change_type`). Динамический вывод происходит на этапе вызова: полностью механическая разница (diff) выводит `safe`, любая семантическая часть (hunk) выводит `review`. Запись политики, указывающая `update` + `safe`, проходит проверку на этапе загрузки; не-механическая разница всё равно выводит `review` и отклоняет запрос `safe` с ошибкой `trust_mismatch`.

**Семантика сбоев:** При прерывании или возникновении ошибки во время выполнения `delegate()` оркестрация должна следовать модели «всё или ничего» — частичные записи для одного файла не сохраняются (гарантируется использованием временного файла и системным вызовом rename). Частичные фиксации между файлами возможны только между операциями rename разных файлов; это не предотвращается атомарностью rename или журналируемыми файловыми системами (журналирование гарантирует внутреннюю согласованность файловой системы, но не атомарность между файлами или доставку журнала аудита). Протокол многофайловой фиксации (§Протокол безопасности #9) обеспечивает восстанавливаемую после сбоев конечную согласованность: сбой в середине последовательности оставляет обнаруживаемое частичное состояние с оставшимися подготовленными файлами и записью намерения, которая согласовывается при следующей проверке при холодном запуске (§Руководство по конфигурации, Журнал намерения). Восстановление без вмешательства оператора происходит автоматически, если не было внешних изменений; в противном случае генерируется структурированное событие ошибки, и восстановление требует явного повторного вызова. Это превращает скрытую порчу данных в задокументированное ограничение с явным путем смягчения. В будущих версиях (Фаза 2+) будут введены контрольные точки и возобновление работы через атомарные снимки состояния, основанные на WAL; до тех пор операторы ДОЛЖНЫ рассматривать каждую границу фазы как точку фиксации.

События, генерируемые в процессе выполнения метода delegate(), используют схему событий, определённую в разделе «Руководство по конфигурации». Каждая ошибка метода delegate() приводит к генерации события согласно схеме событий с указанием `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`).

## Уровни доверия

Четыре уровня развертывания, обеспечивающие постепенно возрастающие возможности записи. Для перехода на каждый следующий уровень требуется явная команда оператора.

| Уровень | Возможность | Авто-выполнение | Требуется разница | Область |
|------|-----------|----------------|---------------|-------|
| 0 | Только аудит (MVP) | Нет | Н/Д (нет записей) | Чтение манифеста и документации, формирование отчёта |
| 1 | Предпросмотр различий | Нет | Да | Генерация различий, без записи в файловую систему |
| 2 | Подтверждение по изменению | Нет | Да, по каждому элементу | Применение изменений только после индивидуального одобрения |
| 3 | Пакетное одобрение | На основе шаблонов | Да, по пакетам с групповыми сводками | Шаблоны, получившие одобрение, применяются автоматически; критические элементы требуют детального рассмотрения по каждому элементу |

Уровень 0–1 поставляется вместе с MVP. Уровень 2+ поступает в эксплуатацию только после того, как появится документированный файл политики, авторизующий конкретные комбинации `change_type` + `trust_level`. Уровень 2+ дополнительно связан на архитектурном уровне: вызовы уровня 2+ не принимаются, пока не существует Operator Surface в виде кода, обеспечивающего аутентифицированный канал одобрения вне сессии — спецификация `operator-surface/index.md` является необходимым, но недостаточным условием (ADR-013). Одного файла политики недостаточно. Переход на уровень 2+ требует: (a) авторизованного файла политики согласно `documenter-service/policy-reference.md`, И (b) архивированного брифинга оператора, на который ссылается файл политики (поле `briefing_ref`), И (c) реализованного Operator Surface, обеспечивающего аутентифицированный вход оператора (ADR-013). Все условия ДОЛЖНЫ быть выполнены перед первым вызовом уровня 2+. См. §Authorization Workflow для пошаговой процедуры. Редактирование файла политики (`active_tier`, `allowed_operations`, `briefing_ref`) является актом активации, зарезервированным за оператором вне сессии; агенты НЕ ДОЛЖНЫ его изменять (ADR-013). Автоматическое применение на основе шаблонов на уровне 3 — единственный путь авто-выполнения в системе; оно вытекает из предварительной авторизации шаблонов оператором, а не из прошедшего времени (см. §Approval semantics).

### Рекомендации по выбору уровня

| Уровень | Рекомендуемый сценарий использования | Предварительное требование |
|------|---------------------|---------------|
| 0 | Первоначальное развертывание, изучение поведения системы | Нет |
| 1 | Проверка точности без риска внесения изменений | Нет |
| 2 | Активное обслуживание, выборочные исправления | Файл политики (`documenter-service/policy-reference.md`), авторизующий операции уровня 2 |
| 3 | Масштабная очистка, сезонная реструктуризация | Операционная история, демонстрирующая уровень одобрения ≥90% на уровне 2 в течение 2 недель |

### Процесс авторизации

Процедура, посредством которой оператор предоставляет права на запись. Документатор не выполняет ни одного из этих шагов от своего имени; каждый из них является явным действием оператора, а подробный контрольный список с описанием сценариев отказа проверки находится в файле `documenter-service/policy-reference.md`, §Authorization Workflow.

1. **Аудит** — устранить проблемы с уровнем `high` и `critical` на текущем уровне. Переход на более высокий уровень при несоответствии корпуса автоматически запускает дрейф, а не очистку.
2. **Автор** — написать файл политики: записи `allowed_operations` для предполагаемых комбинаций `change_type` + `trust_level` + `targets`, а также поля операционный настройки.
3. **Проверка** — загрузить кандидатский файл в режиме только проверки. Загрузка завершается ошибкой при наличии непустого `allowed_operations` ниже уровня 2, `trust_level` ниже выведенного минимума §Trust Classification или при наличии неизвестного замечания политики.
4. **Краткое описание** — архивировать краткое описание оператора (делегированная область, максимальное количество документов, к которым может обратиться один вызов, процедура отмены) и указать `briefing_ref` на него. Установите `active_tier` и `briefing_ref` в одном редактировании, чтобы частичное редактирование не оставляло уровень 2+ без краткого описания.
5. **Продвижение** — следующий вызов выполняется на новом уровне. Первый `delegate()` на новом уровне нацелен на один документ с низким риском; разница просматривается поэлементно независимо от уровня.
6. **Оценка** — уровень 3 требует документально подтвержденных доказательств (одобрение ≥90% на уровне 2 за предыдущие две недели журнала событий) и явного перечисления одобренных шаблонов; ни один шаблон не выводится.

Откат симметричен: понижение `active_tier` вступает в силу при следующем вызове; выполняющийся в данный момент `delegate()` завершается в рамках того уровня, на котором он был принят.

## Протокол безопасности

1. **Снимок до изменений**: зафиксировать статус git и коммит HEAD перед началом модификаций.
2. **Предварительная блокировка**: перед любой записью `delegate()` получить эксклюзивную предварительную блокировку (`flock --exclusive`) на файл блокировки уровня операции (`documenter/.delegate.lock`), охватывающий весь набор изменений — целевой документ, `index-RU.md`, журнал изменений, `docs-manifest.yaml`, хранилище хэшей — для развертываний на одном узле. Одна блокировка уровня операции заменяет блокировки на уровне файлов и не приводит к взаимным блокировкам по конструкции; поэтому порядок блокировок между файлами не требуется. Если получение блокировки не удалось — вывести ошибку с контекстом: "Другой агент удерживает предварительную блокировку на [ресурс]. Владелец блокировки: [PID/IP], получена в [время]. Ждать? (да/нет) — По умолчанию: нет через 30с." Распределенная блокировка между узлами (например, POSIX flock на общем NFS) выходит за рамки MVP; отложено до Фазы 2+.
3. **Чтение перед записью**: непосредственно перед записью любого файла перечитать его, чтобы обнаружить одновременные модификации в той же области блокировки. Прервать, если файл изменен.
4. **Обязательная разница**: каждая оркестрация записи предваряется машиночитаемой разницей, показываемой оператору. Никаких скрытых автоматических изменений.
5. **Атомарная оркестрация**: рассматривать полный цикл выполнения как логическую единицу. При сбое прервать оставшиеся шаги. Операции записи ДОЛЖНЫ использовать шаблон временного файла + вызов rename (запись в путь `.tmp`, затем атомарный `os.rename`) для предотвращения частичных записей. Это гарантирует атомарность на уровне файла; наборы изменений из нескольких файлов ДОЛЖНЫ дополнительно следовать Протоколу коммита из нескольких файлов (#9).
6. **Без авто-коммита**: модифицирует файлы, но никогда не коммитит их. Оператор управляет системой контроля версий.
7. **Структурированные ошибки**: каждый сбой delegate() генерирует событие с использованием §Схема событий с `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`). Процедуры восстановления ссылаются на категорию в `suggested_action`.
8. **Запись после инцидента**: при критических находках, вызванных сбоем delegate(), Документатор фиксирует полный трассировку операции (все предпринятые шаги, промежуточные состояния, метки времени) для проверки оператором.
9. **Протокол коммита из нескольких файлов**: для наборов изменений, охватывающих несколько файлов (документ, `index-RU.md`, журнал изменений, манифест, хранилище хэшей), обеспечить двухфазный коммит, используя только операции с файлами — никаких фоновых процессов или демонов.
 a. **Этап**: записать все новое содержимое в пути `.tmp` в их целевых каталогах. Проверить все временные файлы перед переходом к фазе 2.
 b. **Журнал намерения**: перед первым переименованием записать журнал намерения в `documenter/intent/<tx_id>.json` (см. §Руководство по конфигурации, Журнал намерения), идентифицирующий каждый файл в наборе изменений. Этот журнал переживает сбои и позволяет восстановить состояние. Запись ДОЛЖНА использовать шаблон временного файла + rename (как в §5) для предотвращения частичного журнала намерения при сбое во время записи; холодный запуск проверяет целостность журнала намерения перед его использованием. Записи в журнале намерения ДОЛЖНЫ ссылаться только на пути файлов, отслеживаемых манифестом. Любая попытка подготовить путь, не входящий в манифест, во время набора изменений вызывает отклонение `delegate()` с `error_category: unknown`, и никакие записи не выполняются.
 c. **Упорядоченные переименования**: выполнить переименования в фиксированном порядке — содержимое документа → `index-RU.md` → журнал изменений → `docs-manifest.yaml` → `documenter/hashes.json`. Манифест коммитится последним среди документов, так что сбой до коммита манифеста оставляет осиротевшие, но читаемые файлы (безопасно, проверяемо), а не висячие перекрестные ссылки (сломано).
 d. **Очистка**: после всех переименований отправить события аудита в только для записи журнал аудита, обновить содержимое хранилища хэшей (файл уже был переименован в 9c), затем удалить журнал намерения. Журнал намерения ДОЛЖЕН быть последним удаленным элементом — он является единственным надежным резервным вариантом для восстановления событий после сбоя.
 Восстановление: при холодном запуске, если остались журналы намерения, сравнить `before_hash` и `after_hash` каждой записи с фактическим содержимым файла. Три варианта: (1) если файлы совпадают с `after_hash` — уже закоммичены предыдущим успешным запуском, пропустить; (2) если файлы совпадают с `before_hash` — внешних изменений с момента сбоя не было, автоматически продолжить от подготовленных файлов `.tmp`; (3) если ни один не совпадает — обнаружено внешнее изменение, прервать и передать оператору с `error_category: unknown` и трассировкой после инцидента (§8). Журнал намерения хранит структурные метаданные (tx_id, target_id, created_at, entries[path, before_hash, after_hash]), достаточные для восстановления того, какие файлы были изменены, но НЕ содержит решений событий, позиций оператора или полного полезного载荷 протокольных событий. Утверждение, что "потерянные события аудита восстанавливаются", неверно для MVP — восстанавливаемо только происхождение изменений файлов; истинное восстановление событий требует только для записи журнала аудита (§Семантика доставки, configuration-guide).
