## Purpose

Документатор — это **Вспомогательный сервис** (Supporting service), находящийся вне трёхуровневой цепи и обеспечивающий качество документации в соответствии с правилами `AGENTS.md`. Он работает как **утилита по требованию** — все функции начинаются только по явному вызову оператора; фоновые процессы и мониторы файлов не работают автономно. Он предоставляет два интерфейса: `audit()` для отчётов только на чтение и `delegate()` для операций записи через навык Documentation Worker. Модель доверия из четырёх тиров управляет возможностями записи `delegate()`. Схемы параметров интерфейсов являются авторитетными в §Interfaces; поля конфигурации определены в Справочнике политик (`documenter-service/policy-reference.md`), а структуры данных рантайма — в Руководстве по конфигурации (`documenter-service/configuration-guide.md`).

Граница области: Документатор работает исключительно с артефактами документации, отслеживаемыми в манифесте, и с собственным операционным состоянием (каталог `documenter/`). Файлы за пределами этих пространств — рабочие файлы сессий (`sessions/<id>/`), результаты архивирования и любые другие артефакты вне манифеста — явно исключены из области Документатора. Интерфейсы `audit()` и `delegate()` принимают только значения `target_id` из манифеста; любой вызов, ссылающийся на файлы вне манифеста, отклоняется с `error_category: unknown`.

## Architecture Position

Документатор — это **Вспомогательный сервис** (Supporting service) вне трёхуровневой цепи. Он вызывается поверхностью оператора Layer 2 (явный вызов MCP-инструмента) и для записей с участием LLM использует **порт исполнения Layer 1** (Layer 1 execution port), чтобы обратиться к Documentation Worker. Он никогда не обращается к Layer 2 или Layer 0 напрямую, и Layer 2 никогда не вызывает LLM от имени Документатора. События и вердикты возвращаются вызывающей поверхности синхронно; Документатор не держит цикла событий, не имеет подписок и не имеет монитора файловой системы.

Он не является частью пути role-agent Layer 1: ScenarioLoader и RoleAgentFactory принадлежат Layer 1 (`planned-architecture/layer-1.md`), поэтому отношений «равный» или «подчинённый» с ScenarioLoader не существует. Документатор не оркеструет сессии Консилиума и не имеет причинной зависимости от потока оркестровки. Каждый вызов явный и инициирован оператором. **Исключение:** операции только на чтение (`audit()`) доступны Оператору, Агенту и Сервису в пределах разрешённой области согласно матрице authZ (§Caller Identity and Authorization, operator-surface); операции записи (`delegate()`) исходят от оператора или от делегированного агента. Намерение записи требует проверки тира согласно политике `allowed_operations`; вызовы предварительного просмотра (`preview: true`) полностью обходят проверки тира (§Preview Exemption).

Режим синхронизации (`pre_check`, см. §Interfaces) — это вентиль целостности в середине сессии. Запрос на вентиль поступает через поверхность оператора Layer 2, вызывает Документатора и возвращает синхронный вердикт этой поверхности. Документатор никогда не принимает вызовы от Layer 0 или Layer 1; режим синхронизации сохраняет семантику «простаивает до вызова» (idle-until-invoked). Все режимы выполняют независимое полное сканирование целевых документов. Когда Документатор недоступен (сетевой сбой, таймаут, сервис остановлен), вызов аудита возвращает `unavailable` синхронно; поверхность излучает событие `precheck.unavailable` и откладывает переход до переопределения через `council.override_precheck`.

## Interfaces

### audit() — Диагностика только на чтение

Возвращает структурированный отчёт, не затрагивая путь записи. Сканирует документы на соответствие правилам, используя информацию из манифеста и глоссария. Таблица ниже — авторитетная схема параметров для этого интерфейса.

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста, либо `"*"` для всех |
| severity_min | enum | Минимальная серьёзность для включения: `low`, `medium`, `high`, `critical`. По умолчанию: `low` |
| pre_check | bool | Флаг вентиля целостности в середине сессии, устанавливаемый поверхностью Layer 2 на границах фаз (см. `operator-surface/index.md`, §pre_check Gate). Семантика сканирования идентична; отчёт дополнительно возвращается вызывающей стороне как синхронный вердикт вентиля. Путь записи не задействован. По умолчанию: `false` |
| scan_cursor | string \| null | Токен продолжения от предыдущего частичного сканирования (когда `has_remaining` был `true`). Заставляет `audit()` продолжить сканирование с сохранённой позиции. Отсутствие или `null` означает начало нового полного сканирования. |

| Возвращает | Тип | Описание |
|---------|------|-------------|
| audit_id | string | Уникальный идентификатор этого вызова аудита (UUIDv4). Сохраняется в реестре аудита (`documenter-service/configuration-guide.md`, §Audit Registry) вместе с временной меткой, областью, выводами, `scanned_ids`, `has_remaining` и `scan_cursor`. Используется вентилем предварительного аудита `delegate()` для проверки свежести, покрытия области, отсутствия блокирующих выводов и завершения сканирования. |
| report | dict | Структурированный список выводов с серьёзностью, темой, идентификатором документа, описанием, рекомендуемым действием |
| has_remaining | boolean | `true`, когда сканирование было приостановлено из-за `rescan_batch_ceiling`; вызывающий должен повторно вызвать `audit(scan_cursor=<value>)` с возвращённым `scan_cursor`, чтобы продолжить. |
| scan_cursor | string \| null | Токен продолжения для возобновлённых сканирований. Присутствует только когда `has_remaining` равно `true`. Непрозрачное значение, кодирующее последнюю обработанную позицию документа. |

Уровни серьёзности (единые для всех интерфейсов и схемы событий):

| Уровень | Описатель | Влияние на оператора |
|-------|-----------|-----------------|
| `low` | Косметическая проблема, нет влияния на данные | Только журнал аудита |
| `medium` | Потенциальное несоответствие, низкий риск | Отображается в отчёте; событие сохраняется в журнал только для добавления (append-only). Запись может быть выполнена только при явном одобрении оператора (не автоматически). |
| `high` | Подтверждённая проблема, умеренный риск | Блокирует запись по умолчанию; требует явного одобрения оператора перед продолжением. |
| `critical` | Нарушение целостности данных, немедленный риск | Блокирует запись + обязательный сбор постмортем-трассировки (§Safety Protocol #8); пути автоприменения нет ни на одном тире |

### Approval semantics

Одобрение — это явное действие оператора посредством внеполосного вызова инструмента `documenter.approve(approval_id, operator_id)` (§Documenter Integration, operator-surface). Документатор не отслеживает состояния, зависящие от времени, между вызовами и не одобряет выводы автоматически: таймера или фонового процесса не существует (см. §Purpose, idle-until-invoked). Единственный путь автовыполнения — автоприменение по паттерну на Tier 3, обусловленное предварительной авторизацией паттернов оператором, — но никогда прошествием времени.

Внеполосный поток одобрения: (1) на Tier 2+ `delegate()` возвращает `approval_required` с `approval_id` и хешем diff, но не выполняет записи; (2) оператор независимо вызывает `documenter.approve(approval_id, operator_id)` (это ДОЛЖЕН быть отдельный вызов, отличный от предлагающего); (3) одобряющий `operator_id` ДОЛЖЕН отличаться от идентификатора актора предлагающего вызова, чтобы предотвратить самоодобрение; (4) после успешного одобрения система выполняет запись с использованием того же хеша diff для привязки; (5) изменившийся diff аннулирует ожидающие одобрения.

Одобрение истекает по прошествии настроенного окна (`approval_expiry_window`, по умолчанию 30 минут согласно policy-reference.md §Field Reference). Истёкшее одобрение необходимо получить заново, прежде чем diff сможет быть применён. Новый diff-хеш аннулирует любое ещё действующее одобрение.

Устаревшие сопоставления из предыдущих версий: `info` → `low`, `warning` → `medium`, `error` → `high`. Все инструменты рендеринга ДОЛЖНЫ сопоставлять: `critical`→красный, `high`→оранжевый, `medium`→жёлтый, `low`→серый.

### delegate() — Запись через навык Documentation Worker

Вызывает определённую операцию над документом с контролем уровня доверия. Может вызываться только после проверки порога политики оператора. Таблица ниже — авторитетная схема параметров для этого интерфейса; потребляемые им поля политики определены в Справочнике политик (§Cross-References).

| Параметр | Тип | Описание |
|-----------|------|-------------|
| target_id | string | Идентификатор документа из манифеста |
| change_type | enum | Одно из: `update`, `split`, `create_ru`, `custom` |
| trust_level | enum | *Запрос* вызывающего, а не фактическое значение: `safe` или `review`. Документатор выводит требуемый базовый уровень (trust floor) по §Trust Classification и принимает запрос, только если он равен этому базовому уровню или строже его (`requested >= derived`); запрос ниже базового уровня отклоняется с `error_category: trust_mismatch`. Фактический уровень — запрошенный. |
| diff | string (base64-encoded) | Машиночитаемый diff для предварительного просмотра оператором, закодированный в base64 для обеспечения JSON-безопасной передачи согласно ограничениям UTF-8 JSON (§Common Conventions, service-contract). Обязателен для всех тиров. |
| audit_id | string | Идентификатор из предыдущего возврата `audit()`. Проходит валидацию согласно политике `audit_freshness`. Опускается только когда вентиль явно отключён в файле политики. |
| preview | boolean | Когда `true`, вызов возвращает только diff без намерения записи и не подлежит проверкам `allowed_operations` ни на одном тире (§Preview Exemption). Когда опущено или `false`, вызов несёт намерение записи и подчиняется обычным ограничениям тира (Tier 0–1 всегда отклоняют записи независимо от остального; Tier 2+ требует явного одобрения; Tier 3 может автоприменять на основе паттернов). |

Поток выполнения: `audit → compute diff → present to operator → wait for approve/reject → apply if approved → commit per Multi-file Commit Protocol (§Safety Protocol #9) → log to audit trail`. Записи в файлы используют системный вызов переименования поверх записи во временный файл (temp-file + rename, см. §Safety Protocol #5), что гарантирует атомарный переход от staged-состояния к зафиксированному содержимому для одного файла. Атомарность между файлами одним лишь переименованием НЕ обеспечивается — см. §Failure semantics.

**Вентиль предварительного аудита:** По умолчанию `delegate()` требует действительный `audit_id` из предыдущего вызова `audit()`. Валидация выполняется по реестру аудита (`documenter-service/configuration-guide.md`, §Audit Registry): (1) `audit_id` должен существовать; (2) его `issued_at` должен попадать в окно `audit_freshness` (поле политики, по умолчанию 30 минут; схема: `documenter-service/policy-reference.md`, §Field Reference); (3) его `scope` должен полностью покрывать `target_id` (`*` совпадает с любым, иначе точное совпадение); (4) для `target_id` в реестре не должно существовать вывода уровня `high` или `critical`; (5) если `has_remaining` было `true` для зарегистрированного сканирования, делегат отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение по правилам (1–3) использует `error_category: audit_mismatch`; по правилу (4) или (5) — `error_category: blocking_finding`. Предлагаемое действие в обоих случаях: заново запустите `audit()` для цели и повторите попытку. Когда реестр аудита отсутствует, повреждён или нечитаем, вентиль ЗАКРЫВАЕТСЯ ОТКАЗОМ (fails closed) — все операции записи запрещены до явного переопределения оператором. Переопределение требует аутентифицированного действия через `documenter.override_gate(reason, operator_id)`, которое протоколирует инцидент и разрешает ровно один последующий вызов `delegate()` без нового аудита. Повторные переопределения требуют одобрения Tier 2+. Вентиль настраивается полем политики `audit_freshness`, но по умолчанию действует обязательно.

**Классификация доверия:** Фактический уровень доверия назначается Документатором, а не вызывающим. Параметр `trust_level` вызывающего может совпадать с выводимым базовым уровнем или ужесточать его, но никогда не ослабляет: на шкале `safe < review` инвариант — `requested >= derived`, а фактический уровень — `requested`. Если `requested < derived`, `delegate()` отклоняет вызов с `error_category: trust_mismatch` ещё до стадии одобрения оператором. Тихого повышения не происходит. Когда классификация неоднозначна, применяется `review`. Справочник политик (`documenter-service/policy-reference.md`) может поднять базовый уровень выше табличного, но НЕ ДОЛЖЕН понижать его (§Policy File, §Authority rule). `suggested_trust_level` в §Event Schema — это выход того же классификатора.

| change_type | Статический базовый уровень (загрузка политики) | Динамический вывод (вызов) | `safe` разрешён |
|-------------|---------------------------|--------------------------------|------------------|
| `update`      | `safe`                    | `safe`, если каждый фрагмент (hunk) механический; иначе `review` | Да, только для полностью механического diff |
| `split`       | `review`                  | `review`                         | Никогда |
| `create_ru`   | `review`                  | `review`                         | Никогда (авто-исправление RU запрещено в MVP) |
| `custom`      | `review`                  | `review`                         | Никогда (значение по умолчанию при неопределённости) |

Статический базовый уровень для `update` равен `safe` ради валидации политики при загрузке (валидатор видит только `change_type`). Динамический вывод выполняется во время вызова: полностью механический diff выводит `safe`, любой смысловой фрагмент выводит `review`. Запись политики, называющая `update` + `safe`, проходит валидацию при загрузке; немеханический diff по-прежнему выводит `review` и отклоняет запрос `safe` с `trust_mismatch`.

**Семантика отказа:** При прерывании или сбое во время выполнения `delegate()` операция должна следовать модели «всё или ничего» — частичные записи не сохраняются для одного файла (гарантируется системным вызовом temp-file + rename). Частичные коммиты между файлами возможны только в промежутках между переименованиями разных файлов; это не предотвращается ни атомарностью переименования, ни журналируемыми файловыми системами (журналирование гарантирует внутреннюю согласованность файловой системы, а не межфайловую атомарность или доставку журнала аудита). Протокол многофайлового коммита (§Safety Protocol #9) обеспечивает восстанавливаемую согласованность в конечный момент времени (eventual consistency): сбой в середине последовательности оставляет обнаруживаемое частичное состояние с оставшимися staged-файлами и журналом намерения (intent record), которое сверяется следующей проверкой на холодном старте (§Configuration Guide, Intent Record). Восстановление без вмешательства оператора происходит автоматически, если внешних изменений не было; в противном случае излучается структурированное событие об ошибке, и восстановление требует явного повторного вызова. Это превращает тихую порчу данных в задокументированное ограничение с явным путём смягчения. Будущие версии (Phase 2+) введут checkpoint/resume на основе атомарных снимков состояния с журналированием (WAL); до тех пор операторы ДОЛЖНЫ рассматривать каждую границу фазы как точку фиксации.

События, излучаемые во время `delegate()`, используют схему событий (Event Schema), определённую в §Configuration Guide. Каждая ошибка `delegate()` излучает событие по §Event Schema с полем `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`).

## Trust Tiers

Четыре тира развёртывания, управляющие прогрессивно большими возможностями записи. Каждый тир требует явной команды оператора для продвижения.

| Тир | Возможность | Автовыполнение | Diff обязателен | Область |
|------|-----------|----------------|---------------|-------|
| 0 | Только аудит (MVP) | Нет | Н/Д (записей нет) | Чтение манифеста + docs, формирование отчёта |
| 1 | Предварительный просмотр diff | Нет | Да | Формирование diff, запись в файловую систему отсутствует |
| 2 | Подтверждение на каждое изменение | Нет | Да, поэлементно | Применяет изменения только после поштучного approve |
| 3 | Пакетное approve | На основе паттернов | Да, на пакет с групповыми сводками | Авторизованные паттерны применяются автоматически; критичные элементы требуют поэлементного расширенного просмотра |

Tier 0–1 поставляются в MVP. Tier 2+ попадает в эксплуатацию только после того, как существует задокументированный файл политики, авторизующий конкретные сочетания `change_type` + `trust_level`. Tier 2+ дополнительно взаимно заблокирован на уровне архитектуры: ни один вызов Tier 2+ не принимается, пока спецификация Operator Surface & Escalation не определит аутентифицированный внеполосный канал одобрения. Самого по себе файла политики недостаточно. Продвижение на Tier 2+ требует: (a) составленного файла политики согласно `documenter-service/policy-reference.md` И (b) заархивированного брифинга оператора, на который ссылается файл политики (поле `briefing_ref`). Оба условия ДОЛЖНЫ быть выполнены до первого вызова Tier 2+. Пошаговая процедура см. в §Authorization Workflow. Автоприменение по паттернам на Tier 3 — единственный путь автовыполнения в системе; оно проистекает из предварительной авторизации паттернов оператором, а не из прошествия времени (см. §Approval semantics).

### Tier Selection Guidance

| Тир | Рекомендуемый случай использования | Предпосылка |
|------|---------------------|---------------|
| 0 | Начальное развёртывание, изучение поведения системы | Нет |
| 1 | Проверка точности без риска изменений | Нет |
| 2 | Активное сопровождение, выборочные исправления | Файл политики (`documenter-service/policy-reference.md`), авторизующий операции Tier 2 |
| 3 | Крупномасштабная уборка, сезонная реструктуризация | История эксплуатации, демонстрирующая долю одобрения ≥90% на Tier 2 в течение 2 недель |

### Authorization Workflow

Процедура, посредством которой оператор предоставляет возможность записи. Документатор не выполняет ни один из этих шагов самостоятельно; каждый — дискретное действие оператора, а детальный контрольный список с режимами отказа валидации находится в `documenter-service/policy-reference.md`, §Authorization Workflow.

1. **Аудит** — устраните выводы `high` и `critical` на текущем тире. Продвижение тира над некомплаентным корпусом автоматизирует дрейф, а не уборку.
2. **Составление** — напишите файл политики: записи `allowed_operations` для предполагаемых сочетаний `change_type` + `trust_level` + `targets` плюс поля операционной настройки.
3. **Валидация** — загрузите файл-кандидат в режиме только проверки. Загрузка падает на непустом `allowed_operations` ниже Tier 2, на `trust_level` ниже выводимого базового уровня из §Trust Classification либо на нераспознанном значении политики.
4. **Брифинг** — заархивируйте брифинг оператора (делегированная область, максимальное число документов, которые может затронуть один вызов, процедура отката) и укажите `briefing_ref` на него. Устанавливайте `active_tier` и `briefing_ref` одной и той же правкой, чтобы частичная правка не оставила Tier 2+ без брифинга.
5. **Продвижение** — следующий вызов выполняется на новом тире. Первый `delegate()` на новом тире нацелен на один документ с низким риском; diff просматривается поэлементно независимо от тира.
6. **Оценка** — Tier 3 требует задокументированных свидетельств (доля одобрения ≥90% на Tier 2 за предшествующие две недели журнала событий) и явного перечисления авторизованных паттернов; ни один паттерн не выводится автоматически.

Откат симметричен: понижение `active_tier` вступает в силу при следующем вызове; выполняющийся `delegate()` завершается под тем тиром, на котором был принят.

## Safety Protocol

1. **Снимок перед изменением**: зафиксировать `git status` и коммит HEAD до начала изменений.
2. **Рекомендательная блокировка (advisory lock)**: перед любой записью `delegate()` захватить эксклюзивную рекомендательную блокировку (`flock --exclusive`) на файле блокировки уровня операции (`documenter/.delegate.lock`), покрывающем весь набор изменений — целевой документ, `index-RU.md`, changelog, `docs-manifest.yaml`, хранилище хешей — для однохостовых развёртываний. Одна блокировка уровня операции заменяет пофайловые блокировки и по построению свободна от взаимных блокировок; потому порядок захвата блокировок между файлами не требуется. Если захват блокировки не удался — излучить ошибку с контекстом: «Другой агент удерживает рекомендательную блокировку на [ресурс]. Владелец блокировки: [PID/IP], захвачена в [метка времени]. Ждать? (да/нет) — по умолчанию: нет после 30 с». Распределённая межхостовая блокировка (например, POSIX flock по общему NFS) вне области MVP; перенесена в Phase 2+.
3. **Чтение перед записью**: непосредственно перед записью любого файла перечитать его, чтобы обнаружить одновременные изменения в той же области блокировки. Прерывать, если файл изменился.
4. **Обязательность diff**: каждая операция записи предварится машиночитаемым diff, показанным оператору. Никаких тихих автоизменений.
5. **Атомарность операции**: рассматривать полный цикл выполнения как логическую единицу. При сбое прерывать оставшиеся шаги. Операции записи ДОЛЖНЫ использовать шаблон «временный файл + переименование» (запись по пути `.tmp`, затем атомарный `os.rename`), чтобы предотвратить частичные записи. Это гарантирует атомарность только в пределах одного файла; многофайловые наборы изменений ДОЛЖНЫ дополнительно следовать Протоколу многофайлового коммита (#9).
6. **Без автокоммита**: изменяет файлы, но никогда их не коммитит. Контроль версий ведёт оператор.
7. **Структурированные ошибки**: каждая ошибка delegate() излучает событие по §Event Schema с полем `error_category` (`hash_mismatch`, `trust_mismatch`, `audit_mismatch`, `blocking_finding`, `skill_failure`, `operator_timeout`, `gate_failure`, `unknown`). Процедуры восстановления ссылаются на категорию в `suggested_action`.
8. **Сбор постмортем-трассировки**: при выводах уровня critical, вызванных сбоем delegate(), Документатор фиксирует полный трассировочный след операции (все предпринятые шаги, промежуточные состояния, метки времени) для просмотра оператором.
9. **Протокол многофайлового коммита**: для наборов изменений, охватывающих несколько файлов (документ, `index-RU.md`, changelog, манифест, хранилище хешей), обеспечивать двухфазную фиксацию только средствами файловых операций — без фоновых процессов и демонов.
  a. **Подготовка (Stage)**: записать всё новое содержимое по путям `.tmp` в их целевых каталогах. Проверить все временные файлы перед переходом к фазе 2.
  b. **Журнал намерения (Intent record)**: до первого переименования записать журнал намерения в `documenter/intent/<tx_id>.json` (см. §Configuration Guide, Intent Record), идентифицирующий каждый файл набора изменений. Этот журнал переживает сбои и позволяет выполнить восстановление. Запись ДОЛЖНА использовать шаблон «временный файл + переименование» (тот же, что в §5), чтобы предотвратить частичный журнал при сбое посреди записи; холодный старт проверяет целостность журнала перед его использованием. Записи журнала намерения ДОЛЖНЫ ссылаться только на пути файлов, отслеживаемых манифестом. Любая попытка подготовить путь вне манифеста в ходе набора изменений приводит к тому, что `delegate()` отклоняет вызов с `error_category: unknown`, и никакие записи не выполняются.
  c. **Упорядоченные переименования**: выполнять переименования в фиксированном порядке — содержимое документа → `index-RU.md` → changelog → `docs-manifest.yaml` → `documenter/hashes.json`. Манифест фиксируется последним среди документов, чтобы сбой до манифеста оставил осиротевшие, но читаемые файлы (безопасно, аудируемо), а не висячие перекрёстные ссылки (ломающе).
  d. **Очистка**: после всех переименований излучить события аудита в журнал аудита только для добавления, обновить содержимое хранилища хешей (этот файл уже был переименован на шаге 9c), затем удалить журнал намерения. Журнал намерения ДОЛЖЕН удаляться последним — это единственный долговременный резервный источник для реконструкции событий после сбоя.
  Восстановление: при холодном старте, если остались незакрытые журналы намерения, сравнить `before_hash` и `after_hash` каждой записи с фактическим содержимым файла. Три ветви: (1) если файлы совпадают с `after_hash` — уже зафиксировано предыдущим успешным запуском, пропустить; (2) если файлы совпадают с `before_hash` — внешних изменений после сбоя не было, автоматически выполнить прямую докатку (roll-forward) из подготовленных файлов `.tmp`; (3) если не совпадает ни то ни другое — обнаружено внешнее изменение, прервать и эскалировать оператору с `error_category: unknown` и постмортем-трассировкой (§8). Журнал намерения хранит структурные метаданные (tx_id, target_id, created_at, entries[path, before_hash, after_hash]), достаточные, чтобы реконструировать, какие файлы были изменены, но НЕ содержит решений событий, позиций оператора или полной полезной нагрузки протокольных событий. Утверждение о том, что «утраченные события аудита реконструируются», неверно для MVP — восстановимо только происхождение изменений файлов; истинная реконструкция событий требует журнала аудита только для добавления (§Delivery Semantics, configuration-guide).
