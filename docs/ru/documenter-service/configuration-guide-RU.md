## Область применения

В данном документе определяются структуры данных времени выполнения и их правила целостности: хранилище хэшей, журнал аудита, журнал намерения, схема событий, режимы соответствия глоссария и процедура согласования RU. Схема файла политики, правила проверки в момент загрузки, параметры операционной настройки и рабочий процесс авторизации по уровням находятся в файле `documenter-service/policy-reference.md` — единственном источнике истины для конфигурации. Там, где это руководство ссылается на поле политики по имени (например, `audit_freshness`, `rescan_batch_ceiling`), §Field Reference в справочнике по политике определяет его тип, значение по умолчанию и допустимые замечания; поведение, приписываемое полю здесь, там не повторяется.

## Происхождение поля манифеста

`docs-manifest.yaml` — это сгенерированный индекс: frontmatter является источником истины, а манифест — его выводом. Единственным автором является `tools/gen_manifest.py` до момента выпуска генератора этапа A согласно плану (sess-doc-reliability-algo), после чего он остаётся единственным автором.

| Поле манифеста | Происхождение |
|----------------|------------|
| `id` | frontmatter `id` (обязательный) |
| `path` | генератор обхода `docs/en/` (фактическое расхождение файла) |
| `title` | frontmatter `title`, по умолчанию первый H1 |
| `version` | frontmatter `Version` |
| `status` | frontmatter `Status` |
| `abstraction` | frontmatter `Abstraction` |
| `has_translation` | frontmatter `has_translation` |
| `changelog-path` | frontmatter `changelog-path` |
| `references` | frontmatter `references` (исключение, редактируемое автором) |
| `allow_non_index_paths` | frontmatter `allow_non_index_paths` |

Правила:

- Не пустые `references` / `allow_non_index_paths` разрешены только для зарегистрированных многодокументных исключений (AGENTS.md §2.1); валидатор помечает остальные как высокий Уровень серьёзности.
- Записи отсортированы по `id`.
- Сгенерированный файл содержит маркер `GENERATED — DO NOT EDIT`.
- Заголовочные комментарии исторического манифеста сохраняются генератором как фиксированная константа преамбулы.

## Хранилище хэшей

Токены content-hash хранятся во внешнем файле `documenter/hashes.json` — управляются исключительно Документатором, скрыты от оператора. Обеспечивают оптимистичный контроль параллельного доступа для записей в режиме делегата.

### Структура

```json
{
  "version": 1,
  "entries": {
    "path/to/file.md": {
      "last_hash": "sha256:abcdef...",
      "last_modified": "2026-11-08T10:30:00Z",
      "history": [
        {"hash": "sha256:...old", "timestamp": "2026-11-07T09:00:00Z"}
      ]
    }
  }
}
```

Две концептуальные подсистемы с различными семантиками сохранения состояния и жизненного цикла:

| Подсистема | Содержание | Постоянство | Жизненный цикл |
|-----------|---------|-------------|-----------|
| **Снимок** | `last_hash`, `last_modified` | Сохраняется между вызовами | Обновляется после каждого цикла `audit()` или `delegate()` |
| **История** | `history[]` записей об изменении хеша | Бессрочно | Добавляется только; периодическая сборка мусора перед Tier 2+ |

Снимок состояния обеспечивает обнаружение конфликтов OCC за время O(1). Журнал изменений предоставляет возможность аудита и воспроизведения истории.

### Разрешение конфликтов

Прочитать → сравнить ожидаемый хэш с текущим хэшем содержимого → применить при совпадении → обновить запись. При несовпадении: отклонить с сигналом повторной попытки («Файл изменился с момента сканирования; пожалуйста, повторно запустите audit() и повторите попытку»). Повторные вызовы ОБЯЗАНЫ использовать экспоненциальную задержку с джиттером (базовая задержка: `retry_backoff_base`; максимальное число попыток: `retry_max_attempts` — оба поля политики, см. §Field Reference в `documenter-service/policy-reference.md`). Полное повторное сканирование ограничено полем политики `rescan_batch_ceiling` (по умолчанию 50 документов за один вызов). При достижении этого предела ответ включает `has_remaining: true` и курсор продолжения (`scan_cursor`) — передайте его обратно, чтобы возобновить сканирование с места, на котором остановился предыдущий вызов. Запись в реестре аудита фиксирует фактически просканированные идентификаторы документов (никогда не `*`, если все документы не были просканированы за один вызов). Частичное сканирование НЕ дает права на вызов delegate() для непросканированных документов — оператор должен завершить сканирование, прежде чем делегирование станет разрешено. Фоновое выполнение отсутствует. При изменении статуса глоссария полное повторное сканирование всех документов вызывает обновление хэшей для каждой записи.

**Гарантия самовосстановления на основе поведения:** Хранилище хэшей должно быть восстанавливаемо при любом сбое во время запуска. Реализация ОБЯЗАНА сочетать как минимум ДВА из следующих методов: атомарная запись (временный файл + переименование), хэш снимка перед записью (CRC32c/SHA-256 вместе с содержимым) или ротация `.bak`. WAL не требуется для MVP. Проверка целостности при холодном старте проверяет наличие файла hashes.json, валидирует его структуру и сканирует `documenter/intent/` на наличие оставшихся записей в соответствии с правилами §Журнал намерения.

**Git diff как дополнительный сигнал:** `git log` по `hashes.json` может обеспечить историческое восстановление, но НЕ заменяет CRC/контрольную сумму (повреждение между коммитами невозможно обнаружить только по журналу) и WAL/резервную копию (сбой во время записи приводит к потере незафиксированного состояния). Разница HEAD в Git должна оставаться сигналом **только рекомендательного характера** — она не может служить основным средством обнаружения конфликтов, поскольку ссылки (refs) перемещаются независимо от изменений содержимого. Для авторитетного разрешения конфликтов используйте прямые контрольные суммы файлов с семантикой оптимистичной блокировки.

`documenter/hashes.json` отслеживается манифестом как операционный артефакт (`operational: true`). `documenter/intent/` (записи намерений) и `documenter/audits.json` (реестр аудитов) аналогичным образом являются операционными — управляются исключительно Документатором, скрыты от оператора и исключены из области действия манифеста для `audit()` и `delegate()`.

**Семантика кэша (ADR-010):** `documenter/hashes.json` — это **восстанавливаемый кэш**, а не авторитетное состояние. Документатор может восстановить его с нуля в любой момент (флаг CLI `--rebuild`); промах кэша вызывает восстановление и продолжение работы, а не ошибку. Поэтому обнаружение оптимистичной конкурентности охватывает только гонки в пределах одного окна вызова (между аудитом и применением); история git является основным журналом аудита (согласно `documenter-service/mvp-contract.md` §2.1 / ADR-007). Локальные инструменты в `tools/` НЕ обязаны обновлять хранилище хэшей при изменении документов, отслеживаемых манифестом.

## Журнал намерения

Журнал восстановления после сбоев, записываемый в `documenter/intent/<tx_id>.json` перед первым переименованием в многофайловом коммите. Управляется исключительно Документатором, скрыт от оператора. Обеспечивает «намеренную» часть протокола двухфазного коммита (см. основной спецификацию, `documenter-service/index.md`, §Протокол безопасности #9).

**Схема:** `{tx_id: uuid-v4, target_id: string, created_at: ISO8601Z, entries: [{path, tmp_path, before_hash: sha256, after_hash: sha256}]}` — одна запись на файл в наборе изменений.

**Атомарная запись:** файл намерений должен записываться атомарно с использованием временного файла и операции переименования (тот же паттерн, что и в §Протокол безопасности #5 основного спецификации), чтобы предотвратить частичные записи. При холодном старте необходимо проверять структуру JSON файла намерений перед использованием его для восстановления; поврежденные или неполные записи намерений логируются и пропускаются.

**Правила восстановления (холодный старт):** при запуске сканировать `documenter/intent/`; для каждого оставшегося `.json` сравнить фактический хэш файла с `before_hash`/`after_hash`. Три варианта: (1) если файлы совпадают с `after_hash` — уже закоммичены предыдущим успешным запуском, пропустить; (2) если файлы совпадают с `before_hash` — внешних изменений с момента сбоя не было, выполнить откат вперёд путём переименования `.tmp` (в соответствии с порядком коммита в основном спецификации); (3) если ни один из вариантов не совпадает — обнаружены внешние изменения, прервать и эскалировать (`error_category: unknown`).

## Реестр аудита

Вызовы аудита сохраняются в `documenter/audits.json` — управляется исключительно **Документатором**, скрыто от оператора. Обеспечивает данные, лежащие в основе шлюза предварительного аудита `delegate()` (§Interfaces, основной спецификации). Только по запросу: фоновый процесс записи отсутствует; реестр обновляется синхронно в конце каждого вызова `audit()`.

### Структура

```json
{
  "version": 1,
  "entries": {
    "<audit_id>": {
      "issued_at": "2026-11-08T10:30:00Z",
      "scope": "*",
      "findings": [
        {"severity": "high", "target_id": "doc-a", "description": "Missing changelog"}
      ],
      "scanned_ids": ["doc-a", "doc-b", "..."],
      "has_remaining": false,
      "scan_cursor": null
    }
  }
}
```

| Поле | Тип | Описание |
|-------|------|-------------|
| `audit_id` | uuid-v4 | Ключ. Совпадает с `audit_id`, возвращаемым функцией `audit()`. |
| `issued_at` | ISO8601Z | Временная метка завершения аудита. Используется шлюзом для проверки `audit_freshness`. |
| `scope` | string | `*` только тогда, когда все документы были проверены за один вызов; в противном случае равно единственному `target_id`, переданному в `audit()` (например, `audit(target_id="doc-a")`). При использовании частичных сканирований (`has_remaining: true`) scope может всё ещё совпадать с `target_id`, но делегирование блокируется правилом 5 в §Gate Validation. Полное покрытие проверяется через `scanned_ids`, а не только через scope. |
| `findings` | array | Структурированные результаты из `audit()`. Шлюз проверяет наличие записей `high`/`critical`, соответствующих `target_id`. |
| `scanned_ids` | array[string] | Список идентификаторов документов, фактически проверенных в ходе данного вызова. Заполняется при каждом аудите — никогда не бывает пустым, если только сканирование не охватило ноль документов. |
| `has_remaining` | boolean | `true`, когда сканирование было приостановлено из-за `rescan_batch_ceiling`; указывает на неполное покрытие. Значение false или отсутствие означает, что все документы были проверены. |
| `scan_cursor` | string \| null | Токен продолжения для возобновлённых сканирований. Присутствует только тогда, когда `has_remaining` равно `true`. Непрозрачное значение, кодирующее позицию последнего обработанного документа. |

### Проверка шлюза

Когда `delegate()` получает `audit_id`, он считывает реестр и проверяет:

1. **Существование:** `audit_id` является ключом в `entries`. Отсутствует → отклонить с `error_category: audit_mismatch`.
2. **Свежесть:** `now - issued_at ≤ audit_freshness` (поле политики). Просрочено → отклонить с `error_category: audit_mismatch`.
3. **Покрытие области:** `scope == "*" OR scope == target_id`. Несоответствие → отклонить с `error_category: audit_mismatch`. Для сканирования полных корпусов (`target_id: "*"`) полнота дополнительно проверяется через `scanned_ids` — делегатский целевой объект должен присутствовать в списке; если `has_remaining` равно `true`, некоторые документы не просканированы, и любой делегат блокируется согласно правилу 5 ниже.
4. **Блокирующие результаты:** любой элемент в `findings` с `severity ∈ {high, critical}` И `target_id`, совпадающим с делегатским целевым объектом → отклонить с `error_category: blocking_finding`.
5. **Завершение сканирования:** если `has_remaining` было `true` для зарегистрированного сканирования, делегат отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение использует `error_category: blocking_finding`.

**Предварительный контрольный пункт:** По умолчанию `delegate()` требует действительный `audit_id` от предыдущего вызова `audit()`. Проверка выполняется по реестру аудитов (см. выше): (1) `audit_id` должен существовать; (2) его `issued_at` должен попадать в окно `audit_freshness` (поле политики, по умолчанию 30 минут; схема: `documenter-service/policy-reference.md`, §Справочник по полям); (3) его `scope` должен полностью покрывать `target_id` (`*` совпадает с любым, в противном случае требуется точное совпадение); (4) в реестре не должно существовать `high` или `critical` вывода для `target_id`; (5) если для зарегистрированного сканирования `has_remaining` было `true`, делегирование отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение по правилам (1–3) использует `error_category: audit_mismatch`; по (4) или правилу (5) использует `error_category: blocking_finding`.

**Исключение для предварительного просмотра:** Вызовы `delegate()` с параметром `change_type=update` и без указания намерения записи (режим предварительного просмотра, возвращающий разницу без применения изменений) освобождаются от проверок `allowed_operations` на всех уровнях. Такие вызовы всегда возвращают вычисленную разницу, но никогда не изменяют файлы.

**Режим отказа при холодном старте:** Если реестр аудита отсутствует, поврежден или недоступен для чтения, шлюз переходит в режим FAIL CLOSED — все операции записи запрещаются до явного вмешательства оператора. Для отмены ограничений требуется аутентифицированное действие через `documenter.override_gate(reason, operator_id)`, которое фиксирует инцидент и разрешает ровно один последующий вызов `delegate()` без свежего аудита. Повторные отключения ограничений требуют одобрения уровня Tier 2 и выше.

## Схема события

События **Документатора** генерируются внутри канонического [EventEnvelope](../../service-contract/index.md#event-envelope), определённого в контракте на Артефакты и события между сервисами. Конверт содержит метаданные маршрутизации (`schema_version`, `event_id`, `event_type`, `emitted_at`, `session_id`, `phase_id`, `actor`, **`severity`**, `causation_id`/`correlation_id`); специфичные для **Документатора** данные находятся в объекте `payload` ниже.

### Схема полезной нагрузки проблемы

Генерируется, когда `audit()` или `delegate()` обнаруживает проблемы. `event_type: documenter.issue`.

| Поле | Тип | Обязательно | Описание |
|-------|------|----------|-------------|
| `target_id` | string | да | Идентификатор документа из манифеста |
| `document_id` | string | да | Путь в файловой системе (относительно корня рабочей области) |
| `description` | string | да | Краткое описание Вывода, понятное человеку |
| `suggested_trust_level` | `safe` \| `review` | да | Результат работы классификатора доверия; авторитетный нижний предел для запросов delegate() |
| `suggested_action` | string | да | Краткая рекомендация к действию |
| `before_hash` | sha256:hex \| null | нет | Хэш содержимого до операции (null, если предыдущего состояния не было) |
| `after_hash` | sha256:hex \| null | нет | Хэш содержимого после операции (null, если изменений ещё не произошло) |
| `tier` | int | да | Текущая Ступень доверия на момент выдачи (0–3) |
| `error_category` | string \| null | нет | Устанавливается только для событий с ошибкой (см. §Замечания категорий ошибок ниже) |
| `audit_id` | uuid-v4 \| null | условно | Присутствует в событиях `delegate()`, прошедших пре-аудит (UUID вызова аудита, авторизовавшего этот вызов); отсутствует в событиях `audit()` и событиях отклонения шлюза. Null в событиях, где delegate был вызван без аудита (шлюз явно отключён в политике). |

**Поля на уровне конверта:** `event_id` (уникальный; ключ идемпотентности), `event_type` (`documenter.issue`), `emitted_at` (ISO 8601Z, обязательно), `actor` (`{kind: operator\|agent\|service, id}`), `severity` (`low` | `medium` | `high` | `critical` — унифицированная таксономия), `session_id` (`string\|null`; обязательно при проверке конкретной сессии; может быть null при сканировании соответствия документатора для всего корпуса), `phase_id` (integer \| null; присутствует, когда событие связано с конкретной фазой протокола, в противном случае null).

### Схема полезной нагрузки для одобрения

Генерируется при вычислении уровня одобрения для уровня 3 или при явном вызове `documenter.approve()`. `event_type: documenter.approval`. Поля, не указанные ниже, заменяют соответствующие поля полезной нагрузки проблемы в том же envelope.

| Поле | Тип | Описание |
|-------|------|-------------|
| `change_type` | `update` \| `split` \| `create_ru` \| `custom` | Тип изменения, которое было рассмотрено |
| `requested_trust_level` | `safe` \| `review` | Запрошенный уровень доверия вызывающего |
| `effective_trust_level` | `safe` \| `review` | Фактически применённый уровень доверия |
| `diff_hash` | `sha256:hex` | Хэш диффа, представленного оператору (привязан к `approval_id`) |
| `approval_id` | uuid-v4 \| null | Значение `approval_id`, возвращённое `delegate()`, когда `approval_required` равно true; присутствует для внеканальных согласований, null для событий автоматического согласования Tier 3 |
| `decision` | `approved` \| `rejected` \| `auto_approved` | Внеканальное одобрение/отклонение оператором или решение по шаблону Tier 3 |
| `operator_id` | string | Идентичность оператора, который одобрил/отклонил; ОБЯЗАТЕЛЬНО должна отличаться от actor.id предлагающего актора (внеканально). Для `auto_approved` содержит `pattern:<pattern_id>` вместо реального ID оператора. |
| `decided_at` | ISO8601Z | Временная метка действия одобрения/отклонения через `documenter.approve()` |
| `pattern_id` | string \| null | Заполняется только для событий `auto_approved` |

Формула для расчёта уровня одобрения для требования 3-го уровня:

```
approval_rate = count(decision = approved) / (count(decision = approved) + count(decision = rejected))
```

События `auto_approved` и `operator_timeout` исключаются из знаменателя. Для уровня 3 требуется `approval_rate >= 0.90` И минимальный размер выборки из 20 ручных решений. Автоматическое применение шаблона блокируется, если в журнале аудита содержатся результаты `high` или `critical` для целевого объекта.

### Замечания категорий ошибок

| Значение | Описание | Процедура восстановления |
|-------|---------|--------------------|
| `trust_mismatch` | Вызывающий запросил `trust_level` ниже выведенного порога (§Классификация доверия, основной спецификации) | Повторно вызвать `delegate()` с уровнем, указанным в ошибке |
| `hash_mismatch` | Обнаружено изменение во время чтения перед записью | Повторно запустить `audit()`, получить свежий diff, повторить `delegate()` |
| `audit_mismatch` | `audit_id` отсутствует в реестре аудитов, истёк согласно `audit_freshness`, его `scope` не покрывает `target_id`, или его сканирование неполное (`has_remaining: true`) (§Реестр аудитов) | Повторно запустить `audit()` для цели с `scan_cursor`, если существует частичное сканирование, получить свежий `audit_id`, повторить `delegate()` |
| `blocking_finding` | Реестр аудитов содержит `high` или `critical` находки для `target_id`, или сканирование неполное (`has_remaining: true`) — делегат не может авторизовать для несканированных документов (§Реестр аудитов) | Устранить блокирующие находки, повторно запустить `audit()` для получения чистого `audit_id`, повторить `delegate()` |
| `skill_failure` | Навык Документатора упал или вернул ошибку | Проверить логи навыка, убедиться в правильности входных параметров, повторить |
| `operator_timeout` | Оператор не ответил на предложенный diff в течение `operator_approval_timeout` секунд на этапе синхронного одобрения активного вызова `delegate()` (поле политики) | Вручную проверить находки, повторно выдать команду с теми же параметрами |
| `gate_failure` | Реестр аудитов отсутствует, повреждён или недоступен при холодном старте — поведение FAIL-CLOSED блокирует делегата. Требуется аутентифицированное переопределение через `documenter.override_gate(reason, operator_id)` перед тем, как любая запись сможет продолжиться. Повторные переопределения требуют одобрения уровня Tier 2+. | Выполнить переопределение оператором, затем повторить `delegate()` |
| `unknown` | Необработанное исключение во время выполнения delegate() | Захватить трассировку после инцидента (§Протокол безопасности #8), эскалировать |

### Семантика доставки

События поступают в артефакты Фазы 5 во время заседаний Совета. В режиме по запросу события генерируются синхронно и сохраняются через `$WORKSPACE/documenter/events/` для повторного воспроизведения оператором. Потерянные события восстанавливаются на основе оставшихся записей намерения при холодном запуске (§Журнал намерения). Порядок сохраняется в пределах области `target_id`. Во время пост-аварийного согласования события генерируются до удаления записей намерения (§Журнал намерения, порядок очистки). **Единое место хранения**: все данные о событиях в рамках всего корпуса хранятся в `sessions/<session_id>/events.jsonl` (каноническая обёртка); аудиты Документатора в рамках всего корпуса используют `documenter/corpus-audit/events.jsonl`. Других путей для событий не существует. Потребители устраняют дублирование по `event_id`; контракт предполагает только добавление.
