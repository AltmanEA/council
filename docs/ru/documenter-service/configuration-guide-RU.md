## Область применения

Этот документ определяет структуры данных рантайма и их правила целостности: хранилище хешей, реестр аудита, журнал намерения, схему событий, режимы соответствия глоссарию и процедуру выравнивания RU. Схема файла политики, правила валидации при загрузке, параметры операционной настройки и рабочий процесс авторизации ступеней находятся в `documenter-service/policy-reference.md` — едином источнике истины для конфигурации. Когда данное руководство ссылается на поле политики по имени (например, `audit_freshness`, `rescan_batch_ceiling`), §Field Reference в справочнике политик определяет его тип, значение по умолчанию и допустимые значения; поведение, приписанное полю здесь, там не дублируется.

## Хранилище хешей

Токены хешей содержимого хранятся вовне в `documenter/hashes.json` — управляются исключительно Документатором, скрыты от оператора. Обеспечивают оптимистический контроль конкурентности для записей в режиме delegate.

### Структура

```json
{
  "version": 1,
  "entries": {
    "path/to/file.md": {
      "last_hash": "sha256:abcdef...",
      "last_modified": "2026-11-08T10:30:00Z",
      "history": [
        {"hash": "sha256:...old", "timestamp": "2026-11-07T09:00:00Z"}
      ]
    }
  }
}
```

Две концептуальные подсистемы с различными семантиками сохранения и жизненного цикла:

| Подсистема | Содержимое | Сохранение | Жизненный цикл |
|-----------|---------|-------------|-----------|
| **Снимок (Snapshot)** | `last_hash`, `last_modified` | Сохраняется между вызовами | Обновляется после каждого цикла `audit()` или `delegate()` |
| **История (History)** | `history[]` записей об изменении хешей | Бессрочно | Только добавление; периодическая сборка мусора перед Ступенью 2+ |

Снимок обеспечивает обнаружение конфликтов OCC за O(1). История обеспечивает журнал аудита и возможность воспроизведения.

### Разрешение конфликтов

Чтение → сравнение ожидаемого хеша с хешем текущего содержимого → применение при совпадении → обновление записи. При несовпадении: отклонение с сигналом повтора («Файл изменился со времени сканирования; пожалуйста, заново запустите audit(), затем повторите попытку»). Повторные вызовы ДОЛЖНЫ использовать экспоненциальную задержку с джиттером (базовая задержка: `retry_backoff_base`; потолок попыток: `retry_max_attempts` — оба поля политики, см. §Field Reference в `documenter-service/policy-reference.md`). Полное пересканирование ограничено полем политики `rescan_batch_ceiling` (по умолчанию 50 документов за вызов). Когда потолок достигнут, ответ включает `has_remaining: true` и курсор продолжения (`scan_cursor`) — передайте его обратно, чтобы возобновить сканирование с точки остановки предыдущего вызова. Запись реестра аудита фиксирует фактически просканированные идентификаторы документов (никогда `*`, если только все документы не были просканированы за один вызов). Частичное сканирование НЕ авторизует delegate() для непросканированных документов — оператор должен завершить сканирование до разрешения делегирования. Фоновое выполнение отсутствует. Когда статус глоссария меняется, полное пересканирование всех документов запускает обновление хешей для каждой записи.

**Гарантия поведенческого самолечения:** хранилище хешей должно быть восстановимо при любом сбое запуска. Реализация ДОЛЖНА сочетать как минимум ДВА из: атомарная запись (temp-file + rename), снимок хеша перед записью (CRC32c/SHA-256 наряду с содержимым) или ротация `.bak`. WAL для MVP не требуется. Проверка целостности на холодном старте проверяет наличие hashes.json, валидирует структуру и сканирует `documenter/intent/` на наличие незакрытых записей согласно правилам §Журнал намерения.

**Git diff как дополнительный сигнал:** `git log` по `hashes.json` может обеспечивать историческое восстановление, но НЕ заменяет CRC/контрольную сумму (порча между коммитами необнаружима из одного лишь журнала) и не заменяет WAL/резервное копирование (сбой посреди записи теряет незафиксированное состояние). Дифференция Git HEAD должна оставаться сигналом **только рекомендательного характера** — она не может служить основным средством обнаружения конфликтов, поскольку refs двигаются независимо от изменений содержимого. Для авторитетного разрешения конфликтов используйте прямые контрольные суммы файлов с семантикой оптимистической блокировки.

`documenter/hashes.json` отслеживается манифестом как операционный артефакт (`operational: true`). `documenter/intent/` (журналы намерения) и `documenter/audits.json` (реестр аудита) аналогично операционные — управляются исключительно Документатором, скрыты от оператора и исключены из области манифеста для `audit()` и `delegate()`.

## Журнал намерения

Журнал восстановления после сбоя, записываемый в `documenter/intent/<tx_id>.json` до первого переименования в многофайловой фиксации. Управляется исключительно Документатором, скрыт от оператора. Обеспечивает половину «намерения» протокола двухфазной фиксации (см. основную спецификацию, `documenter-service/index.md`, §Safety Protocol #9).

**Схема:** `{tx_id: uuid-v4, target_id: string, created_at: ISO8601Z, entries: [{path, tmp_path, before_hash: sha256, after_hash: sha256}]}` — одна запись на файл в наборе изменений.

**Атомарная запись:** файл намерения ДОЛЖЕН записываться через temp-file + rename (тот же шаблон, что §Safety Protocol #5 в основной спецификации), чтобы предотвратить частичные записи. Холодный старт ДОЛЖЕН валидировать структуру JSON намерения перед использованием для восстановления; повреждённые или неполные журналы намерения протоколируются и пропускаются.

**Правила восстановления (холодный старт):** при запуске сканируйте `documenter/intent/`; для каждого незакрытого `.json` сравните фактический хеш файла с `before_hash`/`after_hash`. Три ветви: (1) если файлы совпадают с `after_hash` — уже зафиксировано предыдущим успешным запуском, пропустить; (2) если файлы совпадают с `before_hash` — внешних изменений после сбоя не было, выполнить прямую докатку (roll-forward) переименованием `.tmp` (согласно порядку коммита в основной спецификации); (3) если не совпадает ни то ни другое — обнаружено внешнее изменение, прервать и эскалировать (`error_category: unknown`).

## Реестр аудита

Вызовы аудита сохраняются в `documenter/audits.json` — управляются исключительно Документатором, скрыты от оператора. Обеспечивают данными вентиль предварительного аудита `delegate()` (§Interfaces, основная спецификация). Только по требованию: фонового писателя нет; реестр обновляется синхронно в конце каждого вызова `audit()`.

### Структура

```json
{
  "version": 1,
  "entries": {
    "<audit_id>": {
      "issued_at": "2026-11-08T10:30:00Z",
      "scope": "*",
      "findings": [
        {"severity": "high", "target_id": "doc-a", "description": "Missing changelog"}
      ],
      "scanned_ids": ["doc-a", "doc-b", "..."],
      "has_remaining": false,
      "scan_cursor": null
    }
  }
}
```

| Поле | Тип | Описание |
|-------|------|-------------|
| `audit_id` | uuid-v4 | Ключ. Совпадает с `audit_id`, возвращаемым `audit()`. |
| `issued_at` | ISO8601Z | Метка времени завершения аудита. Используется вентилем для проверки `audit_freshness`. |
| `scope` | string | `*` только когда ВСЕ документы были просканированы за один вызов; иначе равен единственному `target_id`, переданному в `audit()` (например, `audit(target_id="doc-a")`). При частичных сканированиях (`has_remaining: true`) scope может по-прежнему равняться `target_id`, но делегирование блокируется правилом 5 в §Проверка шлюза. Полное покрытие проверяется через `scanned_ids`, а не по одному лишь scope. |
| `findings` | array | Структурированные выводы из `audit()`. Вентиль ищет записи `high`/`critical`, совпадающие с `target_id`. |
| `scanned_ids` | array[string] | Список идентификаторов документов, фактически просканированных за этот вызов. Заполняется при каждом аудите — никогда не пуст, если только сканирование не покрыло ноль документов. |
| `has_remaining` | boolean | `true`, когда сканирование было приостановлено из-за `rescan_batch_ceiling`; означает неполное покрытие. False или отсутствие означает, что все документы просканированы. |
| `scan_cursor` | string \| null | Токен продолжения для возобновлённых сканирований. Присутствует только когда `has_remaining` равно `true`. Непрозрачное значение, кодирующее последнюю обработанную позицию документа. |

### Проверка шлюза

Когда `delegate()` получает `audit_id`, он читает реестр и валидирует:

1. **Существование:** `audit_id` является ключом в `entries`. Отсутствует → отклонить с `error_category: audit_mismatch`.
2. **Свежесть:** `now - issued_at ≤ audit_freshness` (поле политики). Истёк → отклонить с `error_category: audit_mismatch`.
3. **Покрытие области:** `scope == "*" OR scope == target_id`. Невыполнение → отклонить с `error_category: audit_mismatch`. Для сканирований полного корпуса (`target_id: "*"`) полнота дополнительно проверяется через `scanned_ids` — цель делегата должна присутствовать в списке; если `has_remaining` равно `true`, часть документов не просканирована и любой делегат блокируется правилом 5 ниже.
4. **Блокирующие выводы:** любая запись в `findings` с `severity ∈ {high, critical}` И совпадением `target_id` с целью делегата → отклонить с `error_category: blocking_finding`.
5. **Завершённость сканирования:** если `has_remaining` было `true` для зарегистрированного сканирования, делегат отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение использует `error_category: blocking_finding`.

**Вентиль предварительного аудита:** По умолчанию `delegate()` требует действительный `audit_id` из предыдущего вызова `audit()`. Валидация выполняется по реестру аудита (§ выше): (1) `audit_id` должен существовать; (2) его `issued_at` должен попадать в окно `audit_freshness` (поле политики, по умолчанию 30 минут; схема: `documenter-service/policy-reference.md`, §Field Reference); (3) его `scope` должен полностью покрывать `target_id` (`*` совпадает с любым, иначе точное совпадение); (4) для `target_id` в реестре не должно существовать вывода уровня `high` или `critical`; (5) если `has_remaining` было `true` для зарегистрированного сканирования, делегат отклоняется до выполнения завершённого повторного сканирования (продолжение на основе курсора через `audit(scan_cursor=<value>)`). Отклонение по правилам (1–3) использует `error_category: audit_mismatch`; по правилу (4) или правилу (5) — `error_category: blocking_finding`.

**Исключение для предварительного просмотра:** Вызовы `delegate()` с `change_type=update` и без намерения записи (режим preview, возвращающий diff без применения изменений) не подлежат проверкам `allowed_operations` ни на одной ступени. Такие вызовы всегда возвращают вычисленный diff, но никогда не изменяют файлы.

**Режим отказа холодного старта:** Если реестр аудита отсутствует, повреждён или нечитаем, вентиль ЗАКРЫВАЕТСЯ ОТКАЗОМ (fails closed) — все операции записи запрещены до явного переопределения оператором. Переопределение требует аутентифицированного действия через `documenter.override_gate(reason, operator_id)`, которое протоколирует инцидент и разрешает ровно один последующий вызов `delegate()` без нового аудита. Повторные переопределения требуют одобрения Ступени 2+.

## Схема событий

События Документатора излучаются внутри канонического [EventEnvelope](../docs/service-contract/index.md#event-envelope), определённого в Контракте артефактов и событий между сервисами. Конверт несёт маршрутизирующие метаданные (`schema_version`, `event_id`, `event_type`, `emitted_at`, `session_id`, `phase_id`, `actor`, `severity`, `causation_id`/`correlation_id`); специфичные для Документатора данные находятся в объекте `payload` ниже.

### Схема полезной нагрузки события о проблеме

Излучается, когда `audit()` или `delegate()` находит проблемы. `event_type: documenter.issue`.

| Поле | Тип | Обязательно | Описание |
|-------|------|----------|-------------|
| `target_id` | string | да | Идентификатор документа из манифеста |
| `document_id` | string | да | Путь в файловой системе (относительно корня рабочего пространства) |
| `description` | string | да | Краткое человекочитаемое описание вывода |
| `suggested_trust_level` | `safe` \| `review` | да | Выход классификатора доверия; авторитетный базовый уровень для запросов delegate() |
| `suggested_action` | string | да | Краткая практически применимая рекомендация |
| `before_hash` | sha256:hex \| null | нет | Хеш содержимого до операции (null, если предыдущего состояния нет) |
| `after_hash` | sha256:hex \| null | нет | Хеш содержимого после операции (null, если изменения ещё нет) |
| `tier` | int | да | Текущая ступень доверия на момент излучения (0–3) |
| `error_category` | string \| null | нет | Заполняется только на событиях отказа (см. §Значения категорий ошибок ниже) |
| `audit_id` | uuid-v4 \| null | условно | Присутствует на событиях `delegate()`, прошедших вентиль предварительного аудита (UUID вызова аудита, авторизовавшего этот вызов); отсутствует на событиях `audit()` и на событиях отклонения вентилем. Null на событиях, где delegate был вызван без аудита (вентиль явно отключён в политике). |

**Поля уровня конверта:** `event_id` (уникальный; ключ идемпотентности), `event_type` (`documenter.issue`), `emitted_at` (ISO 8601Z, обязательно), `actor` (`{kind: operator\|agent\|service, id}`), `severity` (`low` | `medium` | `high` | `critical` — единая таксономия), `session_id` (`string\|null`; обязателен при аудите конкретной сессии; может быть null для общекорпусных проверок соответствия Документатора), `phase_id` (integer \| null; присутствует, когда событие соотносится с конкретной фазой протокола, иначе null).

### Схема полезной нагрузки одобрения

Излучается вычислением доли одобрений Ступени 3 либо явным вызовом `documenter.approve()`. `event_type: documenter.approval`. Поля, не перечисленные ниже, заменяют соответствующие поля issue-payload в том же конверте.

| Поле | Тип | Описание |
|-------|------|-------------|
| `change_type` | `update` \| `split` \| `create_ru` \| `custom` | Тип изменения, которое было просмотрено |
| `requested_trust_level` | `safe` \| `review` | Запрошенный вызывающим уровень доверия |
| `effective_trust_level` | `safe` \| `review` | Фактически применённый уровень доверия |
| `diff_hash` | `sha256:hex` | Хеш diff, представленного оператору (привязан к `approval_id`) |
| `approval_id` | uuid-v4 \| null | `approval_id`, возвращённый `delegate()`, когда `approval_required` истинно; присутствует при внеполосных одобрениях, null для событий автоодобрения Ступени 3 |
| `decision` | `approved` \| `rejected` \| `auto_approved` | Внеполосное одобрение/отклонение оператора или решение паттерна Ступени 3 |
| `operator_id` | string | Идентификация оператора, одобрившего/отклонившего; ДОЛЖЕН отличаться от actor.id предлагающего (внеполосно). Для `auto_approved` содержит `pattern:<pattern_id>` вместо реального идентификатора оператора. |
| `decided_at` | ISO8601Z | Метка времени действия одобрения/отклонения через `documenter.approve()` |
| `pattern_id` | string \| null | Заполняется только для событий `auto_approved` |

Формула доли одобрений для предпосылки Ступени 3:

```
approval_rate = count(decision = approved) / (count(decision = approved) + count(decision = rejected))
```

События `auto_approved` и `operator_timeout` исключаются из знаменателя. Ступень 3 требует `approval_rate >= 0.90` И минимальной выборки из 20 ручных решений. Автоприменение паттернов блокируется, если реестр аудита содержит выводы `high` или `critical` для цели.

### Значения категорий ошибок

| Значение | Смысл | Процедура восстановления |
|-------|---------|--------------------|
| `trust_mismatch` | Вызывающий запросил `trust_level` ниже выводимого базового уровня (§Trust Classification, основная спецификация) | Повторно вызвать `delegate()` с выводимым уровнем, сообщённым в ошибке |
| `hash_mismatch` | Чтение-перед-записью обнаружило одновременное изменение | Заново запустить `audit()`, получить свежий diff, повторить `delegate()` |
| `audit_mismatch` | `audit_id` отсутствует в реестре аудита, истёк согласно `audit_freshness`, его `scope` не покрывает `target_id`, или его сканирование незавершено (`has_remaining: true`) (§Реестр аудита) | Заново запустить `audit()` для цели с `scan_cursor`, если существует частичное сканирование, получить свежий `audit_id`, повторить `delegate()` |
| `blocking_finding` | Реестр аудита содержит выводы `high` или `critical` для `target_id`, либо сканирование незавершено (`has_remaining: true`) — delegate не может авторизовать для непросканированных документов (§Реестр аудита) | Устранить блокирующие выводы, заново запустить `audit()` для получения чистого `audit_id`, повторить `delegate()` |
| `skill_failure` | Навык Documentation Worker аварийно завершился или вернул ошибку | Проверить журналы навыка, проверить входные параметры, повторить попытку |
| `operator_timeout` | Оператор не ответил на представленный diff в пределах `operator_approval_timeout` секунд синхронной стадии одобрения активного вызова `delegate()` (поле политики) | Просмотреть выводы вручную, выпустить команду заново с теми же параметрами |
| `gate_failure` | Реестр аудита отсутствует, повреждён или нечитаем на холодном старте — поведение FAIL-CLOSED блокирует делегат. Требует аутентифицированного переопределения через `documenter.override_gate(reason, operator_id)` до выполнения любой записи. Повторные переопределения требуют одобрения Ступени 2+. | Выполнить переопределение оператором, затем повторить `delegate()` |
| `unknown` | Необработанное исключение во время выполнения delegate() | Зафиксировать постмортем-трассировку (§Safety Protocol #8), эскалировать |

### Семантика доставки

События поступают в артефакты Фазы 5 во время сессий Консилиума. В режиме по требованию события излучаются синхронно и сохраняются через `$WORKSPACE/documenter/events/` для воспроизведения оператором. Утраченные события реконструируются из незакрытых журналов намерения на холодном старте (§Журнал намерения). Порядок сохраняется внутри области `target_id`. Во время пост-аварийной сверки события излучаются до удаления журнала намерения (§Журнал намерения, порядок очистки). **Единое место хранения:** все данные событий общекорпусно находятся под `sessions/<session_id>/events.jsonl` (канонический конверт); общекорпусные аудиты Документатора используют `documenter/corpus-audit/events.jsonl`. Никаких иных путей событий не существует. Потребители дедуплицируют по `event_id`; контракт — только для добавления (append-only).
