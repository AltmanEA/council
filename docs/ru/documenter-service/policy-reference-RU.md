## Назначение

Авторитетная схема для файла политики Документатора: определения полей, правила проверки во время загрузки, параметры операционный настройки и пошаговый рабочий процесс авторизации по уровням. Семантика протокола, которую настраивают эти поля (уровни доверия, протокол безопасности, контракты интерфейсов), определена в `documenter-service/index.md`; структуры данных во время выполнения (хранилище хэшей, журнал намерения, схема событий) определены в `documenter-service/configuration-guide.md`. Этот документ не определяет собственного поведения — это поверхность конфигурации для поведения, определённого в других местах.

## Файл политики

Конфигурация в формате YAML, определяющая, какие операции разрешены на каждом уровне и в каких режимах соответствия. Создается и поддерживается оператором. Автоматическое продолжение на основе времени не является частью модели: одобрение всегда является явным действием оператора в рамках вызова `delegate()`, а единственным путем автоматического выполнения является автоматическое применение на основе шаблонов уровня 3 (см. §Доверенные уровни и §Семантика одобрения в основной спецификации, `documenter-service/index.md`).

**Правило валидатора:** Документатор обязан отклонять загрузку любого файла политики, в котором `allowed_operations` не пуст, а `active_tier < 2`. Это предотвращает ошибки конфигурации во время развертывания. **Правило авторизации:** Записи политики могут только ужесточать нижнюю границу встроенной классификации доверия, установленную основной спецификацией (§Trust Classification): запись `allowed_operations` может требовать `review` там, где таблица допускает `safe`, однако комбинация политик, разрешающая `trust_level` ниже *статического порога* для её `change_type`, является недействительной и должна быть отклонена на этапе загрузки — Документатор рассматривает это как ошибку конфигурации, что согласуется с приведённым выше правилом валидатора.

**Правило совместимости:** Все поля в разделе §Field Reference являются необязательными, за исключением `version`, `active_tier` и `allowed_operations`. Файл политики, написанный в соответствии с более ранней версией схемы, загружается успешно: отсутствующие поля принимают замечания по умолчанию, указанные ниже, а увеличение версии схемы не подразумевает удаление или переименование каких-либо полей.

```yaml
documenter_policy:
  version: "0.2.0"
  active_tier: 0                  # 0 = audit-only (MVP default)
  allowed_operations: []          # inert at active_tier < 2; populate when advancing
  glossary_enforcement: draft     # draft | active — controls noise reduction
  audit_freshness: 30             # minutes; max age of audit_id accepted by delegate() pre-audit gate
  lock_wait_timeout: 30           # seconds; advisory lock acquisition wait before abort
  retry_backoff_base: 1           # seconds; exponential backoff base on hash_mismatch retry
  retry_max_attempts: 3           # count; retry attempts before escalation to operator
  operator_approval_timeout: 300  # seconds; synchronous wait for approve/reject inside delegate()
  notification_mode: inline       # inline only — no asynchronous notification channel exists
  approval_expiry_window: 30            # minutes; maximum time between Tier 2+ authorization and the first delegate() invocation under that approval
  rescan_batch_ceiling: 50        # documents per full-rescan invocation before partial-report return
  max_diff_bytes: 524288          # bytes; maximum size of a decoded diff payload (default 512 KiB)
  sync_latency_budget_ms: 30000   # milliseconds; a synchronous call exceeding this budget returns a structured timeout error instead of blocking
  glossary_staleness_days: 30     # days since last glossary modification; terms appearing ≥3 times within this window are flagged as missing
  briefing_ref: null              # path to operator briefing artifact; required when active_tier >= 2
  allow_solo_approval: false      # bool; solo (self-)approval exception per ADR-017; absent ⇒ false (fail-closed)
  min_approval_delay_seconds: 0   # int; minimum seconds between proposal and solo approval; range [60, 86400]; absent ⇒ 0
```

На уровнях 0–1 `allowed_operations` должно оставаться пустым независимо от содержимого. Оператор обновляет этот файл явно при переходе на следующие уровни. Документатор отказывается выполнять любые операции, не указанные в списке.

**Исключение для предварительного просмотра:** Вызовы `delegate()` без намерения записи (режим предварительного просмотра, возвращающий разницу без применения изменений) освобождаются от проверки `allowed_operations` на всех уровнях. Уровень 1 специально полагается на это исключение для формирования разницы. Такие вызовы всегда возвращают вычисленную разницу, но никогда не изменяют файлы. Предварительный просмотр управляется через булевый параметр `preview` (§Interfaces, delegate()) — при установке замечания `true` не применяются ни валидация по уровням, ни контроль через шлюзы; проверяется только корректность схемы обязательных полей (`target_id`, `change_type`, `diff`).

### Ссылка на поле

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `version` | string | Да | `"0.2.0"` | Версия схемы политики для обнаружения совместимости |
| `active_tier` | int | Да | `0` | Текущая ступень доверия (0–3). Должна совпадать с таблицей Ступеней доверия (§Ступени доверия, основной спецификации). |
| `allowed_operations` | array | Да | `[]` | Операции, разрешённые на текущей ступени. Пусто ниже 2-й ступени. Может только ужесточать базовый уровень доверия (§Правило авторитета выше). |
| `approval_expiry_window` | int | Нет | `30` | Максимальное время (в минутах) до истечения срока неутверждённого `approval_id`. Диапазон: 5–1440 (от 5 минут до 24 часов). Используется вместе с внеканальным вызовом `documenter.approve(approval_id, operator_id)`, указанным в `documenter-service/mvp-contract.md` §4 (канонический контракт утверждения). |
| `allow_solo_approval` | bool | Нет | `false` | Включает исключение для самоутверждения одиночного оператора (`mvp-contract.md` §4, ADR-017) для единственной идентичности `op-*`. Отсутствие ⇒ `false`: самоутверждение запрещено (fail-closed), сохраняя норму `approver ≠ proposer`. Когда `true`, одиночное утверждение дополнительно требует, чтобы совпадающая оркестрация была `safe` (проверена против `change_type`, сохранённого в записи об утверждении), токен подтверждения `CONFIRMED_SOLE_REVIEWER` и окно `min_approval_delay_seconds`; ответ об утверждении содержит баннер с предупреждением о смещении. |
| `min_approval_delay_seconds` | int | Нет | `0` | Минимальное количество секунд, которое должно пройти между `created_at` предложения и его одиночным утверждением. Диапазон: 60–86400. Применяется только на пути одиночного утверждения (`allow_solo_approval: true`); замечания вне диапазона или нецелочисленные отклоняются при загрузке политики. Отсутствие или невозможность разобрать `created_at` во время проверки задержки → `gate_failure` (fail-closed). Рекомендуемый минимум для одиночного развертывания: 300. |
| `audit_freshness` | int | Нет | `30` | Максимальный возраст (в минутах) `audit_id`, принимаемого вратарём предварительной проверки `delegate()`. Вратарь дополнительно проверяет покрытие области действия (точное совпадение или `*`), заблокированные результаты и завершение сканирования (`has_remaining` не должно быть `true`) против реестра аудита (`documenter-service/configuration-guide.md`, §Реестр аудита). Установите `0`, чтобы полностью отключить вратарь (аудит не требуется; `audit_id` будет проигнорирован, если предоставлен). Любое другое значение обеспечивает окно свежести. |
| `briefing_ref` | string | Нет | `null` | Путь к архивированному артефакту инструктажа оператора, документирующему область делегированных полномочий. ДОЛЖНО быть не равным null, когда `active_tier >= 2` (§Рабочий процесс авторизации, шаг 4). |
| `glossary_enforcement` | enum | Нет | `draft` | Управляет снижением шума соблюдения глоссария (§Соблюдение глоссария, руководство по конфигурации). |
| `glossary_staleness_days` | int | Нет | `30` | Дней с момента последней модификации глоссария; термины, появляющиеся ≥3 раза в течение этого окна, помечаются как отсутствующие (§Соблюдение глоссария, руководство по конфигурации). |
| `lock_wait_timeout` | int | Нет | `30` | Секунды ожидания блокировки уровня операции перед прерыванием с ошибкой владельца блокировки, описанной в §Протокол безопасности #2 (основной спецификации). |
| `max_diff_bytes` | int | Нет | `524288` | Максимальный размер в байтах декодированного полезного груза `diff`/`diff_input` (по умолчанию 512 КиБ). Более крупный полезный груз отклоняется на входе со структурированной ошибкой до любой обработки diff. |
| `notification_mode` | enum | Нет | `inline` | Режим доставки для операторных подсказок. `inline` — единственное принятое значение в MVP: подсказки, diff и вердикты возвращаются внутри ответа вызова. Неизвестные замечания отклоняются при загрузке. |
| `operator_approval_timeout` | int | Нет | `300` | Секунды, которые активный вызов `delegate()` ожидает явного утверждения/отклонения перед выдачей `error_category: operator_timeout`. Не является окном автоутверждения (§Семантика утверждения, основной спецификации). |
| `rescan_batch_ceiling` | int | Нет | `50` | Документы, обрабатываемые за один полный вызов повторного сканирования. При достижении этого замечания ответ включает `has_remaining: true` и токен продолжения `scan_cursor`; передача его обратно возобновляет выполнение с того места, где остановился предыдущий вызов. Частичные сканирования никогда не авторизуют делегатов для несканированных документов — оператор должен завершить все пакеты, прежде чем станет разрешено делегирование. Фоновое выполнение отсутствует. |
| `retry_backoff_base` | int | Нет | `1` | Базовая задержка (в секундах) для экспоненциального backoff с джиттером, используемого вызовами повторных попыток (§Разрешение конфликтов, руководство по конфигурации). |
| `retry_max_attempts` | int | Нет | `3` | Максимальное количество вызовов повторных попыток после `hash_mismatch` перед тем, как Документатор эскалирует оператору вместо повторной попытки. |
| `temperature` | float | Нет | `0.1` | Случайность генерации LLM; более высокие замечания увеличивают разнообразие (диапазон: 0.0–2.0). Применяется для каждого вывода агента роли (§Нулевые молчаливые замечания, layer-1.md). |
| `top_p` | float | Нет | `0.9` | Параметр выборки ядра; токены с кумулятивной вероятностью ниже этого порога исключаются (диапазон: 0.0–1.0). Применяется для каждого вывода агента роли (§Нулевые молчаливые замечания, layer-1.md). |
| `sync_latency_budget_ms` | int | Нет | `30000` | Максимальная продолжительность в миллисекундах для синхронного вызова `delegate()`. Вызов, превышающий этот бюджет, возвращает структурированную ошибку тайм-аута, а не блокируется бесконечно. |
| `frequency_penalty` | float | Нет | `0.0` | Снижает повторение токенов; положительные замечания штрафуют повторяющиеся токены (диапазон: -2.0–2.0). Нейтральное значение по умолчанию, явно установлено, а не выведено (§Нулевые молчаливые замечания, layer-1.md). |

### Записи для каждой операции

Записи в `allowed_operations` для каждой операции имеют следующую структуру:

```yaml
# Tier 2+ operation entry (default type — no explicit type field needed):
allowed_operations:
  - type: operation          # operation | pattern — omitted defaults to "operation"
    change_type: update      # update | split | create_ru | custom
    trust_level: safe        # safe | review — must not fall below the static floor (§Trust Classification, main spec)
    targets: []              # empty = all docs; list = specific manifest IDs
    requires_diff_preview: true  # always enforced at Tier 2+

# Tier 3 pattern entry (enables auto-apply for matching changes):
  - type: pattern
    pattern_id: "auto-bump-patch"   # unique identifier for this pattern
    pattern_description: "Deterministic patch-level version bumps in CHANGELOGS/*.changes.md and index.md metadata"
    match_criteria:
      change_type: update
      file_pattern: "CHANGELOGS/*.changes.md"  # glob-style path pattern; empty = match any file
    trust_level: safe
    requires_diff_preview: true
```

Поля ввода шаблона:

| Поле | Тип | Описание |
|-------|------|-------------|
| `type` | `operation` \| `pattern` | Дискриминатор. По умолчанию используется `operation` (для обратной совместимости). |
| `pattern_id` | string | Уникальный идентификатор данного шаблона (kebab-case). |
| `pattern_description` | string | Человекочитаемое описание того, что соответствует шаблону. |
| `match_criteria.change_type` | enum | Ограничивает соответствие определённым `change_type`. |
| `match_criteria.file_pattern` | string | Шаблон пути в стиле Glob относительно корня рабочей области. `*` = любые символы, кроме `/`, `**` = любые символы, включая `/`, `?` = один символ, кроме `/`. Недействительные шаблоны отклоняются при загрузке политики. |

## Активационный оверлей

Активационный оверлей — это **внешний YAML-файл**, который прозрачно загружается функцией `load_policy()` и объединяется с эффективной политикой на этапе чтения. Базовый файл политики (`documenter_policy.yml`) остаётся **базовой конфигурацией Tier 1** и не изменяется механизмом оверлея.

### Расположение оверлея

Путь к оверлею определяется следующим образом:

1. **Явный путь:** переменная окружения `DOCUMENTER_ACTIVATION_PATH` (должна быть абсолютной и находиться вне корня рабочей области).
2. **Путь по умолчанию:** `~/.council/documenter_activation.yml` (вне рабочей области по соглашению).

Когда явный путь установлен, но указывает на несуществующий файл или не-файл, загрузка завершается ошибкой `PolicyError` (fail-closed). Когда путь по умолчанию отсутствует, оверлей считается **отсутствующим**, и базовая политика Tier 1 используется без изменений.

### Схема оверлея

YAML оверлея — это плоское отображение. Разрешены только следующие ключи (строгий список разрешённых ключей):

| Ключ | Тип | Описание |
|-----|------|-------------|
| `active_tier` | int (не bool) | Переопределить эффективный уровень (обычно 2) |
| `scope` | str | Идентификатор шаблона области (см. ниже) |
| `allowed_operations` | list | Расширенное переопределение — ручной список операций (XOR с `scope`) |
| `scope_targets` | list[str] | Сужающее подмножество для шаблона (только с `scope`) |
| `briefing_ref` | str или null | Абсолютный путь вне корня рабочей области |
| `allow_solo_approval` | bool | Исключение для одиночного оператора (по умолчанию: false) |
| `min_approval_delay_seconds` | int в [60, 86400] | Окно задержки одиночного одобрения |

Неизвестные ключи вызывают `PolicyError` (fail-closed).

### Шаблоны области

Четыре шаблона области сопоставляют короткий идентификатор детерминированному набору разрешённых операций:

| Идентификатор шаблона | Тип изменения | Уровень доверия | Количество целей | Описание |
|-----------|-------------|-------------|--------------|-------------|
| `pilot-safe-v1` | `update` | `safe` | 2 | Минимальный безопасный пилот: механические обновления для 2 операционных документов |
| `docs-maint-safe` | `update` | `safe` | 24 | Механическое обслуживание (метаданные) по всему корпусу документов |
| `docs-content-review` | `update` | `review` | 24 | Контентные/нормативные обновления по всему корпусу документов |
| `ru-sync-review` | `create_ru` | `review` | 18 | RU-синхронизация создания/синхронизации для документов с переводами |

Когда выбран шаблон области, `scope_targets` может сузить набор целей до **непустого подмножества** целей шаблона (только сужение; расширение отклоняется).

### Правило XOR

Оверлей должен содержать **ровно один** из `scope` или `allowed_operations`. Указание обоих или отсутствия обоих вызывает `PolicyError`.

### Правила вложенности

- Явный путь оверлея должен быть абсолютным и находиться вне корня рабочей области.
- `briefing_ref` (если присутствует и не равен null) должен быть абсолютным путём вне корня рабочей области.
- Вложенность проверяется через `realpath` для сопротивления обходу через симлинки.

### Пример оверлея

```yaml
# Пример: активация pilot-safe-v1
active_tier: 2
scope: pilot-safe-v1
briefing_ref: /home/user/.council/briefings/tier2-pilot-safe-v1.md
allow_solo_approval: false
```

### Процедура активации / деактивации

1. **Активировать:** разместить действительный файл оверлея (или установить `DOCUMENTER_ACTIVATION_PATH`), проверить с помощью `python3 -m documenter_service --verify-activation --root .` (состояние `active`) или `python3 tools/activation_helper.py verify`.
2. **Деактивировать:** удалить или нейтрализовать файл оверлея, остановить Operator Ingress и удалить readiness sentinel; проверить с помощью `--verify-activation` (состояние `baseline`).

## Операционная настройка

Какая ручка управляет каким путём отказа. Все замечания являются полями политики из §Field Reference; для их применения не требуется изменение кода или перезапуск, кроме перезагрузки политики.

| Сбой или давление | Поле | При истощении |
|---------------------|-------|---------------|
| Одновременный `delegate()` от другого агента | `lock_wait_timeout` | Прервать до любой записи; ошибка указывает PID/IP владельца блокировки и метку времени получения (§Протокол безопасности #2) |
| Файл изменён между сканированием и записью | `retry_backoff_base` + `retry_max_attempts` | Эскалировать оператору; повторно запустить `audit()` для получения нового `audit_id` |
| Оператор отсутствует при представлении разницы | `operator_approval_timeout` | Выдать `error_category: operator_timeout`; ничего не записывается, временные `.tmp` файлы отбрасываются |
| Ожидание внеканальных оповещений | `notification_mode` | Не применимо — асинхронный канал отсутствует; см. §Семантика уведомлений |
| Полное повторное сканирование превышает количество документов | `rescan_batch_ceiling` | Ответ включает `has_remaining: true` и `scan_cursor`; оператор повторно вызывает `audit(scan_cursor=<value>)` для продолжения с места остановки предыдущего вызова |
| Устаревший, недействительный или неполный `audit_id` передан в `delegate()` | `audit_freshness` | Отклонить с `error_category: audit_mismatch` (реестр отсутствует/истёк/несоответствие области) или `error_category: blocking_finding` (присутствуют высокие/критические находки или сканирование не завершено, `has_remaining: true`) и действием повторного запуска `audit()`. Если реестр отсутствует/недоступен, FAILS CLOSED — все записи запрещены до аутентифицированного отмены через `documenter.override_gate(reason, operator_id)` |

### Семантика уведомлений

Документатор не имеет подсистемы уведомлений: нет таймера, нет демона, нет канала push-уведомлений, нет фонового опроса (см. §Цели и §Семантика одобрения, основной спецификации). Любой сигнал, видимый оператору — отчёт аудита, предварительный просмотр различий, запрос разрешения конфликта блокировки, запрос одобрения — генерируется в рамках синхронного ответа на вызов, который его породил, и дополнительно сохраняется в неизменяемый журнал событий (§Схема событий, руководство по конфигурации) для последующего воспроизведения. Поле `notification_mode` существует, чтобы сделать это явным и зарезервировать пространство имён: введение асинхронного канала стало бы изменением модели в основной спецификации, а не редактированием политики, и потребовало бы нового замечания `notification_mode` плюс определённого контракта доставки.

## Процесс авторизации

Порядок предоставления прав на запись. Каждый шаг представляет собой отдельное действие оператора; Документатор никогда не выполняет шаги самостоятельно. Шаги 1–3 предшествуют первому вызову уровня Tier 2+; в основном спецификации §Trust Tiers указано, что файл политики и брифинг являются обязательными предварительными условиями. Механики одобрения и отмены вне канала со стороны оператора, которые активируются после включения, описаны в `documenter-service/approval-surface.md` (канонический контракт: `mvp-contract.md` §4).

1. **Аудит на текущем уровне.** Запустите `audit("*")` и устраните замечания на уровнях `high` и `critical`. Уровень 2+ на некорректном корпусе автоматизирует дрейф, а не очистку.
2. **Создайте файл политики.** Составьте `documenter_policy.yml` согласно §Файл политики: установите допустимые комбинации `change_type` + `trust_level` + `targets` в `allowed_operations` и настройте операционные параметры согласно §Операционная настройка.
3. **Проверьте офлайн.** Загрузите кандидатский файл в режиме только проверки. Загрузка завершается ошибкой, если: `allowed_operations` не пусто ниже Уровня 2 (правило валидатора), `trust_level` ниже выведенного порога для его `change_type` (правило авторитета) или значение `notification_mode` не распознано.
4. **Запишите брифинг.** Напишите и сохраните брифинг оператора — в котором задокументированы, какие документы и замечания `change_type` делегированы, максимальное количество документов, к которым может обратиться один вызов, и процедура отмены — затем установите `briefing_ref` в путь к нему. Этот Артефакт является читаемым человеком counterpartом `allowed_operations`.
5. **Повысьте уровень.** Установите `active_tier` в том же редактировании, что и `briefing_ref`, чтобы частичное редактирование не могло оставить Уровень 2+ без ссылки на брифинг. Либо разместите действительный активационный оверлей (см. §Активационный оверлей), который предоставляет `active_tier: 2`, либо `scope`, либо `allowed_operations`, и `briefing_ref`; базовый файл политики остаётся базовой конфигурацией Tier 1 при использовании активации через оверлей.
6. **Самостоятельная авторизация (только ADR-017).** Если — и только если — в развертывании есть один оператор, дополнительно установите `allow_solo_approval: true` и `min_approval_delay_seconds` (рекомендуется ≥300) в том же редактировании, что и шаг 5, и запишите область действия самостоятельного одобрения в брифинге. В брифинге должно быть указано: эксперимент принят с риском и ограничен; самостоятельное одобрение применяется только к операциям с соответствием `safe`-trust; каждое самостоятельное одобрение требует введённого токена подтверждения `CONFIRMED_SOLE_REVIEWER` и окна задержки; каждое самостоятельное одобрение возвращает баннер предупреждения о смещении; область действия расширяется только после 5 последовательных чистых циклов записи (по одному change_type или одному документу за расширение); обязательный обзор оператором происходит в течение 30 дней после активации. Без `allow_solo_approval: true` система сохраняет строгую норму `approver ≠ proposer`.
7. **Первая запись на новом уровне.** Вызовите `delegate()` для одной низко-рисковой цели с новым `audit_id`. Просмотрите изменения по одному независимо от уровня; Уровень 2 предоставляет возможности, а не снижает тщательность проверки.
8. **Оцените для Уровня 3.** Повышайте уровень только на основе задокументированных доказательств: ≥90% одобрений на Уровне 2 за предшествующие две недели журнала событий (§Руководство по выбору уровня, основной спецификации), вычисляемое из полей `decision` в журнале событий (§Схема событий, руководство по конфигурации). Затем одобренные шаблоны явно перечисляются в `allowed_operations` с использованием записей `type: pattern` с `pattern_id`, `pattern_description` и `match_criteria` (§Записи на основе операций); Уровень 3 никогда не выводит шаблон, который оператор не авторизовал.

**Откат:** установите `active_tier` в меньшее значение. Изменение вступает в силу при следующем вызове; выполняющийся `delegate()` завершается на том уровне, на котором он был принят, удерживая блокировку на уровне операции для §Протокол безопасности #2.
