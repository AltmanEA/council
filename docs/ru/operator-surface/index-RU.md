## Область применения

Определяет единственный транспорт MVP, идентификатор вызывающей стороны, глаголы оператора, шлюз `pre_check`, доставку и возобновление Эскалации, вызов Документатора и доставку событий. Поля Артефакта находятся в `service-contract/index.md`; семантика времени выполнения — в `execution-runtime/index.md`.

Поверхность взаимодействия с оператором представляет собой адаптер в слое 2: он аутентифицирует вызывающую сторону, проверяет входные данные и вызывает функции слоя 1. Он не содержит логики протокола и не выполняет вызовы LLM. CLI и REST остаются отложенными адаптерами поверх тех же библиотечных функций.

## Идентификация и авторизация вызывающего абонента

Три класса вызывающих: `operator`, `agent`, `service`.

- AuthN: локальный процесс stdio плюс `COUNCIL_OPERATOR_ID` и `COUNCIL_OPERATOR_TOKEN` из окружения. Поверхность проверяет токен и никогда не передаёт его в Layer 1.
- AuthZ — отказ по умолчанию. Ошибки аутентификации (неизвестный вызывающий, отсутствующие/недействительные/отозванные учётные данные, истёкший токен) отклоняются согласно кодам ошибок AUTH.* в `operator-surface/index.md` §Идентификация и авторизация вызывающего; нарушения структурной схемы остаются `VAL.001`.
- `operator_id` — это человек. Агенты-принципалы НЕ ДОЛЖНЫ одобрять записи Документатора или разрешать эскалации на этапе MVP.

#### Аутентификация (MVP)

Выделяются три класса вызывающих объектов:

| Класс | Тип учетных данных | Область | Проверка |
|-------|----------------|-------|--------------|
| `Operator` | Сессия-привязанный подписанный токен | На основе сессии, оператор идентифицируется префиксом `op-...` (формат `^op-[a-z0-9][a-z0-9-]{2,63}$`) | Подпись проверяется общим модулем аутентификации в пределах Layer 2 |
| `Agent` | Подписанный токен с ограничением по сессии и утверждением о роли | Привязан к session_id и role_id | Подпись и принадлежность к роли проверяются на входе |
| `Service` | Учетные данные сервисного аккаунта с HMAC-подписью | Привязан к имени сервиса и разрешенным операциям | Предварительно зарегистрирован в конфигурации политик; HMAC проверяется на входе |

Структура токена: минимальный формат, похожий на JWT, `{alg, iss, sub, exp}`. Токены агента включают дополнительное утверждение `role`, связывающее субъект с конкретным role_id. Секрет HMAC, используемый для общих операций, хранится в файле `documenter-service/policy-reference.md` в разделе «Справочник по полям» под ключом `hmac_secret`, по умолчанию принимает значение, предоставленное оператором при запуске. Просроченные токены приводят к ошибке `AUTH.001`. Некорректные подписи приводят к ошибке `AUTH.002`. Неизвестные классы вызывающих объектов приводят к ошибке `AUTH.003`.

Коды ошибок для сбоев аутентификации:
- `AUTH.001` — Истекло время действия учетных данных. Запросите у вызывающей стороны получение нового токена.
- `AUTH.002` — Неверная подпись или измененный токен. Запишите в журнал и отклоните.
- `AUTH.003` — Нераспознанный класс вызывающей стороны. Проверьте разрешения инструментов MCP или конфигурацию интеграции.
- `AUTH.004` — Отозванные учетные данные (например, выход оператора из системы отзывает все токены агентов из Сессия).

## Шлюз `pre_check`

### Область применения и точка применения

Шлюз `pre_check` представляет собой проверку целостности артефактов документации перед фиксацией переходов состояния протокола. Он выполняется на уровне 2 (поверхность оператора) в виде синхронного вызова метода `audit(pre_check=true)` у Документатора и возвращает вердикт вызывающей стороне в рамках того же вызова.

- **Область применения:** все документы манифеста, относящиеся к текущей сессии (определяются по `target_id` из активного сценария).
- **Точка принудительного применения:** вызывается при каждом переходе между фазами (`2 → 3`, `3 → 4`, `4 → 5`) перед фиксацией состояния новой фазы в слое 1.
- **Переходы с контролем:** `2 → 3` (начало обсуждения), `3 → 4` (проверка консенсуса), `4 → 5` (принятие резолюции). Переход разрешён только при вердикте `pass`.
- **Передача вердикта в слой 1:** поверхность записывает результат вердикта (pass/fail/причина) в поле манифеста `pre_check_override` при переопределении или генерирует событие `precheck.failed`; среда выполнения читает это поле/событие при следующей оценке границы и либо продолжает выполнение, либо блокирует его.

### Логика вердикта

| Условие | Вердикт | Действие |
|-----------|---------|--------|
| Нет `high`/`critical` выводов для целевой области | `pass` | Продолжить переход |
| Присутствует любой `high` или `critical` вывод | `fail` | Блокировать переход; сгенерировать событие `precheck.failed` |
| Документатор недоступен (тайм-аут, сервис не работает) | `unavailable` | Тайм-аут и продолжение: продолжить переход, синхронно сгенерировать предупреждающее событие `precheck.unavailable` (решение по дорожной карте 3); действие применяется только к недоступности, вызванной тайм-аутом, а не к `fail` целостности реестра |
| Реестр аудита Документатора отсутствует/поврежден/не читается | `fail` | Блокировать переход (fail-closed согласно C-03) |

Таймаут шлюза — это константа, устанавливаемая на этапе загрузки: по умолчанию 5 секунд, может быть изменён один раз при запуске с помощью переменной окружения `PRE_CHECK_TIMEOUT`; в течение времени жизни процесса значение неизменно. Превышение таймаута приводит к вынесению вердикта `unavailable`. При запуске шлюза генерируется событие `precheck.running`, что позволяет наблюдателям отличать выполняющуюся проверку от зависшего состояния. (План MVP для Operator Surface, этап p3, ADR-015.)

### Документатор недоступен — Режим переопределения

Когда Документатор недоступен (вердикт `unavailable`), Модератор MVP НЕ ДОЛЖЕН блокировать выполнение бесконечно. Аутентифицированный вызов `council.override_precheck(reason, operator_id)` может быть выполнен, несмотря на сбой:

- Записи обхода содержат `reason` (свободный текст, объясняющий, почему шлюз был обойден).
- Обход записывается в манифест через поле `pre_check_override`.
- Событие `precheck.overridden` синхронно генерируется во время вызова обхода.
- Обход разрешает ровно один последующий переход фазы без новой проверки. После этого перехода следующая граница требует еще одной проверки или нового обхода.
- Обход никогда не обходит присутствие роли Core, правила консенсуса или шлюзы целостности эскалации.

## Модель эскалации

Эскалация — это остановка с последующим возобновлением. Runtime записывает `EscalationRecord`, устанавливает `phase_state = awaiting-operator`, генерирует событие `escalation.opened` и завершает работу. Сессия является устойчивой; оператор разрешает её в следующем вызове или позволяет сработавшему `timeout_at` автоматически применить `fallback_strategy`.

- Блокировка stdin и фоновый ожидатель отсутствуют.
- `timeout_at` обеспечивается средой выполнения: когда текущее время превышает `timeout_at`, `fallback_strategy` из `EscalationRecord` применяется автоматически без дополнительного ввода оператора (см. `execution-runtime/index.md` §Эскалация Маршрутизация).
- Поверхность отображает `timeout_at` как видимый крайний срок, чтобы оператор мог принять обоснованное решение до автоматической Резолюции.
- Стратегия резервного копирования применяется автоматически по истечении времени; до этого оператор может принять или отклонить запрос в любое время.

## Эскалация Презентация

Оператор должен видеть в одном представлении:

1. Противоречащие друг другу позиции рядом: роль, позиция и резюме по каждому **Объекту обсуждения**.
2. Конкретный запрос: одно решение или один недостающий ввод.
3. Последствия по умолчанию: что произойдет, если ответ не будет дан.
4. Срок: `timeout_at` или явное «без срока».
5. Точка возобновления: точный `resume_phase`.
6. Ссылки на доказательства: артефакты и идентификаторы событий, подтверждающие запрос.

Представление является проекцией `EscalationRecord`; оно никогда не перефразирует запрос через LLM.

## Машина состояний Эскалации

| От | До | Условие |
|------|----|-----------|
| `pending` | `accepted` | Аутентифицированный оператор принимает запрос или предоставляет недостающие данные |
| `pending` | `rejected` | Аутентифицированный оператор отклоняет запрос; применяется резервный вариант |
| `pending` | `superseded` | Более новая эскалация заменяет эту до резолюции |
| `pending` | `expired` | Оператор явно помечает её как истёкшую; никогда не автоматически |
| `accepted` / `rejected` | — | Терминальная; резолюция неизменна после записи |

Каждая запись о переходе фиксирует `operator_id`, `resolved_at` и необязательное примечание. **Резолюция** без соответствующего `escalation_id` имеет код `VAL.003`.

## Привязка и возобновление Резолюции

`council.resolve_escalation` требует `{session_id, escalation_id, decision, note, operator_id}`. Поверхность проверяет, что вызывающий является оператором, а эскалация находится в статусе `pending`.

- Решение привязано к `escalation_id`; его нельзя применить к другой эскалации или сессии.
- `resume_phase` по умолчанию принимает значение записи. Явное переопределение требует указания причины и фиксируется.
- `resume_context` содержит `{phase_id, subject_ids, artifacts, operator_note}` для частичного продолжения; отсутствующие поля означают «продолжить с существующими артефактами».
- При успехе среда выполнения применяет решение, обновляет запись, генерирует событие `escalation.resolved` и продолжает работу с `resume_phase`.

## Уведомления

На поверхности должны отображаться заметные для оператора уведомления, когда происходит любое из следующих событий:

- К параметрам протокола было применено упрощение.
- Резервный вариант был отложен или является лишь рекомендательным.
- Путь быстрого обзора отключен, а полный путь принудительно активирован.
- Документатор Уровня 2+ заблокирован.
- Переопределение `pre_check` было записано.

Уведомления сопоставляются со следующими типами событий в каноническом конверте: `notice.simplification-applied`, `notice.fallback-deferred`, `notice.quick_review_disabled`, `notice.documenter_tier2_interlock`. События предварительной проверки используют `precheck.passed`, `precheck.failed`, `precheck.overridden` и `precheck.unavailable`. Все они отображаются в `council.status` и сохраняются как события, добавляемые только в конец журнала (append-only). Полное соответствие между уведомлениями и событиями:

| Условие уведомления | Тип события |
|------------------|------------|
| Упрощение, примененное к параметрам протокола | `notice.simplification-applied` |
| Отложенное или рекомендательное резервное решение | `notice.fallback-deferred` |
| Путь быстрого обзора отключен, принудительно используется полный путь | `notice.quick_review_disabled` |
| Документатор Уровня 2+ заблокирован | `notice.documenter_tier2_interlock` |
| `pre_check` переопределение записано | `precheck.overridden` |

## Интеграция с Документатором

<!-- STATUS: Только спецификация, до реализации. Не исполняемо, пока не создан Модератор. См. AGENTS.md §1.7 -->

<span style="color:red;font-weight:bold">⚠ ТОЛЬКО СПЕЦИФИКАЦИЯ — НЕ ВЫПОЛНЯЕТСЯ ДО РЕАЛИЗАЦИИ</span> Все инструменты `documenter.*` являются спецификацией; вызовы MCP в настоящее время недоступны. Поверхность оператора интегрируется со службой **Документатор** в соответствии с её контрактом.

Документатор — это Вспомогательный сервис, вызываемый через данную поверхность. Его функции `audit()` и `delegate()` являются инструментами MCP; события и вердикты возвращаются синхронно.

- Корабли уровня 0–1 в MVP: только для чтения, аудит и предпросмотр diff. `documenter.delegate` проверяет `change_type`, `diff` и `audit_id`, затем возвращает предпросмотр без записи.
- Уровень 2+ контролируется политикой (блокировка до тех пор, пока оператор не повысит `active_tier` с помощью валидного `briefing_ref`). При включении `documenter.delegate` возвращает `approval_required` с `approval_id` и хэшем diff; запись не выполняется до получения одобрения.
- Одобрение происходит **вне канала**: оператор вызывает `documenter.approve(approval_id, operator_id)` как отдельный вызов инструмента MCP, отличный от вызова `delegate()`, инициирующего предложение. Утверждающий `operator_id` ДОЛЖЕН отличаться от `actor.id` вызова предложения, чтобы предотвратить самоутверждение.
- `approval_id` — это UUID-v4, возвращаемый `delegate()`. Он привязывает конкретный хэш diff; изменённые diff аннулируют ожидающие одобрения. Одобрение истекает через `approval_expiry_window` минут (по умолчанию 30) — см. policy-reference.md §Field Reference для определения поля.
- `documenter.approve` генерирует событие `documenter.approval` в каноническом envelope с `decision: approved` или `rejected`.

## Доставка событий

События добавляются в файл `sessions/<session_id>/events.jsonl` в виде канонического конверта. Это **единственное место хранения** для всех данных о событиях во всей корпусной системе. Правило для `session_id = null` (аудит Документатор по всему корпусу) следующее: когда `session_id` имеет значение `null`, события добавляются в файл `documenter/corpus-audit/events.jsonl`. Ни один другой путь не является допустимым. Оба пути следуют семантике доставки «хотя бы раз»; потребители устраняют дубликаты по полю `event_id`.

## Обработка ошибок

Ошибки используют реестр, описанный в файле `service-contract/index.md`, и локализуются с помощью таблицы поиска второго уровня. Ответы содержат код, локализованное сообщение и действие оператора. Стек вызовов, необработанные полезной нагрузки провайдеров и секреты никогда не возвращаются оператору.

## Отложенные

CLI Typer, REST-транспорт, параллельный режим, распределённая блокировка, автоматическое истечение срока **Эскалации** и контрольная точка/возобновление в середине **Фазы** (ADR-004). Записи уровня Tier 2+ остаются заблокированными до тех пор, пока не будет реализован и протестирован внешний путь одобрения.
