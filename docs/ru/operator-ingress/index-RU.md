## Область применения

Определяет единственный MVP-транспорт, идентификатор вызывающей стороны, глаголы оператора, шлюз `pre_check`, доставку и возобновление эскалации, вызов документатора, а также доставку событий. Поля артефакта находятся в `service-contract/index.md`; семантика времени выполнения — в `execution-runtime/index.md`.

## Транспорт и точка входа

<span style="color:red;font-weight:bold">⚠ MCP НЕ ЗАРЕГИСТРИРОВАН — ТОЛЬКО stdio</span> В этом разделе описывается контракт транспорта; сервер MCP не зарегистрирован в конфигурации рабочей области (решение оператора). Сессии работают в режиме отката согласно `AGENTS.md` §1.7 до тех пор, пока не станет доступен адаптер **Модератор**.

MVP поставляется с одним транспортом: MCP через stdio. Точка входа оператора (ранее Поверхность оператора) — это адаптер в слое 2: он аутентифицирует вызывающую сторону, проверяет входные данные и обращается к слою 1. Он не содержит логики протокола и не вызывает LLM. CLI и REST остаются отложенными адаптерами над теми же функциями библиотеки.

## Идентификация и авторизация вызывающего абонента

Три класса вызывающих объектов: `operator`, `agent`, `service`.

- AuthN: локальный процесс stdio плюс `COUNCIL_OPERATOR_ID` и `COUNCIL_OPERATOR_TOKEN` из окружения. Поверхность верифицирует токен и никогда не передаёт его в Layer 1.
- AuthZ — отказ по умолчанию. Ошибки аутентификации (неизвестный вызывающий, отсутствующие/недействительные/отозванные учётные данные, истёкший токен) отклоняются согласно кодам ошибок AUTH.* в `operator-ingress/index.md` §Идентичность вызывающего и Авторизация; нарушения структурной схемы остаются `VAL.001`.
- `operator_id` — это человеческий принципал. Принципалы агентов НЕ ДОЛЖНЫ утверждать записи Документатора или разрешать эскалации на этапе MVP.
- Идентичность оператора определена **исключительно** в данном разделе. `operator_id`, который разрешает эскалации (§Привязка Резолюции и Возобновление) и утверждает записи Документатора (`documenter.approve`, `archive/documenter-service/approval-surface.md`), является тем же самым человеческим принципалом, действительным между документами. Ни один другой документ не может определять или расширять, кто считается оператором.

#### Аутентификация (MVP)

Выделяются три класса вызывающих объектов:

| Класс | Тип учетных данных | Область действия | Проверка |
|-------|----------------|-------|--------------|
| `Operator` | Сессия-привязанный подписанный токен | В рамках сессии, оператор идентифицируется префиксом `op-...` (формат `^op-[a-z0-9][a-z0-9-]{2,63}$`) | Подпись проверяется общим модулем аутентификации в пределах Layer 2 |
| `Agent` | Подписанный токен с ограничением по сессии и утверждением о роли | Привязан к session_id и role_id | Подпись и принадлежность к роли проверяются на входе |
| `Service` | Учетные данные сервисного аккаунта с HMAC-подписью | Привязан к имени сервиса и разрешенным операциям | Предварительно зарегистрирован в конфигурации политик; HMAC проверяется на входе |

Структура токена: минимальный формат, похожий на JWT, `{alg, iss, sub, exp}`. Токены агента включают дополнительное утверждение `role`, связывающее субъект с конкретным role_id. Секрет HMAC для общих ключей хранится в файле `archive/documenter-service/policy-reference.md` §Справочник по полям (УСТАРЕЛО, архивировано) под именем `hmac_secret`, по умолчанию принимает значение, предоставленное оператором при запуске. Просроченные токены приводят к ошибке `AUTH.001`. Некорректные подписи приводят к ошибке `AUTH.002`. Неизвестные классы вызывающих сторон приводят к ошибке `AUTH.003`.

Коды ошибок для сбоев аутентификации:
- `AUTH.001` — Истекшие учетные данные. Запросите у вызывающей стороны получить новый токен.
- `AUTH.002` — Неверная подпись или измененный токен. Запишите в журнал и отклоните.
- `AUTH.003` — Нераспознанный класс вызывающей стороны. Проверьте разрешения инструментов MCP или конфигурацию интеграции.
- `AUTH.004` — Отозванные учетные данные (например, выход оператора отзывает все токены агентов из сессии).

## Безопасность и модель угроз (MVP)

<!-- СТАТУС: Описывает реализованный MVP (шаги 0-9 из p3, sess-operator-surface-split). -->

- **Ingress.** Единственная точка входа — локальный JSON-RPC сервер stdio. Аутентификация принудительно выполняется перед любой маршрутизацией глагола; неаутентифицированные запросы получают оболочки AUTH.*, и ни один глагол не выполняется. Только класс вызывающего `operator` может осуществлять правящие глаголы; `agent` и `service` по умолчанию заблокированы согласно таблице разрешений выше. Секрет HMAC берётся из `COUNCIL_OPERATOR_SECRET` (отказ при отсутствии: пропущенный или пустой параметр прерывает запуск).
- **Нет пути записи.** Ветвь записи Tier 2+ недоступна с поверхности (двойная блокировка ADR-013). `documenter.delegate` доступен только для предварительного просмотра; `documenter.override_gate` фиксирует событие переопределения, не вызывая порт Документатор.
- **Sentinel не является активацией.** `documenter/.operator_ingress_ready` — это следствие кода успешного рукопожатия READY; активация остаётся исключительно актом состояния файла политики (ADR-016). Присутствие Sentinel ничего не предоставляет. При использовании механизма overlay готовность политики определяется содержимым файла overlay (scope, `active_tier`, `briefing_ref`), объединяемым с эффективной политикой во время чтения, в то время как sentinel остаётся вторым условием двойной блокировки (ADR-013/ADR-016); базовый файл политики остаётся на базовом уровне Tier 1.
- **Эфемерное состояние.** Реестры эскалации и одобрения находятся в памяти; они теряются при перезапуске. Поверхность сообщает об этом через предупредительное уведомление `notice.fallback-deferred`.
- **Деградация.** Когда `documenter_service` не может быть импортирован, поверхность всё равно запускается; глаголы `documenter.*` возвращают честную оболочку IO.004, указывающую `council.status` как действие резервного варианта; шлюз pre_check возвращает `unavailable`, а submit автоматически продолжается с событием `precheck.unavailable` (ADR-015).
- **Целостность при сбое.** Хранилище сессий молча пропускает некорректные строки в конце файла при холодном старте и игнорирует устаревшие записи намерений; Прямая докатка восстановления откладывается (OD-3).
- **Выходит за рамки MVP (принятые угрозы):** ротация/отзыв общего секретного ключа, защита от повторов и устойчивость корня состояния к изменению откладываются (см. §Deferred).

## Шлюз `pre_check`

### Область применения и точка применения

Шлюз `pre_check` представляет собой проверку целостности артефактов документации перед фиксацией переходов состояния протокола. Он выполняется на уровне 2 (точка входа оператора) в виде синхронного вызова метода `audit(pre_check=true)` у Документатора и возвращает вердикт вызывающей стороне в рамках того же вызова.

- **Область применения:** все манифест-документы, относящиеся к текущей сессии (определяются по `target_id` из активного сценария).
- **Точка применения:** вызывается при каждом переходе между фазами (`2 → 3`, `3 → 4`, `4 → 5`) перед фиксацией состояния новой фазы в слое 1.
- **Переходы с блокировкой:** `2 → 3` (начало обсуждения), `3 → 4` (проверка консенсуса), `4 → 5` (принятие резолюции). Переход разрешён только при вердикте `pass`.
- **Передача вердикта в слой 1:** поверхность записывает результат вердикта (pass/fail/причина) в поле манифеста `pre_check_override` при переопределении или генерирует событие `precheck.failed`; среда выполнения читает это поле/событие при следующей оценке границы и либо продолжает выполнение, либо блокирует его.

### Логика вердикта

| Условие | Вердикт | Действие |
|-----------|---------|--------|
| Нет `high`/`critical` выводов для целевой области | `pass` | Продолжить переход |
| Присутствует любой `high` или `critical` вывод | `fail` | Блокировать переход; сгенерировать событие `precheck.failed` |
| Документатор недоступен (таймаут, сервис не работает) | `unavailable` | Таймаут-и-продолжить: продолжить переход, синхронно сгенерировать предупреждающее событие `precheck.unavailable` (решение по дорожной карте 3); действие применяется только к недоступности, вызванной таймаутом, а не к `fail` целостности реестра |
| Реестр аудита Документатора отсутствует/поврежден/не читается | `fail` | Блокировать переход (fail-closed согласно C-03) |

Таймаут шлюза — это константа, задаваемая на этапе загрузки: по умолчанию 5 секунд, может быть переопределён один раз при запуске с помощью переменной окружения `PRE_CHECK_TIMEOUT`; в течение всего времени жизни процесса значение неизменно. Превышение таймаута приводит к вынесению вердикта `unavailable`. Событие `precheck.running` генерируется при запуске шлюза, что позволяет наблюдателям отличать выполняющуюся проверку от зависшего состояния. (План MVP для Точка входа оператора, этап p3, ADR-015.)

### Документатор недоступен — Режим обхода

Когда Документатор недоступен (вердикт `unavailable`), Модератор MVP НЕ ДОЛЖЕН блокировать выполнение бесконечно. Аутентифицированный вызов `council.override_precheck(reason, operator_id)` может быть выполнен, несмотря на сбой:

- Записи об отмене содержат `reason` (свободный текст, объясняющий, почему шлюз был обойден).
- Отмена записывается в манифест через поле `pre_check_override`.
- Событие `precheck.overridden` синхронно генерируется во время вызова отмены.
- Отмена разрешает ровно один последующий переход фазы без новой проверки. После этого перехода следующая граница требует еще одной проверки или новой отмены.
- Отмена никогда не обходит наличие роли Core, правила консенсуса или шлюзы целостности эскалации.

## Модель **Эскалации**

Эскалация — это остановка с последующим возобновлением. Runtime записывает `EscalationRecord`, устанавливает `phase_state = awaiting-operator`, генерирует событие `escalation.opened` и завершает работу. Сессия является долговременной; оператор разрешает её в последующем вызове или позволяет срабатыванию `timeout_at` автоматически применить `fallback_strategy`.

- Не блокировать stdin и не использовать фоновый ожидатель.
- `timeout_at` обеспечивается средой выполнения: когда текущее время превышает `timeout_at`, `fallback_strategy` из `EscalationRecord` применяется автоматически без дальнейшего ввода оператора (см. `execution-runtime/index.md` §Эскалация Маршрутизация).
- Поверхность отображает `timeout_at` как видимый крайний срок, чтобы оператор мог принять обоснованное решение до автоматической резолюции.
- Стратегия резервного варианта применяется автоматически по истечении времени; до этого оператор может принять или отклонить запрос в любое время.

## Презентация Эскалации

Оператор должен видеть в одном представлении:

1. Противоречащие друг другу позиции рядом: роль, позиция и резюме по каждому объекту обсуждения.
2. Конкретный запрос: одно решение или один недостающий ввод.
3. Последствия в случае отказа: что произойдёт, если не будет дан ответ.
4. Срок: `timeout_at` или явное «без срока».
5. Точка возобновления: точный `resume_phase`.
6. Ссылки на доказательства: артефакты и идентификаторы событий, подтверждающие запрос.

Представление является проекцией `EscalationRecord`; оно никогда не перефразирует запрос через LLM.

## Машина состояний Эскалации

| От | До | Условие |
|------|----|-----------|
| `pending` | `accepted` | Аутентифицированный оператор принимает запрос или предоставляет недостающие данные |
| `pending` | `rejected` | Аутентифицированный оператор отклоняет запрос; применяется резервный вариант |
| `pending` | `superseded` | Более новая Эскалация заменяет эту до Резолюции |
| `pending` | `expired` | Оператор явно помечает её как истёкшую; никогда не автоматически |
| `accepted` / `rejected` | — | Терминальный; Резолюция неизменна после записи |

Каждая запись перехода фиксирует `operator_id`, `resolved_at` и необязательную заметку. **Резолюция** без соответствующего `escalation_id` является `VAL.003`.

## Привязка разрешения и возобновление

`council.resolve_escalation` требует `{session_id, escalation_id, decision, note, operator_id}`. Поверхность проверяет, что вызывающий является оператором, а эскалация находится в статусе `pending`.

- Решение привязано к `escalation_id`; его нельзя применить к другой эскалации или сессии.
- `resume_phase` по умолчанию принимает значение записи. Явное переопределение требует указания причины и фиксируется.
- `resume_context` содержит `{phase_id, subject_ids, artifacts, operator_note}` для частичного продолжения; отсутствующие поля означают «продолжить с существующими артефактами».
- В случае успеха среда выполнения применяет решение, обновляет запись, генерирует событие `escalation.resolved` и продолжает выполнение с `resume_phase`.

## Уведомления

На поверхности ОБЯЗАТЕЛЬНО должны отображаться заметные для оператора уведомления при возникновении любого из следующих событий:

- К параметрам протокола было применено упрощение.
- Отказной вариант был отложен или носит исключительно рекомендательный характер.
- Путь быстрого обзора отключен, а полный путь принудительно активирован.
- Документатор Уровня 2+ заблокирован.
- Переопределение `pre_check` было зафиксировано.
- Состояние Активационного оверлея изменилось — см. ниже `notice.activation_active` и `notice.activation_invalid`.

Уведомления сопоставляются со следующими типами событий в каноническом конверте: `notice.simplification-applied`, `notice.fallback-deferred`, `notice.quick_review_disabled`, `notice.documenter_tier2_interlock`, `notice.activation_active`, `notice.activation_invalid`. События предварительной проверки используют `precheck.passed`, `precheck.failed`, `precheck.overridden` и `precheck.unavailable`. Все они отображаются в `council.status` и сохраняются как события, допускающие только добавление. Полное соответствие между уведомлениями и событиями:

| Условие уведомления | Тип события |
|------------------|------------|
| Упрощение применено к параметрам протокола | `notice.simplification-applied` |
| Отложенный или рекомендательный режим резервного варианта | `notice.fallback-deferred` |
| Путь быстрого обзора отключен, принудительно используется полный путь | `notice.quick_review_disabled` |
| Документатор Уровня 2+ заблокирован | `notice.documenter_tier2_interlock` |
| `pre_check` переопределение записано | `precheck.overridden` |
| Активационный оверлей присутствует, действителен и активен (состояние `active`) | `notice.activation_active` |
| Активационный оверлей присутствует, но недействителен, отказ в закрытом режиме (состояние `invalid`) | `notice.activation_invalid` |

## Доставка событий

События добавляются в файл `sessions/<session_id>/events.jsonl` в виде канонического конверта. Это **единственное место хранения** для всех данных о событиях во всем корпусе. Правило для `session_id = null` (аудит Документатора во всем корпусе) следующее: когда `session_id` равен `null`, события добавляются в файл `documenter/corpus-audit/events.jsonl`. Ни один другой путь не является допустимым. Оба пути следуют семантике доставки «хотя бы раз»; потребители устраняют дубликаты по `event_id`.

## Обработка ошибок

Ошибки используют реестр, описанный в `service-contract/index.md`, и локализуются с помощью таблицы поиска Layer 2. Ответы содержат код, локализованное сообщение и действие оператора. Стек вызовов, необработанные полезны данные провайдера и секреты никогда не возвращаются оператору.

## Отложенный

Отложенные элементы (A10, p2 roadmap; источник: список вне диапазона p3 impl-plan): прямая докатка при восстановлении после сбоя (OD-3); полная таксономия ошибок; Typer CLI и REST transport; параллельный режим и распределённая блокировка; автоматическое истечение срока эскалации; контрольная точка/возобновление в середине фазы (ADR-004); ротация и отзыв общего секрета (roadmap SUBJ-003); классы вызывающих объектов Agent и Service; реальные адаптеры Layer 1 / Модератор; `council.get_artifacts` (единственный оставшийся отложенный инструмент поверхности, roadmap KD-1). Записи уровня Tier 2+ не отложены, а **ограничены**: ветка записи реализована и находится в состоянии «реализовано, не активировано» за двойным блокиратором ADR-013, активируемым оператором только вне сессии.
