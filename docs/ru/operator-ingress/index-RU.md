## Область применения

Определяет единственный MVP-транспорт, идентификатор вызывающего, глаголы оператора, шлюз `pre_check`, доставку и возобновление эскалации, вызов документатора, а также доставку событий. Поля артефакта находятся в `service-contract/index.md`; семантика времени выполнения — в `execution-runtime/index.md`.

## Транспорт и точка входа

<span style="color:red;font-weight:bold">⚠ MCP НЕ ЗАРЕГИСТРИРОВАН — ТОЛЬКО stdio</span> В этом разделе описывается контракт транспорта; сервер MCP не зарегистрирован в конфигурации рабочей области (решение оператора). Сессии работают в режиме отката согласно `AGENTS.md` §1.7 до тех пор, пока не станет доступен адаптер Модератор.

MVP поставляется с одним транспортом: MCP поверх stdio. Точка входа оператора (ранее — Operator Surface) представляет собой адаптер в слое 2: он аутентифицирует вызывающую сторону, проверяет входные данные и вызывает функции слоя 1. Он не содержит логики протокола и не вызывает LLM. CLI и REST остаются отложенными адаптерами над теми же библиотечными функциями.

## Идентификация и авторизация вызывающего абонента

Три класса вызывающих объектов: `operator`, `agent`, `service`.

- AuthN: локальный процесс stdio плюс `COUNCIL_OPERATOR_ID` и `COUNCIL_OPERATOR_TOKEN` из окружения. Поверхность проверяет токен и никогда не пересылает его в Layer 1.
- AuthZ — отказ по умолчанию. Ошибки аутентификации (неизвестный вызывающий, отсутствующие/недействительные/отозванные учётные данные, истёкший токен) отклоняются согласно кодам ошибок AUTH.* в `operator-ingress/index.md` §Идентификация и авторизация вызывающего; нарушения структурной схемы остаются `VAL.001`.
- `operator_id` — это человеческий принципал. Принципалы агентов НЕ ДОЛЖНЫ одобрять записи Документатора или разрешать эскалации на этапе MVP.
- Идентичность оператора определена **исключительно** в этом разделе. `operator_id`, который разрешает эскалации (§Привязка и возобновление резолюции) и одобряет записи Документатора (`documenter.approve`, `archive/documenter-service/approval-surface.md`), — это тот же самый человеческий принципал, действительный между документами. Ни один другой документ не может определять или расширять, кто считается оператором.

#### Аутентификация (MVP)

Выделяются три класса вызывающих объектов:

| Класс | Тип учетных данных | Область действия | Проверка |
|-------|----------------|-------|--------------|
| `Operator` | Подписанный токен, привязанный к сессии | В рамках сессии, оператор идентифицируется префиксом `op-...` (формат `^op-[a-z0-9][a-z0-9-]{2,63}$`) | Подпись проверяется общим модулем аутентификации в пределах Layer 2 |
| `Agent` | Подписанный токен с областью действия сессии и утверждением о роли | Привязан к session_id и role_id | Подпись и принадлежность к роли проверяются на входе |
| `Service` | Учетные данные сервисного аккаунта с HMAC-подписью | Привязаны к имени сервиса и разрешенным операциям | Предварительно зарегистрированы в конфигурации политик; HMAC проверяется на входе |

Структура токена: минимальный формат, похожий на JWT, `{alg, iss, sub, exp}`. Токены агента включают дополнительное утверждение `role`, связывающее субъект с конкретным role_id. Секрет HMAC для общих ключей хранится в файле `archive/documenter-service/policy-reference.md` §Field Reference (SUPERSEDED, в архиве) под именем `hmac_secret`, по умолчанию принимает значение, предоставленное оператором при запуске. Просроченные токены приводят к ошибке `AUTH.001`. Некорректные подписи приводят к ошибке `AUTH.002`. Неизвестные классы вызывающих объектов приводят к ошибке `AUTH.003`.

Коды ошибок для сбоев аутентификации:
- `AUTH.001` — Истекшие учетные данные. Запросите у вызывающей стороны получить новый токен.
- `AUTH.002` — Недействительная подпись или измененный токен. Журналируйте и отклоняйте.
- `AUTH.003` — Нераспознанный класс вызывающей стороны. Проверьте разрешения инструментов MCP или конфигурацию интеграции.
- `AUTH.004` — Отозванные учетные данные (например, выход оператора отзывает все токены агентов из сессии).

## Безопасность и модель угроз (MVP)

<!-- СТАТУС: Описывает реализованный MVP (шаги 0-9 p3, sess-operator-surface-split). -->

- **Ingress.** Единственная точка входа — локальный JSON-RPC сервер stdio. Аутентификация обеспечивается перед выполнением любого маршрута глагола; неаутентифицированные запросы получают оболочки AUTH.*, и ни один глагол не выполняется. Только класс вызывающего `operator` может осуществлять правящие глаголы; `agent` и `service` по умолчанию заблокированы согласно таблице разрешений выше. Секрет HMAC берётся из `COUNCIL_OPERATOR_SECRET` (отказ при отсутствии: пропущенный или пустой параметр прерывает запуск).
- **Нет пути записи.** Ветвь записи Tier 2+ недоступна с поверхности (двойная блокировка ADR-013). `documenter.delegate` доступен только для предварительного просмотра; `documenter.override_gate` фиксирует событие переопределения, не вызывая порт Документатор.
- **Sentinel не является активацией.** `documenter/.operator_ingress_ready` — это следствие кода успешного рукопожатия READY; активация остаётся актом состояния политики/блокировки (ADR-016). При использовании runtime activation overlay готовность по политике определяется эффективной слитой политикой (overlay `scope`/`active_tier`/`briefing_ref`), в то время как sentinel остаётся вторым условием блокировки (ADR-013/ADR-016); базовая политика остаётся базовой линией Tier 1. Присутствие sentinel само по себе не предоставляет активацию.
- **Непостоянное состояние.** Реестры эскалации и одобрения находятся в памяти; они теряются при перезапуске. Поверхность сообщает об этом через предупреждающее уведомление `notice.fallback-deferred`.
- **Деградация.** Когда `documenter_service` недоступен для импорта, поверхность всё равно запускается; глаголы `documenter.*` возвращают честную оболочку IO.004 с указанием `council.status` как действия по умолчанию; шлюз pre_check возвращает `unavailable`, а отправка автоматически продолжается с событием `precheck.unavailable` (ADR-015).
- **Целостность при сбое.** Хранилище сессий молча пропускает некорректные завершающие строки при холодном старте и игнорирует устаревшие записи намерений; прямая докатка восстановления откладывается (OD-3).
- **Выходит за рамки MVP (угрозы приняты):** ротация/аннулирование общего секрета, защита от повторов и устойчивость корня состояния к подделке откладываются (см. §Deferred).

## Шлюз `pre_check`

### Область применения и точка применения

Шлюз `pre_check` представляет собой проверку целостности артефактов документации перед фиксацией переходов состояния протокола. Он выполняется на уровне 2 (точка входа оператора) как синхронный вызов метода `audit(pre_check=true)` у Документатора и возвращает вердикт вызывающей стороне в рамках того же вызова.

- **Область действия:** все манифест-документы, относящиеся к текущей сессии (определяются по `target_id` из активного сценария).
- **Точка принудительного применения:** вызывается при каждом переходе между фазами (`2 → 3`, `3 → 4`, `4 → 5`) перед фиксацией нового состояния фазы в слое 1.
- **Переходы с контролем:** `2 → 3` (начало обсуждения), `3 → 4` (проверка консенсуса), `4 → 5` (принятие резолюции). Переход разрешён только при вердикте `pass`.
- **Передача вердикта в слой 1:** поверхность записывает результат вердикта (pass/fail/причина) в поле манифеста `pre_check_override` при переопределении или генерирует событие `precheck.failed`; среда выполнения считывает это поле/событие при следующей оценке границы и либо продолжает выполнение, либо блокирует его.

### Логика вынесения приговора

| Условие | Вердикт | Действие |
|-----------|---------|--------|
| Нет `high`/`critical` выводов для целевой области | `pass` | Продолжить переход |
| Присутствует любой `high` или `critical` вывод | `fail` | Блокировать переход; сгенерировать событие `precheck.failed` |
| Документатор недоступен (тайм-аут, сервис не работает) | `unavailable` | Тайм-аут и продолжить: продолжить переход, синхронно сгенерировать предупреждающее событие `precheck.unavailable` (решение по дорожной карте 3); действие применяется только к недоступности, вызванной тайм-аутом, а не к `fail` целостности реестра |
| Реестр аудита Документатора отсутствует/поврежден/не читается | `fail` | Блокировать переход (fail-closed согласно C-03) |

Таймаут шлюза — это константа, устанавливаемая на этапе загрузки: по умолчанию 5 секунд, может быть переопределён один раз при запуске с помощью переменной окружения `PRE_CHECK_TIMEOUT`; в течение всего времени жизни процесса она неизменна. Превышение таймаута приводит к вынесению вердикта `unavailable`. При запуске шлюза генерируется событие `precheck.running`, что позволяет наблюдателям отличать выполняющуюся проверку от зависшего состояния. (План MVP для Точка входа оператора, этап p3, ADR-015.)

### Документатор недоступен — Режим переопределения

Когда Документатор недоступен (вердикт `unavailable`), Модератор MVP НЕ ДОЛЖЕН блокировать операцию бесконечно. Аутентифицированный вызов `council.override_precheck(reason, operator_id)` может быть выполнен, несмотря на сбой:

- Записи обхода содержат `reason` (свободный текст, объясняющий, почему шлюз был обойден).
- Запись обхода записывается в манифест через поле `pre_check_override`.
- Событие `precheck.overridden` синхронно генерируется во время вызова обхода.
- Обход разрешает ровно один последующий переход фазы без новой проверки. После этого перехода следующий рубеж требует еще одной проверки или нового обхода.
- Обход никогда не обходит присутствие роли Core, правила консенсуса или шлюзы целостности эскалации.

## Модель эскалации

Эскалация — это остановка и возобновление. Runtime записывает `EscalationRecord`, устанавливает `phase_state = awaiting-operator`, генерирует событие `escalation.opened` и завершает работу. Сессия является долговременной; оператор разрешает её в следующем вызове или позволяет сработавшему `timeout_at` автоматически применить `fallback_strategy`.

- Блокировка stdin и фоновый ожидатель отсутствуют.
- `timeout_at` обеспечивается средой выполнения: когда текущее время превышает `timeout_at`, `fallback_strategy` из `EscalationRecord` применяется автоматически без дополнительного ввода оператора (см. `execution-runtime/index.md` §Эскалация Маршрутизация).
- Точка входа отображает `timeout_at` как видимый крайний срок, чтобы оператор мог принять обоснованное решение до автоматической Резолюции.
- Стратегия резервного копирования применяется автоматически по истечении времени ожидания; до этого момента оператор может принять или отклонить запрос в любое время.

## Эскалация Презентация

Оператор должен видеть в одном представлении:

1. Конфликтующие позиции рядом: роль, позиция и резюме по каждому объекту обсуждения.
2. Конкретный запрос: одно решение или один недостающий ввод.
3. Последствия по умолчанию: что произойдет, если ответ не будет дан.
4. Срок: `timeout_at` или явное «без срока».
5. Точка возобновления: точный `resume_phase`.
6. Ссылки на доказательства: артефакты и идентификаторы событий, подтверждающие запрос.

Представление является проекцией `EscalationRecord`; оно никогда не перефразирует запрос через LLM.

## Машина состояний Эскалации

| От | До | Условие |
|------|----|-----------|
| `pending` | `accepted` | Аутентифицированный оператор принимает запрос или предоставляет недостающие данные |
| `pending` | `rejected` | Аутентифицированный оператор отклоняет запрос; применяется резервный вариант |
| `pending` | `superseded` | Более новая эскалация заменяет эту до резолюции |
| `pending` | `expired` | Оператор явно помечает её как истёкшую; никогда не автоматически |
| `accepted` / `rejected` | — | Терминальная; резолюция неизменна после записи |

Каждая запись о переходе фиксирует `operator_id`, `resolved_at` и необязательное примечание. **Резолюция** без соответствующего `escalation_id` является `VAL.003`.

## Привязка разрешения и возобновление Резолюция

`council.resolve_escalation` требует `{session_id, escalation_id, decision, note, operator_id}`. Точка входа проверяет, что вызывающий является оператором, а эскалация находится в статусе `pending`.

- Решение привязано к `escalation_id`; его нельзя применить к другой эскалации или сессии.
- `resume_phase` по умолчанию принимает значение записи. Явное переопределение требует указания причины и фиксируется.
- `resume_context` содержит `{phase_id, subject_ids, artifacts, operator_note}` для частичного продолжения; отсутствующие поля означают «продолжить с существующими артефактами».
- В случае успеха среда выполнения применяет решение, обновляет запись, генерирует событие `escalation.resolved` и продолжает выполнение с `resume_phase`.

## Уведомления

Точка входа оператора ОБЯЗАННА отображать заметные для оператора уведомления, когда происходит любое из следующих событий:

- К параметрам протокола было применено упрощение.
- Резервный вариант был отложен или носит только рекомендательный характер.
- Путь быстрого обзора отключен, а полный путь принудительно активирован.
- Документатор Уровня 2+ заблокирован.
- Переопределение `pre_check` было записано.
- Активационный overlay присутствует, валиден и эффективен (состояние активации `active`).
- Активационный overlay присутствует, но невалиден (fail-closed, состояние активации `invalid`).

Уведомления сопоставляются со следующими типами событий в каноническом конверте: `notice.simplification-applied`, `notice.fallback-deferred`, `notice.quick_review_disabled`, `notice.documenter_tier2_interlock`, `notice.activation_active`, `notice.activation_invalid`. События предварительной проверки используют `precheck.passed`, `precheck.failed`, `precheck.overridden` и `precheck.unavailable`. Все они отображаются в `council.status` и сохраняются как события, добавляемые только в конец (append-only). Типы уведомлений активации специфицированы для диагностики активации; эмиссия в runtime Operator Ingress следует реализации. Полное отображение уведомлений на события:

| Условие уведомления | Тип события |
|------------------|------------|
| Упрощение, примененное к параметрам протокола | `notice.simplification-applied` |
| Отложенное или рекомендательное резервное решение | `notice.fallback-deferred` |
| Путь быстрого обзора отключен, принудительно используется полный путь | `notice.quick_review_disabled` |
| Документатор Уровня 2+ заблокирован | `notice.documenter_tier2_interlock` |
| Активационный overlay активен и эффективен (состояние `active`) | `notice.activation_active` |
| Активационный overlay присутствует, но невалиден, fail-closed (состояние `invalid`) | `notice.activation_invalid` |
| `pre_check` переопределение записано | `precheck.overridden` |

## Доставка событий

События добавляются в файл `sessions/<session_id>/events.jsonl` в виде канонического конверта. Это **единственное место хранения** для всех данных о событиях в рамках всего корпуса. Правило для `session_id = null` (аудит Документатор в масштабах всего корпуса): когда `session_id` равно `null`, события добавляются в файл `documenter/corpus-audit/events.jsonl`. Ни один другой путь не является допустимым. Оба пути следуют семантике доставки «хотя бы раз»; потребители устраняют дубликаты по полю `event_id`.

## Обработка ошибок

Ошибки используют реестр, описанный в `service-contract/index.md`, и локализованы через таблицу поиска уровня 2. Ответы содержат код, локализованное сообщение и действие оператора. Трассировки стека, необработанные полезной нагрузки провайдеров и секреты никогда не возвращаются оператору.

## Отложенный

Отложенные элементы (A10, p2 roadmap; источник: список вне диапазона p3 impl-plan): прямая докатка при восстановлении после сбоя (OD-3); полная таксономия ошибок; Typer CLI и REST transport; параллельный режим и распределённая блокировка; автоматическое истечение срока эскалации; контрольная точка/возобновление в середине фазы (ADR-004); ротация и отзыв общего секретного ключа (roadmap SUBJ-003); классы вызывающих объектов Agent и Service; реальные адаптеры Layer 1 / Модератор; `council.get_artifacts` (единственный оставшийся отложенный инструмент точки входа, roadmap KD-1). Записи уровня Tier 2+ не отложены, а **ограничены**: ветка записи реализована и спит за двойным блокиратором ADR-013, активация возможна оператором только вне сессии.
