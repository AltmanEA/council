## Реестр кодов ошибок

| Код | Значение | Действия оператора |
|------|---------|-----------------|
| `VAL.001` | Нарушение схемы или неизвестное поле | Исправить запрос |
| `VAL.002` | Неизвестное значение перечисления | Исправить запрос |
| `VAL.003` | Отсутствует обязательное поле | Исправить запрос |
| `VAL.004` | Несоответствие базового уровня доверия | Повторить попытку на уровне или выше вычисленного порога |
| `VAL.005` | Отсутствует, устарел или вне области действия токен аудита | Повторно запустить `audit()` |
| `PROT.001` | Отсутствует роль Core | Эскалировать |
| `PROT.002` | Неверный формат статуса роли | Эскалировать |
| `PROT.003` | Нарушение правила консенсуса | Эскалировать |
| `PROT.004` | Неверный переход фазы | Повторить попытку; эскалировать, если проблема сохраняется |
| `PROT.005` | Присутствует блокирующий вывод | Устранить вывод, повторить аудит |
| `PROT.006` | Истекло время ожидания одобрения оператора | Возобновить или отменить |
| `PROT.007` | Не пройдена контрольная точка целостности предварительной проверки | Блокировать выполнение; запустить аудит или запросить разрешение |
| `MODEL.001` | Лимит скорости провайдера | Повторить попытку |
| `MODEL.002` | Ошибка аутентификации провайдера | Исправить конфигурацию |
| `MODEL.003` | Тайм-аут провайдера | Повторить попытку |
| `IO.001` | Не удалось выполнить атомарную запись | Повторить попытку |
| `IO.002` | Разорвана цепочка хэшей манифеста | Эскалировать |
| `IO.003` | Удерживается блокировка сессии | Подождать, затем повторить попытку |
| `IO.004` | Сбой делегированного навыка | Проверить трассировку, повторить попытку |
| `CONFIG.001` | Отсутствует ключ API | Исправить конфигурацию |
| `CONFIG.002` | Неверный сценарий или конфликтующая конфигурация | Исправить конфигурацию |
| `AUTH.001` | Истекли учетные данные | Исправить запрос |
| `AUTH.002` | Неверная подпись / подделанный токен | Исправить учетные данные |
| `AUTH.003` | Нераспознанный класс вызывающего объекта | Исправить конфигурацию MCP или интеграции |
| `AUTH.004` | Отозванные учетные данные | Повторно аутентифицироваться |
| `PROT.GATE.001` | Сбой контрольной точки предварительной проверки или предварительного аудита, требующий разрешения | Записать разрешение через `documenter.override_gate(reason, operator_id)` и повторить попытку |
| `PROT.008` | Контрольная точка целостности предварительной проверки недоступна (Документатор недостижим) | Блокировать переход; запросить `council.override_precheck` |
| `IO.999` | Необработанное исключение во время выполнения делегата() | Зафиксировать трассировку после инцидента (процедура трассировки находилась в упразднённом Протоколе безопасности v0.x, ныне в архиве), эскалировать |

Документатор сопоставление: `hash_mismatch` → `IO.002`; `trust_mismatch` → `VAL.004`; `audit_mismatch` → `VAL.005`; `blocking_finding` → `PROT.005`; `skill_failure` → `IO.004`; `operator_timeout` → `PROT.006`; `gate_failure` → `PROT.GATE.001`; `unknown` → `IO.999`.

## Приоритет конфигурации

От высшего к низшему: (1) явное значение запроса MCP; (2) файл сценария; (3) `documenter_policy.yml` для операций Документатора; (4) `defaults/policy.yaml`; (5) встроенные безопасные замечания по умолчанию. Файл маппера схем не поставляется на этапе MVP — `schema_versions.json`, упомянутый в предыдущих черновиках, явно зарезервирован, но не используется во время выполнения согласно ADR-005 (§Версионирование схем). Конфликт между сценарием и политикой по параметру безопасности является ошибкой `CONFIG.002`, а не тихим победителем.

## Версионирование схемы

`schema_version` зарезервировано и зафиксировано на значении `1` для MVP. Неизвестные версии отклоняются с кодом `VAL.001`. В составе MVP не поставляется ни одна цепочка миграций; данное поле существует, чтобы цепочку можно было добавить без изменения идентичности **Артефакт**. Любая будущая миграция ОБЯЗАНА сохранять прозрачность списка, критичного для понижения версии. Файл `schema_versions.json`, упомянутый в предыдущих черновиках, **не поставляется в составе MVP** — он явно зарезервирован (для использования вне времени выполнения) для принятия решения о миграции после MVP в соответствии с ADR-005. Производители НЕ ДОЛЖНЫ генерировать события, ссылающиеся на него; потребители ДОЛЖНЫ игнорировать его, если он присутствует.

## Процесс проверки критических выводов

Валидация следует строгому трехфазному конвейеру. Каждая **Фаза** работает с исходным текстом, а ее результаты передаются в следующую:

1. **Принятие схемы.** Структура артефакта проверяется только на соответствие схеме JSON (наличие обязательных полей, корректные типы, известные имена полей). Поле `justification` на этом этапе НЕ является обязательным независимо от уровня серьёзности; отсутствие обоснования не блокирует подачу заявки (`VAL.003` не выдаётся за отсутствие `justification`). Несоответствие схеме полностью блокирует подачу заявки (`VAL.001`).
2. **Понижение протокола.** Если вывод имеет `severity = critical`, модератор проверяет, проходит ли обоснование проверку формата (непустая строка, называющая как минимум один конкретный режим отказа или сценарий атаки И ссылающаяся как минимум на один идентификатор объекта из списка объектов задачи). Корректное обоснование → уровень серьёзности остаётся `critical`. Некорректное или отсутствующее обоснование → уровень серьёзности понижается до `high` для целей протокола. Исходный объект вывода сохраняется без изменений в журнале прозрачности.
3. **Журнал прозрачности.** Каждый вывод с уровнем critical или пониженным уровнем логируется вместе с его исходным уровнем серьёзности, фактическим уровнем серьёзности (после понижения) и результатом проверки. Этот журнал отображается в документе резолюции и доступен оператору. Никакие изменения исходного текста не вносятся на этапах 1 или 2.

### Золотые матчи

Золотые тестовые данные находятся в файле `tests/fixtures/contracts/golden_test_cases.yaml`. Каждый тестовый набор определяет конкретный полезный груз для проверки на соответствие каноническим схемам (`service-contract/index.md` §Схемы Артефактов) и кодам ошибок (§Реестр кодов ошибок). Перед написанием кода для уровня 0 заполните поле `input_payload` конкретными данными в формате JSON/YAML, соответствующими схеме Артефакта, и установите `validation_codes` согласно таблице ниже.

#### Матрица тестирования оборудования

| Идентификатор матча | Ожидаемый результат | коды проверки |
|-----------|------------------|------------------|
| `critical-without-justification` | Уровень серьёзности понижен с `critical` до `high`; создана запись о прозрачности; исходный текст сохранён | `[VAL.001]` (проверка схемы проходит — обоснование больше не требуется на этапе MVP) |
| `absent_vs_null_stance` | Различное толкование: absent = объект обсуждения не затронут ролью; null = роль затронула объект обсуждения, но не имеет позиции | `[VAL.003]` |
| `support_oppose_disagreement` | Обнаружено расхождение; `ConsensusVerdict.outcome = no-consensus` | `[PROT.003]` |
| `invalid_format_status` | extraction = `invalid-format` → сессия переходит в `blocked-escalation` с `information-gap` | `[PROT.002]` |
| `missing_core_role` | Отсутствует Core роль → `blocked-escalation` с `risk-threshold-breach` | `[PROT.001]` |
| `manifest_hash_break` | Проверка целостности хеш-цепочки не пройдена | `[IO.002]` |
| `documenter_error_category_mapping` | Каждая категория ошибок Документатора детерминированно сопоставляется с одним кодом реестра | См. таблицу сопоставления ниже |

#### Категория ошибок Документатора → Маппинг реестра (предзаполнено для уровня 0)

| категория ошибки | Код реестра | Описание |
|---------------|--------------|-------------|
| `hash_mismatch` | `IO.002` | Разрыв цепочки хэшей манифеста |
| `trust_mismatch` | `VAL.004` | Несовпадение базового уровня доверия |
| `audit_mismatch` | `VAL.005` | Отсутствует/истек срок действия/вне области действия токента аудита |
| `blocking_finding` | `PROT.005` | Присутствует блокирующий вывод |
| `skill_failure` | `IO.004` | Сбой делегированного навыка |
| `operator_timeout` | `PROT.006` | Истекло время ожидания одобрения оператора |
| `gate_failure` | `PROT.GATE.001` | Сбой шлюза предварительной проверки/аудита, требующий обхода |
| `unknown` | `IO.999` | Необработанное исключение во время выполнения делегата() |

Каждая запись должна быть проверена путем внедрения соответствующего error_category в событие документатора и подтверждения того, что сгенерированный код реестра точно совпадает. Дублирование отображений запрещено.
