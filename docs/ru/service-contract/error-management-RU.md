| `VAL.001` | Нарушение схемы или неизвестное поле | Исправить запрос |
| `VAL.002` | Неизвестное значение перечисления | Исправить запрос |
| `VAL.003` | Отсутствует обязательное поле | Исправить запрос |

| `VAL.005` | Аудиторский токен отсутствует, устарел или вне области | Повторно запустить `audit()` |

| `PROT.002` | Неверный формат статуса роли | Эскалировать |
| `PROT.003` | Нарушение правила консенсуса | Эскалировать |

| `MODEL.002` | Ошибка аутентификации провайдера | Исправить конфигурацию |
| `MODEL.003` | Таймаут провайдера | Повторить попытку |

| `CONFIG.002` | Неверный сценарий или конфликтующая конфигурация | Исправить конфигурацию |
| `AUTH.001` | Истёкшие учётные данные | Исправить запрос |
| `AUTH.002` | Неверная подпись / изменённый токен | Исправить учётные данные |
| `AUTH.003` | Нераспознанный класс вызывающего | Исправить конфигурацию MCP или интеграции |
| `AUTH.004` | Отозванные учётные данные | Повторная аутентификация |
| `PROT.GATE.001` | Сбой контрольной или предварительной проверки, требующий отмены | Зафиксировать отмену через `documenter.override_gate(reason, operator_id)` и повторить попытку |
| `PROT.008` | Контрольная проверка целостности недоступна (Documenter недостижим) | Остановить переход; запросить `council.override_precheck` |
| `IO.999` | Необработанное исключение во время выполнения delegate() | Захватить трассировку после инцидента (§Протокол безопасности #8), эскалировать |

Отображение Documenter: `hash_mismatch` → `IO.002`; `trust_mismatch` → `VAL.004`; `audit_mismatch` → `VAL.005`; `blocking_finding` → `PROT.005`; `skill_failure` → `IO.004`; `operator_timeout` → `PROT.006`; `gate_failure` → `PROT.GATE.001`; `unknown` → `IO.999`.

## Приоритет конфигурации

От высшего к низшему: (1) явное значение запроса MCP; (2) файл сценария; (3) `documenter_policy.yml` для операций Documenter; (4) `defaults/policy.yaml`; (5) встроенные значения по умолчанию с высоким уровнем безопасности. Файл внешнего маппера схемы не поставляется на этапе MVP — `schema_versions.json`, упоминаемый в предыдущих черновиках, явно зарезервирован, но не используется во время выполнения согласно ADR-005 (§Версионирование схем). Конфликт между сценарием и политикой по параметру безопасности является `CONFIG.002`, никогда не происходит тихого победителя.

## Версионирование схем

`schema_version` зарезервирован и зафиксирован на уровне `1` для MVP. Неизвестные версии отклоняются с `VAL.001`. Цепочка миграции не поставляется на этапе MVP; поле существует, чтобы цепочка могла быть добавлена без изменения идентичности артефакта. Любая будущая миграция ОБЯЗАНА сохранять список критической прозрачности пониженной версии. Файл `schema_versions.json`, упомянутый в предыдущих черновиках, **не поставляется на этапе MVP** — он явно зарезервирован (не во время выполнения) для решения пост-MVP миграции согласно ADR-005. Производители НЕ ДОЛЖНЫ генерировать события, ссылающиеся на него; потребители ДОЛЖНЫ игнорировать его, если он присутствует.

## Процесс валидации критических выявлений

Валидация строго следует трёхфазному конвейеру. Каждая фаза работает с исходным текстом, и её выводы передаются в следующую:

1. **Принятие схемы.** Структура артефакта валидируется только по JSON-схеме (обязательные поля присутствуют, правильные типы, известные имена полей). Поле `justification` НЕ требуется на этом этапе, независимо от серьёзности; отсутствие `justification` не блокирует подачу (`VAL.003` не выдаётся для отсутствующей `justification`). Недействительная схема полностью блокирует подачу (`VAL.001`).
2. **Протокольное понижение.** Если выявление имеет `severity = critical`, модератор проверяет, проходит ли обоснование проверку формата (непустая строка, называющая хотя бы одну конкретную модель отказа или сценарий атаки И ссылающаяся хотя бы на один идентификатор субъекта из списка задач субъекта). Действительное обоснование → серьёзность остаётся `critical`. Недействительное или отсутствующее обоснование → серьёзность понижается до `high` для протокольных целей. Исходный объект выявления сохраняется неизменным в записи прозрачности.
3. **Запись прозрачности.** Каждое критическое или пониженное выявление регистрируется с указанием исходной серьёзности, эффективной серьёзности (после понижения) и результата валидации. Этот журнал появляется в документе разрешения и виден оператору. Никакие изменения исходного текста не происходят на фазах 1 или 2.

### Золотые фикстуры

Золотые фикстуры расположены в `tests/fixtures/contracts/golden_test_cases.yaml`. Каждая фикстура определяет конкретный полезный нагрузок для валидации против канонических схем (§Схемы артефактов) и кодов ошибок (§Реестр кодов ошибок). До начала кодирования Layer 0 заполнить поле `input_payload` конкретным JSON/YAML, соответствующим схеме артефакта, и установить `validation_codes` согласно таблице ниже.

#### Матрица тестирования фикстур

| ID фикстуры | Ожидаемый результат | validation_codes |
|-------------|---------------------|------------------|
| `critical-without-justification` | Серьёзность понижена с `critical` до `high`; создана запись прозрачности; исходный текст сохранён | `[VAL.001]` (принятие схемы проходит — обоснование больше не требуется на MVP) |
| `absent_vs_null_stance` | Различная интерпретация: absent = субъект не рассмотрен ролью; null = роль рассмотрела субъекта, но не имеет позиции | `[VAL.003]` |
| `support_oppose_disagreement` | Обнаружено несогласие; `ConsensusVerdict.outcome = no-consensus` | `[PROT.003]` |
| `invalid_format_status` | extraction = `invalid-format` → сессия входит в `blocked-escalation` с `information-gap` | `[PROT.002]` |
| `missing_core_role` | Отсутствует основная роль → `blocked-escalation` с `risk-threshold-breach` | `[PROT.001]` |
| `manifest_hash_break` | Проверка целостности хэш-цепочки не проходит | `[IO.002]` |
| `documenter_error_category_mapping` | Каждая категория ошибок Documenter детерминированно отображается в один код реестра | См. таблицу отображения ниже |

#### Отображение категории ошибки Documenter → Реестр (предзаполнено для Layer 0)

| error_category | Код реестра | Описание |
|---------------|------------|----------|
| `hash_mismatch` | `IO.002` | Разорвана хэш-цепочка манифеста |
| `trust_mismatch` | `VAL.004` | Несоответствие порога доверия |
| `audit_mismatch` | `VAL.005` | Аудиторский токен отсутствует/истёк/вне области |
| `blocking_finding` | `PROT.005` | Присутствует блокирующее выявление |
| `skill_failure` | `IO.004` | Сбой делегированного навыка |
| `operator_timeout` | `PROT.006` | Превышено время ожидания одобрения оператора |
| `gate_failure` | `PROT.GATE.001` | Сбой контрольной/предварительной проверки, требующий отмены |
| `unknown` | `IO.999` | Необработанное исключение во время выполнения delegate() |

Каждая запись должна быть проверена путём инъекции соответствующей error_category в событие documenter и проверки, что изданный код реестра точно совпадает. Дубликаты отображений запрещены.

## Приоритет контента

Когда спецификации конфликтуют между документами, применяется следующий порядок приоритета (от высшего к низшему):

1. Контракты формата (`service-contract`) — поля схем, перечисления, коды ошибок, схемы событий.
2. Спецификации протокола/运行时 (`protocol-core`, `execution-runtime`, `operator-surface`) — переходы фаз, логика эскалации, семантика сессий.
3. Документы конфигурации/сервиса (`planned-architecture`, `documenter-service/*`) — интерфейсы, политики, поведение инструментов.
4. Документы отката и сценариев (`fallback`, `scenario`) — операционные примечания, связанные с определёнными режимами или сценариями.
5. Концептуальные и устаревшие документы (`project-concept`, `project-reference`) — цели, роли, ссылки на дорожную карту.
