## Область применения

Определяет Уровень 1 как Среда исполнения: границы модулей, детерминированная плоскость управления, конечный автомат фаз, сборка артефактов, сохранение сессий, маршрутизация эскалации и правило пространства имён между fallback и code Модератором. Поля артефактов определены в `service-contract/index.md`; доставка оператором определена в `operator-surface/index.md`.

## Границы уровня 1

Слой 1 — это Среда исполнения. Он содержит детерминированного Модератора и недетерминированные исполняемые единицы (Ролевые агенты и Вспомогательные агенты). Слой 2 — это Внешние интерфейсы / Адаптеры; он вызывает Слой 1 и никогда не вызывает Слой 0. Правило для Слой 0 остаётся неизменным: только Слой 1 вызывает Слой 0.

| Модуль | Обязанности | Может импортировать |
|--------|----------------|------------|
| `orchestrator/` | Машина состояний фазы, Модератор, маршрутизация консенсуса и эскалации | `agents/`, `scenario/`, `persistence/`, Уровень 0 |
| `agents/` | Агенты ролей, Вспомогательные агенты, `RoleAgentFactory`, `get_model()` | `scenario/`, типы парсеров Уровня 0 |
| `scenario/` | `ScenarioLoader`, валидация сценария | типы каталога Уровня 0 |
| `persistence/` | Манифест, файлы фаз, атомарные записи, блокировки | — |

Правила импорта: `orchestrator/` может импортировать другие модули; `agents/` НЕ ДОЛЖЕН импортировать `orchestrator/`; только `agents/` может вызывать `get_model()`; `orchestrator/` НЕ ДОЛЖЕН импортировать его напрямую; Layer 1 НЕ ДОЛЖЕН импортировать Layer 2.

## Детерминированная плоскость управления

Модератор контролирует поток выполнения, а каждая фаза, консенсус и решение об эскалации являются детерминированными функциями от проверенных выходов ролей. Ни одна LLM не участвует в управлении потоком выполнения или проверке безопасности. Модератор может читать произвольный текст только для отображения; он никогда не интерпретирует его для принятия решений. Загрузка сценария по умолчанию использует `default-council-session` (см. `scenario/default-council-session.yaml`), если в манифесте сессии не указан явный `scenario_id`.

## Машина состояний фазы

Состояния: `1` отправка задачи, `2` индивидуальный обзор, `3` обсуждение, `4` проверка консенсуса, `5` резолюция, а также `awaiting-operator`, `resolved`, `failed`.

| Откуда | Куда | Охрана |
|------|----|-------|
| 1 | 2 | Задача проверена; сценарий загружен; locked_roles разрешены в соответствии с operator_approval согласно `service-contract/index.md` §Сессия Манифест |
| 2 | 3 | Каждая активная роль имеет `RoleStatus` с `extraction = parsed` |
| 2 | awaiting-operator | Любой статус `invalid-format` или отсутствие Core роли |
| 3 | 4 | Достигнут лимит раундов, или нет новых `blocked-in-scope` |
| 3 | 3 | Есть хотя бы один `blocked-in-scope` и остаётся бюджет целевого раунда |
| 4 | 5 | Согласно таблице протокола-core §Outcome-to-Transition: `consensus` или `conditional` → Фаза 5 |
| 4 | 3 | Согласно таблице протокола-core §Outcome-to-Transition: `no-consensus` при наличии оставшегося бюджета → повторный вход в Фаза 3; уменьшает `no_consensus_budget`. |
| 4 | awaiting-operator | Согласно таблице протокола-core §Outcome-to-Transition: `blocked-escalation`; ИЛИ `no-consensus` при исчерпанном бюджете (`no_consensus_budget` достигает нуля → `blocked-escalation` с `escalation_reason = information-gap`) → `awaiting-operator` |
| 5 | resolved | Финальный артефакт сохранён; манифест обновлён последним |
| awaiting-operator | `resume_phase` | Разрешение оператора привязано к `escalation_id` |
| N → N+1 | Обязательно на границах фаз согласно определению слоя. Быстрый отказ при высоком/критическом выводе Документатора (перечек не прошёл). Если предварительная проверка недоступна → разрешение на обход через council.override_precheck (событие precheck.overridden). Обход записывается в манифест как pre_check_override; разрешает ровно один переход, после чего требуется ещё один проход или новое разрешение. |
| any | failed | Невосстановимая ошибка ввода-вывода или нарушение протокола |

Только `orchestrator/` продвигает фазу. Оператор никогда не редактирует состояние фазы напрямую; резолюция поступает через интерфейс оператора. Хук обновления `SUBJ-007` для быстрого обзора зарезервирован, но не реализован на этапе MVP.

## Обработка статуса роли

`extract_role_status()` является единственным источником истины для **консенсуса**. Извлечение с `invalid-format` представляет собой блокирующую ошибку протокола: **сессия** переходит в состояние `blocked-escalation` с `escalation_reason = information-gap`, сгенерированным структурно конвейером извлечения; сырой обзор сохраняется, а **роль** никогда не учитывается как `agree`. Критический **вывод** с недействительным обоснованием следует тому же принципу непринятия (согласно `service-contract/error-management/index.md` §Процесс проверки критических выводов): он понижается до `high` с сохранением исходного текста, а не вызывает полный отклонение обзора. Отсутствие **роли** Core приводит к `blocked-escalation` с `escalation_reason = risk-threshold-breach`. Наличие роли Core проверяется на каждом пути, а не только перед упрощением. Врата pre_check работают независимо от извлечения **статуса роли**, но должны успешно пройти перед любым продвижением протокола.

## Порядок сборки артефакта

1. Фаза 2: сохранить один `RoleReview` для каждой активной роли.
2. Фаза 3: сохранить один `RoleReview` для каждой активной роли за раунд.
3. Фаза 4: сохранить `ConsensusVerdict`.
4. Фаза 5: сохранить Документ консенсуса или `EscalationRecord`.
5. Обновить `manifest.json` в последнюю очередь.
6. Генерировать события только после успешного выполнения устойчивой записи.

Неудачно выполненный шаг прерывает выполнение оставшихся шагов. Сессия остается на границе последней завершенной фазы.

## Маршрутизация эскалации

Эскалация — это остановка с последующим возобновлением. Runtime записывает `EscalationRecord`, устанавливает `phase_state = awaiting-operator`, генерирует событие `escalation.opened` и возвращает управление оператору. На этапе MVP не требуется блокировка stdin или фоновый ожидатель: runtime проверяет `timeout_at` при каждом последующем вызове сессии. Когда текущее время превышает `timeout_at`, runtime автоматически применяет `fallback_strategy`, определённую в `EscalationRecord`, и переводит фазу вперёд. При ручном вызове до истечения таймаута управление временем принадлежит поверхности оператора; оператор также может переопределить это через явное одобрение.

Для возобновления требуется аутентифицированная резолюция, связанная с `escalation_id` и `operator_id`. При возобновлении среда выполнения применяет решение, устанавливает `current_phase = resume_phase`, записывает резолюцию в запись эскалации и журнал событий, а затем продолжает работу. Эскалация, отклоненная или замененная, следует своей `fallback_strategy`.

## Каталог сессий

```
sessions/<session_id>/
  manifest.json      # SessionManifest (service-contract)
  task.md            # operator-authored task brief
  phase-1.json       # one file per phase, overwritten atomically
  phase-2.json
  phase-3.json
  phase-4.json
  phase-5.json
  events.jsonl       # append-only event log
  .lock              # single-writer lock
```

Каждый файл фазы имеет вид `{schema_version, phase_id, status: complete|partial, artifacts: string[], updated_at}`. Файлы фазы содержат локальный для сессии текст рецензирования; `manifest.json` и `events.jsonl` содержат только обезличенные сводки, хэши и идентификаторы. Состояние времени выполнения является локальным и НЕ ДОЛЖНО коммититься в git; версионируются только конфигурация и схемы.

## Манифест сессии

`manifest.json` следует за `SessionManifest` в `service-contract/index.md`. Дополнительные правила жизненного цикла:

- `manifest_hash` — это `sha256` канонического JSON (отсортированные ключи, без пробелов) с опущенным `manifest_hash`.
- `previous_manifest_hash` связывает каждую запись с предыдущим манифестом; первая запись использует `null`.
- `role_agent_config` фиксирует точные параметры, используемые для каждой роли, обеспечивая соответствие требованиям ADR-002 по происхождению.
- `pending_operator_action` — это проекция, видимая оператору, для открытой Эскалации.

## Механика сохранения

- Записи используют временный файл → `fsync` → атомарный `rename`.
- Блокировка на одного автора (`flock` exclusive) для `.lock` охватывает всю сессию; таймаут получения составляет 30 секунд.
- Записи манифеста сериализованы и хэш-цепочечны. Разрыв цепочки — это `IO.002`.
- Читатели могут проверять сессию без блокировки; они ДОЛЖНЫ терпеть отсутствие файла последней фазы и возвращаться к предыдущей полной границе.

## Семантика аварийного завершения

MVP предоставляет резюме на границах фаз, а не промежуточные контрольные точки (ADR-004 отложено).

1. При запуске проверьте цепочку хэшей манифеста.
2. Найдите самый высокий непрерывный файл фазы с `status: complete`.
3. Отбросьте оставшиеся `.tmp` файлы.
4. Продолжите с этой границы фазы; повторно запустите незавершенную фазу.
5. Если манифест недействителен, отметьте сессию `failed`; оператор должен начать новую сессию.

Повторный запуск фазы вызывает повторное обращение к LLM и может привести к получению иных результатов. Журнал событий фиксирует новую попытку; предыдущие полные артефакты остаются официальным доказательством до момента фиксации результатов повторного запуска.

## Правило пространства имён

Оба режима используют общую структуру каталога сессий (`sessions/<session_id>/`), но различаются внутренними артефактами:

- **Режим Модератора:** Использует каноническую схему — `manifest.json` (SessionManifest), файлы `phase-*.json`, `events.jsonl` и `.lock` (см. §Сессия Directory Contract). Все фазы производят структурированные артефакты в формате JSON.
- **Режим резервного варианта (освобожденный):** Использует обычные текстовые файлы Markdown (`task-brief.md`, `review-*.md`, `consensus-doc.md`). Сессии в режиме резервного варианта НЕ требуют `SessionManifest` или структурированных файлов фаз; они следуют структуре, определенной в `fallback/index.md`, §Сессия workspace convention. Это освобождение существует, потому что основанный на коде Модератор еще не реализован (§1.5 Project Stage in AGENTS.md). Когда Модератор станет доступен, адаптер МОЖЕТ преобразовывать выходные данные резервного варианта в каноническую схему.

## Правило Вспомогательного сервиса (D3)

Документатор, режим резервного копирования и сохранение в формате JSON являются вспомогательными службами вне цепочки слоёв. Документатор вызывается поверхностью оператора Layer 2 и использует порт исполнения Layer 1 для записей, поддерживаемых LLM (Рабочий документатор). Вспомогательные службы никогда не вызывают Layer 2 или Layer 0 напрямую. В Layer 2 отсутствует прямое обращение к LLM.

## Прогноз статуса оператора

Среда выполнения предоставляет доступ к проекции только для чтения, которая отвечает на три вопроса:

| Вопрос | Поля |
|----------|--------|
| Где я? | `session_id`, `mode`, `current_phase`, `phase_state` |
| Что меня ожидает? | `pending_operator_action`, открытый `escalation_id`, `resume_phase` |
| Что изменилось с последнего просмотра? | `last_event_id`, `changed_since_last_view`, `artifacts` |

Хеш-цепочка гарантирует целостность, а не понятность. Эта проекция является обязательной и отображается поверх интерфейса оператора.

## Путь миграции

Если оркестрация выходит за пределы уровня 1, извлеките ядро оркестрации за публичным интерфейсом уровня 1 (вариант B). Границы слоев, правило уровня 0 и контракт сессии остаются неизменными.
