## Обзор

**Сценарий** определяет набор активных Ролей и параметризацию базового пятифазного протокола взаимодействия (см. `protocol-core/index.md` §Протокол взаимодействия) для решения задач определенного рода. Это декларативный рецепт, а не экземпляр выполнения: Сценарий — это то, что выбирается; Сессия — это то, что создается, когда Сценарий выполняется для Задачи.

Сценарии не заменяют и не расширяют базовую структуру протокола. Они выбирают роли, настраивают параметры и при необходимости определяют подготовительные префазы, которые передают входные данные в Фазу 1 (Подача Задачи). Изменения на уровне протокола (различные последовательности фаз, разная логика Консенсуса) реализуются через отдельные варианты протокола, а не через сценарии.

---

## Иерархия моделей

Слои концептуализации:

| Слой | Концепция | Роль |
|-------|---------|------|
| Рецепт | **Сценарий** | Объявляет роли, параметры, предфазы |
| Ввод | **Задача** | Описание проблемы, предоставленное пользователем |
| Выполнение | **Сессия** | Конкретный запуск, сочетающий Сценарий с Задачей |
| Участники | **Роли** | Потенциальные возможности, активируемые Сценарием |

Сценарий выбирает Роли из доступного набора, определённого в `protocol-core`. Сценарий параметризует базовый протокол (ограничения раунда обсуждения, критерии допуска к объекту обсуждения и т. д.), но не изменяет последовательность фаз или логику консенсуса.

## Схема

Каждое объявление **Сценарий** содержит следующие поля:

| Поле | Тип | Обязательно | Описание |
|-------|------|----------|-------------|
| name | string | да | Человекочитаемый идентификатор |
| problem_type | string | да | Описание предметной области проблемы, которое решает данный сценарий |
| roles | array of Роль identifiers | да | Роли для активации; должен включать Специалист по надёжности и безопасности, если явно не исключён с документально обоснованным оправданием оператора |
| no_consensus_budget | integer | да | Максимальное количество раундов обсуждения, после достижения которого автоматически происходит переход к `blocked-escalation` с `escalation_reason = information-gap`. Бюджет уменьшается с каждым раундом в Фазе 3; когда он достигает нуля, Фаза 4 оценивает бюджет как исчерпанный, а не как `no-consensus`. |
| version | semantic version string | да | Независимая версия сценария |
| scenario_id | string | да | Стабильный уникальный идентификатор для данного определения сценария. ОБЯЗАТЕЛЬНО — каждый сценарий должен предоставить свой идентификатор, соответствующий записи в каталоге. Идентификаторы в kebab-case и должны быть глобально уникальными среди всех сценариев. Выводится из имени файла, когда присутствует в каталоге по умолчанию (`default-council-session.yaml` → `default-council-session`). |
| round_timeout_minutes | integer | нет | Время ожидания (в минутах) по умолчанию для каждого раунда обсуждения. По умолчанию `protocol.max_discussion_rounds * 5`, если не указано. Используется средой выполнения для установки `timeout_at` для каждого раунда (см. `execution-runtime/index.md` §Эскалация Routing). |
| escalation_timeout_minutes | integer | нет | Время ожидания (в минутах) по умолчанию для эскалированных сессий, ожидающих разрешения оператора. По умолчанию значение из `defaults/policy.yaml` (30 мин), если не указано. Переопределяет файл политики, если присутствует. |

## Ограничения

### Неизменные инварианты

1. **Неизменяемость структуры протокола.** Сценарии могут параметризовать базовый пятифазный протокол, но никогда не вставлять, удалять или изменять порядок фаз. Каноническая последовательность (Подача задачи → Индивидуальный обзор → Раунд обсуждения → Проверка консенсуса → Формирование резолюции) является незыблемой.

2. **Пути эскалации сохранены.** Ни один сценарий не может отключать или ослаблять каналы эскалации (информационный пробел, неразрешимый конфликт, превышение порога риска).

3. **Вычисление консенсуса не изменено.** Детерминированные правила консенсуса (согласие/замечания/блокировано в области/блокировано из-за эскалации) не могут быть переопределены конфигурацией сценария.

### Ограничения безопасности

4. **Включение специалиста по надёжности и безопасности.** Роль специалиста по надёжности и безопасности должна быть включена в каждый сценарий по умолчанию. Явное исключение требует обоснования, одобренного человеком, которое хранится в записи сессии, а также документированного обоснования на этапе 1.

5. **Фиксированный каталог на момент запуска.** Сценарии разрабатываются исключительно сопровождающими фреймворка. Создание операторов откладывается до тех пор, пока не будет определена модель управления.

6. **Отсутствие компонуемости на этапе MVP.** Сценарии ссылаются на другие сценарии через зарезервированное поле, но не могут быть объединены в композиции при запуске. Семантика валидации композиций будет определена на более позднем этапе.

## Каталог сценариев

Сценарии хранятся в каталоге `scenario/` вместе с данной спецификацией на этапе MVP. Сценарий по умолчанию (`default-council-session.yaml`) всегда доступен независимо от содержимого каталога. Новые сценарии должны быть добавлены как в таблицу каталога ниже, так и в собственный файл YAML в каталоге `scenario/`.

| Файл | scenario_id | имя | тип проблемы | роли (базовые) | Статус |
|------|-------------|------|--------------|--------------|--------|
| `default-council-session.yaml` | `default-council-session` | Сессия совета по умолчанию | Универсальная сессия совместного проектирования с использованием базовых уровней протокола; подходит для широких технических задач без специфичных для домена предварительных этапов | Архитектор, Специалист по надёжности и безопасности, Человекоцентричный проектировщик, Инженер по эксплуатации | Активна (MVP) |

При загрузке из файловой системы `scenario_id` определяется на основе имени файла (без расширения). При явном указании в манифесте оно должно совпадать с записью в каталоге. Конфликты между определением в каталоге и содержимым YAML приводят к ошибке `CONFIG.002`.

## Отношения

- **Сценарий vs Задача:** Задача описывает *что* нужно решить. Сценарий описывает *как* система структурно подходит к решению этого типа проблемы.
- **Сценарий vs Сессия:** Сценарий — это шаблон/рекомендация; Сессия — это конкретный экземпляр выполнения, в котором один Сценарий привязан к одной Задаче.
- **Сценарий vs Роли:** Сценарий выбирает Роли из доступного набора. Он не переопределяет их и их обязанности. Настройка запроса в рамках Сценария ограничена акцентированием/внесением контекста, а не заменой поведения.
- **Сценарий vs ядро протокола:** Сценарий наследует базовую пятифазную структуру протокола из `protocol-core/index.md` и параметризует её. Новые варианты протокола будут отдельными артефактами, на которые ссылаются независимо.
- **Сценарий vs уровни активации Роли:** Модель уровней (Базовый / Расширенный) в `protocol-core` (§Правила активации Роли) служит механизмом резервного/по умолчанию. Сценарии предоставляют декларативные наложения, которые заменяют ручное обоснование после полного внедрения. До этого момента применяются уровневые замечания по умолчанию, если Сценарий не указан.

## Примерные сценарии (иллюстративные)

Данные сценарии предлагаются в качестве иллюстративных примеров. Они НЕ являются частью первоначальной реализации — первоначальная реализация заключается в документировании самой абстракции Сценарий. Будущие итерации будут наполнять каталог, основанный на наблюдаемых шаблонах использования.

- **Мозговой штурм** — Сессия по генерации идей с многоперспективным подходом, направленная на создание вариантов без преждевременного сужения. Вероятно, включает расширенные раунды обсуждения.
- **Допрос** — Интенсивный режим противоречивого прояснения. Многоэтапное задавание вопросов для выявления скрытых предположений и требований до начала формального обзора. Может использовать более высокие лимиты раундов до фазы и более строгие пороги критического обоснования.
- **Генерация спецификации** — Преобразование подробного описания задачи в структурированную спецификацию. Минимальное количество предфаз, возможно, нулевые раунды обсуждения для четко определенных входных данных.
- **Планирование реализации** — Преобразование спецификации в пошаговый план выполнения. Активирует Роли, охватывающие архитектурную декомпозицию, операционные Замечания и зависимости последовательности.
