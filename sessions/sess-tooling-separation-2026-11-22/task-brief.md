# Session Task Brief — Tooling Separation

Session ID: sess-tooling-separation-2026-11-22
Mode: fallback (sequential local subagents, operator as Moderator)
Date: 2026-11-22

## Session Goal

Определить целесообразность разделения репозитория/артефактов проекта Council на две
части: (1) собственно разработка проекта (концепция, спецификации, протокол, документация)
и (2) инструменты разработки (детерминированные инструменты `tools/`, упаковщик `dist/`,
vendored-движки), представив инструменты как установленный, зафиксированный (pinned)
набор из дистрибутива.

## Focus Areas

- Граница между «проектом» и «инструментами»: что именно уходит за границу.
- Модель фиксации: lock-файл, pinned-дистрибутив, vendor-каталог (прецедент ADR-014 /
  `defaults/translation.lock`).
- Влияние на существующие контракты: Write Rule (Documentation Worker — единственный
  писатель), manifest, advisory-аудит `tools/check_all.py`, prose-contract synchronization.
- Процесс обновления инструментов: кто и как обновляет зафиксированный набор, drift.
- Издержки против выгод: упрощение (OP-2), контроль ошибок (OP-3), когнитивная нагрузка
  на оператора.

## Questionnaire per Role

**Architect:**
- Q1: Где проходит естественная граница компонентов между проектом и инструментами?
  Не ломает ли она существующие зависимости (skill → tools, dist → docs, tests → tools)?
- Q2: Не создаст ли разделение новых связей (инструменты, знающие о проекте, или проект,
  знающий о версии инструментов) вместо удаления старых?

**Reliability & Security Specialist:**
- Q1: Что происходит при рассогласовании зафиксированной версии инструментов и ожиданий
  проекта (drift)? Какие режимы отказа даёт pinned-модель и как они обнаруживаются?
- Q2: Не возникают ли новые векторы риска (подмена дистрибутива, устаревание без обновления,
  «замороженный» инструмент с дефектом)?

**Human-Centric Designer:**
- Q1: Становится ли жизнь оператора проще: понятнее ли, где «писать нельзя, только обновить
  версию», яснее ли источник истины?
- Q2: Не добавляет ли разделение лишних шагов/артефактов (lock-файлы, команды обновления)
  при том, что оператор один и процесс должен быть мгновенным (OP-1)?

**Operations Engineer:**
- Q1: Как выглядит жизненный цикл обновления зафиксированного набора: build → archive →
  lock → verify? Кто владелец dist/ в новой модели?
- Q2: Каковы эксплуатационные издержки (версионирование, совместимость tools↔docs↔skill,
  тесты) и окупаются ли они?

## Subject List

- `SUBJ-001`: Разделение артефактов: границы между «разработкой проекта» (docs/, концепция,
  протокол) и «инструментами разработки» (tools/, dist/, vendor/, defaults/, tests инструментов).
- `SUBJ-002`: Модель фиксации инструментов: зафиксированный набор из дистрибутива
  (pinned archive + lock-файл по образцу ADR-014 / translation.lock) vs. текущее
  внутри-репозиторное положение tools/.
- `SUBJ-003`: Влияние на управляющие контракты: Write Rule / Documentation Worker skill,
  manifest, advisory-аудит check_all.py, prose-contract synchronization (AGENTS.md §1.7).
- `SUBJ-004`: Процесс обновления и drift: кто обновляет pinned-набор, как обнаруживается
  рассогласование версий инструментов и ожиданий проекта, откат (git revert, OP-3).
- `SUBJ-005`: Общая целесообразность: перевешивают ли выгоды (изоляция, воспроизводимость,
  переиспользование dist/) издержки (сложность, двойное версионирование, риски рассогласования).
