## Decision

**Принят гибридный принцип организации консилиума** (SUBJ-001):

1. **Fixed Core — неизменяемое ядро.** Роли Core (Architect, Reliability & Security Specialist, Human-Centric Designer) активны в каждой сессии и являются `locked_roles` по умолчанию в fallback-контракте. Анализатору запрещено рекомендовать их исключение — это архитектурный инвариант, а не политика (закрыт вектор prompt-injection через описание задачи).

2. **Advisory analyzer для Extended-ролей.** Для достаточно сложных задач запускается ИИ-анализатор, который по task brief рекомендует набор Extended-ролей с обоснованием. Анализатор — **не роль и не фаза протокола**, а Pre-Phase 0: генератор содержимого Scenario-артефакта (JSON), ложась тем самым в существующий §Scenario-driven assignment protocol-core. Он не занимает слот в лимите ролей.

3. **Оператор утверждает состав** (OP-1, мгновенное одобрение). Оператор может принять, отклонить или дополнить рекомендацию; его решение — финальное и записывается в артефакт анализатора для аудита.

4. **Чистая динамика отклонена.** Автономный подбор всего состава ролей (включая Core) отвергнут единогласно: attack surface, галлюцинация подбора, недетерминизм против OP-3.

## Subjects with outcomes

- **SUBJ-001 (принцип выбора ролей):** agreed — гибрид fixed Core + advisory Extended.
- **SUBJ-002 (контракт анализатора):** conditionally agreed — детерминированный JSON-контракт + человекочитаемое обоснование; формат артефакта подлежит стандартизации (см. reservations).
- **SUBJ-003 (совместимость с протоколом):** agreed — анализатор выражается как «live scenario»-артефакт; изменения требуются в `fallback/index.md` (Pre-Phase 0, locked_roles, fail-safe) и контракт анализатора в protocol-core.
- **SUBJ-004 (воспроизводимость/OP-3):** agreed — полный trace (вход, JSON-выход, обоснование, решение оператора) сохраняется в workspace сессии (`review-analyzer.md` / `review-analyzer.json`); валидация схемы — машинная (`check_all.py`), не ручная.
- **SUBJ-005 (стоимость):** conditionally agreed — анализатор не запускается для простых задач; критерий «простоты» формализуется (см. reservations).

## Role reservations (tied to subjects)

- **Reliability & Security (conditional agree):** требуется формализовать порог «простой задачи» checklist'ом (иначе субъективный judgment ложится на оператора); формат артефакта анализатора должен быть стандартизирован (атомарная пара JSON + MD); fallback-инструкция при сбое анализатора должна быть прописана на уровне протокола. `<SUBJ-002, 004, 005>`
- **Operations Engineer (concerns):** остаётся неопределённость, кто вычисляет порог сложности в fallback-режиме без Moderator (предложение: `classify_bump.py` + эвристики ≤3 файлов / ≤50 строк / ≤2 директории, либо обёртка `council-start.sh`); нужен ли запуск анализатора на meta-задачах — роль считает, что **нет** (рекурсивная зависимость), оператор отключает флагом `analyzer_enabled: false`. `<SUBJ-005, 001, 003>`
- **Human-Centric Designer (agree, с условиями):** артефакт анализатора — один сканируемый блок (≤5–7 строк, одна строка на роль); Core/Extended визуально разделены; решение о запуске анализатора по умолчанию принимает машина (оператор может переопределить); анализатор не должен предлагать роли вне существующего каталога. `<SUBJ-002, 005>`
- **Architect (agree):** конфликт «декларативный Scenario vs генеративный анализатор» решён: анализатор — внутренний генератор декларативных полей сценария; при сбое/невалидном JSON — abort рекомендации и fallback на full Core. `<SUBJ-003>`
