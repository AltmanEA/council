## Решение Q1: кто живёт в main — **Q1-A (unanimous)**
`master` = операционная v1 до switch-over; v2 — ветка `v2-dev` + worktree `council-dev/`.
Обоснование (сняв ошибочный аргумент про аудит sessions, роли сошлись на трёх):
1. **Асимметрия стоимости ошибки:** привычный запуск из корня при Q1-A даёт регламент v1 (безопасно по умолчанию); при Q1-B корень = черновик, промах молЧАТ и лечится только повтором сессии (HCD: guard как backstop vs guard как единственная линия обороны при OP-1).
2. **Релизный провенанс:** `dist/build.sh` собирает из текущего checkout — инвариант «релиз из дефолтного дерева» истинен только при main=v1 (Operations).
3. **История и аудит когерентны:** корень накапливает операционную историю; при Q1-B maintenance-сессии пишутся вне main навсегда.
Q1-B отклонён (HCD critical: баннер-несущая конструкция; Operations: 2–7 сорванных операционных сессий за dual-life; Reliability: production вне ветки по умолчанию). Q1-C отклонён по OP-2 (main не runnable → агент импровизирует или берёт `docs/protocol-core` (active) как регламент — подмена операционной процедуры целевой архитектурой).

## Решение Q2: чем проводится консилиум в v2-ветке — **дистрибутив v1 по умолчанию; dogfooding по пину; dogfood-окно перед go-live**

**Штатный режим (все решающие сессии v2):** движок = материализованная read-only копия v1 из тега (см. механизм ниже). Dogfooding черновиком запрещён как режим по умолчанию (Reliability critical: круговая аргументация — черновик обосновывает сам себя; правка между Фазами 2/3 делает consensus невосстановимым; 2–8 попаданий правок в идущие сессии за разработку, 1–5 ч, из них 20–30% незамеченных — дефект OP-3, HCD critical).

**Dogfooding — узкое исключение:** только сессии, чей явный предмет — сам протокол v2; движок = пин закоммиченного черновика `engine: draft@<sha>`; черновик не редактируется от Фазы 1 до consensus-doc. Плюс обязательный gate 3–5 dogfood-сессий после feature-freeze перед go-live (Operations; иначе v2 уходит в production, не проверенный на собственных правилах).

**Механизм движка (конвергенция): источник истины — git-тег, формат потребления — материализованные read-only файлы.**
- Отвергнуто: **голый git-ref** (Reliability critical: агент читает вывод bash-команды → пересказ правил → галлюцинация порогов; rail-shortcut «открыть рабочий fallback/»; нет артефакта для аудита) и **dist-канал как движок** (Reliability critical: install.sh — host-takeover, второй corpus внутри worktree, блокирует собственные сборки dirty-guard'ом; VERSION=`git describe` легально родит `v1.0.1-3-gabc` — нерелизный движок с релизным именем; вектор тот же, что «новее=главнее»). От dist взята только форма провенанса (tree-sha ≈ SHA256SUMS, DIST-SOURCE ≈ version.txt).
- Итоговая форма: каталог движка создаётся из тега (`git checkout <tag> -- fallback` или `git archive <tag> fallback/ | tar -x`), содержит `DIST-SOURCE` (tag, tree-sha, дата) и императив в первой строке; на старте каждой сессии — advisory-проверка сверки с пином (warn, не блок).
- **Остаточное расхождение — форма каталога (решение оператора №1, см. ниже).**

## Инварианты (принято всеми, mandatory)
1. **Пин движка:** `engine: <идентификатор>` в шапке `task-brief.md`, переносится в шапку `consensus-doc.md`; всегда разрешённая версия (`v1.0.2` / `draft@<sha>`), никогда не алиас (Reliability: две сессии с одним алиасом могут идти по разным правилам).
2. **`premise-drift`:** расхождение пина между фазами ⇒ пометка + один повтор Фазы 4; второй дрейф в сессии ⇒ `invalid-premise`, архив без consensus-doc (Reliability; HCD уточняет: это утверждение в шапке, не блокирующая проверка — оператор заполняет один раз, не «четвёртая обязанность внимания»).
3. **Forward-port багфиксов v1:** каждый фикс, затрагивающий `fallback/`, ⇒ парный коммит в `v2-dev` с трейлером `backport-of: <sha>` + `premise-shift: none|affects=<session-id>`; аудит — по содержимому (строка фикса в черновике/движке), не только по трейлеру (Reliability), на старте каждой v2-сессии (чек-лист), отложенное — `backport-deferred` с причиной; финальная сверка двумя grep'ами перед switch-over (Operations).
4. **Словарь тегов:** `v1-stable` — неизменяемый якорь базовой линии (=v0.6.0, момент ветвления); релизы v1 — `v1.0.x`; `v1-latest` — движущийся указатель для удобства, разрешается при старте сессии, в пин пишется разрешённое; сборка релиза только при `git describe --tags --exact-match` (иначе отказ) — обе правила в `dist/RUNBOOK.md`.
5. **Запрет гейтинга:** pre-commit-гейт на `fallback/` (Architect) отклонён 3:1 (Operations/Reliability/HCD: гейт на рутинном легитимном событии обучает игнорировать сигнал + прямое нарушение OP-1; включение `block-mode.flag` заблокирует и разработку v2). Все проверки — advisory (warn + решение оператора).
6. **Баннеры/канон:** v1 — «ОПЕРАЦИОННАЯ ВЕРСИЯ v0.6.0 — правки только по подтверждённым дефектам» (слово «заморожена» убрать — ложь при живых багфиксах, обесценивает всю шапку); черновик — «ЧЕРНОВИК v2 — объект обсуждения, НЕ регламент: сессию по нему не проводить»; канон `MODE: operational/<ver> | dev-engine/<ver> | dev-dogfood/<sha>` дословно в трёх местах (документ, brief, AGENTS.md); `role: engine | object-of-review` во frontmatter (grep-able).

## Решения оператора
**№1 — форма каталога движка:**
- **A. Tracked-копия (Reliability):** `fallback-dist/` коммитится в v2-dev (`resync dist to <tag>`), provenance в git, проверка `git diff --quiet <tag> -- fallback-dist/`; минус: 200 строк движка в диффах ветки, риск случайного коммита правки.
- **B. Generated, gitignored (HCD/Operations):** `.engine/<version>/`, `tools/gen_engine.sh <tag>` безусловно на старте сессии (~50 мс, идемпотентно), версия в пути; git status чист всегда; минус: provenance только в пине артефакта + DIST-SOURCE.
*(Рекомендация модератора: B — операционно дешевле и не пачкает диффы ветки; A — если нужна git-доказуемость движка.)*

> **РЕШЕНИЕ ОПЕРАТОРА (2026-11-23): B** — генерируемый `.engine/<version>/` (gitignored), `tools/gen_engine.sh <tag>` на старте сессии, provenance в пине `engine:` артефактов + `DIST-SOURCE`.

**№2 — долговечность сессий (OP-3-дыра):** consensus-doc'ы вне git = ссылки в коммитах v2 ни на что не ссылаются; удаление worktree = безвозвратная потеря.
- **A (HCD, рекомендация модератора):** точечное исключение в `.gitignore` — трекаем `sessions/*/consensus-doc.md` (+ task-brief), без миграции 46 старых.
- **B (Operations):** `cp -a` в `archive/sessions/` перед удалением worktree, git не трогаем.

> **РЕШЕНИЕ ОПЕРАТОРА (2026-11-23): A + B как гигиена.** Трекаем `sessions/*/consensus-doc.md` (`!`-исключения в `.gitignore`, без миграции старых сессий); `cp -a sessions/ archive/sessions/<worktree>-<date>/` — обязательный шаг перед удалением worktree (страховка review-материалов).

**№3 — движок dogfood-gate перед go-live:** на черновике (проверяет себя — Reliability указывает на круг) или на копии v1 (проверяет не то, что пойдёт в production)? *(Рекомендация модератора: на пин черновика — gate обязан мерить именно v2, а риск круга снимается тем, что состав ролей и регламент Фаз берутся из движка v1, т.е. «судит» старый регламент, «подсудимый» — новый.)*

> **РЕШЕНИЕ ОПЕРАТОРА (2026-11-23): C — двухпиновый контракт gate-сессий.** Gate-сессии (3–5 после feature freeze) исполняются по черновику v2 (`engine: draft@<sha>`, черновик заморожен на время сессии), вердикт о проходе gate и состав ролей выносятся по стабильному движку v1 (`arbiter: v0.6.0@<sha>`). Обычные (не-gate) dogfood-сессии о протоколе допускаются по A (один пин черновика). Правила, которые принимает арбитр (статусы сессии, провал/проход gate), — 5–7 строк в процедуре switch-over.

**№4 — длительность dual-life (дни/недели)** — влияет на нужность `v1-latest` и строгость forward-port-автоматизации.

> **РЕШЕНИЕ ОПЕРАТОРА (2026-11-23): dual-life = НЕДЕЛИ; багфиксы v1 = редкие хотфиксы.** Следствия: (1) заводим `v1-latest` — движущийся указатель на последний релизный тег v1.0.x; на старте v2-сессии пин разрешается из него, но в шапку пишется разрешённое значение (`engine: v1.0.<x>@<sha>`), не алиас; (2) релизный ритм v1.0.x: каждый багфикс v1 ⇒ новый тег v1.0.(x+1) + движение `v1-latest`; (3) forward-port — ручная дисциплина достаточна (редкие хотфиксы): парный коммит с `backport-of:` + строка чек-листа с двумя grep'ами, без автоматических скриптов.

> **ТЕХНИЧЕСКИЕ ПО УМОЛЧАНИЮ (закрыты оператором, 2026-11-23):**
> - `tools/gen_engine.sh` запускает **оператор** строкой чек-листа старта сессии (агент не получает право писать в рабочую директорию на старте).
> - Путь движка с semver: `.engine/<semver>/` (напр. `.engine/v0.6.0/`); алиасы — только в пине артефакта.
> - Правила арбитра gate (5–7 строк: полномочия — провал/проход gate, статусы сессии) — пишутся как часть подготовки switch-over процедуры.
