# Task Brief — sess-branch-version-strategy

## Session Goal
При уточнённых условиях (v1 продолжает использоваться и получать багфиксы во время разработки v2; версии живут в разных git-ветках) определить:
1. **Q1: какая версия живёт в main** — v1 (стабильная) до switch-over, или v2 (разрабатываемая), или иная схема;
2. **Q2: чем проводится консилиум в v2-ветке** — (A) установленный замороженный дистрибутив v1 (консилиум-«движок» v1 отдельно от разрабатываемых v2-документов) или (B) текущая версия ветки вместе с правками (dogfooding: консилиум проводится по самому черновику v2).
Оценка: в каком варианте выше риск (а) путаницы агентов в версиях, (б) порчи текущего консилиума текущими правками.

## Context
- Уточнение оператора: в ходе разработки v2 первая версия продолжает эксплуатироваться; в v1 возможны исправления багов. Следовательно v1 и v2 — разные ветки git.
- Предыдущая сессия (sess-new-version-dev-start, консенсус `sessions/sess-new-version-dev-start/consensus-doc.md`): работа через git worktree (`council/` root + `council-dev/`), якоря `v1-stable`/`v2-pre-dev`, switch-over без revert (cherry-pick/branch-based), баннеры «РАБОЧАЯ/ЗАМОРОЖЕНА» vs «РАЗРАБАТЫВАЕМАЯ», поля `worktree-path`/`mode` в task-brief, AGENTS.md per-worktree с MODE-маркерами (узел №2 передан оператору), изоляция sessions (узел №1 передан оператору). Настоящая сессия УТОЧНЯЕТ узлы в свете новых условий (две ветки, багфиксы v1).
- Harness: OpenCode; сессии и subagents работают с рабочей директорией; AGENTS.md читается агентом как роутер контекста; артефакты сессий в `sessions/<id>/`; tools/ (check_all.py и др.) — детерминированные.
- Текущий репозиторий: master = v1 (fallback/ v0.6.0, заморожена), 46 проведённых сессий.
- Важно: консилиум в v2-ветке нужен, чтобы ОБОСНОВЫВАТЬ решения о v2 (роль анализатора, locked Core и т.д.) — то есть объект разработки частично совпадает с инструментом разработки.

## Варианты для Q1
- **Q1-A: main = v1** до момента switch-over; v2 в ветке `v2-dev` (worktree `council-dev/`). main всегда = операционная правда.
- **Q1-B: main = v2** (разработка «на витрине»), v1 в ветке `v1-maintenance`. Операционные сессии — из ветки v1.
- **Q1-C: main = «нейтральный» интеграционный** (docs/, tools/, AGENTS.md ядро), обе версии в ветках `v1-stable-line` / `v2-dev`.

## Варианты для Q2 (разработка в v2-ветке)
- **Q2-A: дистрибутив v1 в v2-ветке.** В `v2-dev` кладётся копия дистрибутива v1 (`fallback-dist/` или сохранённый `fallback/` в frozen-состоянии) + `.frozen` баннеры; рабочие консилиумы v2-разработки проводятся им; редактируемые v2-документы — в отдельном пространстве (`fallback-v2-draft/`). Багфиксы v1 в основной ветке порождают необходимость ре-синка дистрибутива (cherry-pick / периодическое обновление).
- **Q2-B: dogfooding.** Консилиум в v2-ветке проводится ТЕКУЩИМ состоянием v2 (черновиком с правками). Собака ест собствен корм: правила консилиума обкатываются на самих себе. Риск: правка в середине цикла разработки может сломать сам процесс проведения консилиума; агент видит редактируемые документы и может принять черновик за регламент.
- **Q2-гибрид** допускается (например: dogfooding только для сессий о самом протоколе; дистрибутив v1 — для всех прочих сессий v2-разработки).

## Focus Areas
- Сопоставление рисков по обоим Q2-вариантам: путаница версий у агентов; порча идущего консилиума текущими правками (включая правку между Фазами 2 и 3); восстановление.
- Двойная поддержка v1: багфиксы в v1-ветке → синхронизация с v2-веткой (нужен ли ре-синк дистрибутива, как часто, кто решает).
- Куда пишутся артефакты сессий каждой ветки (развитие узла №1 предыдущей сессии под новые условия).
- AGENTS.md маршрутизация при «main vs ветки» (развитие узла №2).
- Switch-over и откат (concern из предыдущей сессии) — не сломать ли выбранной схемой.

## Questionnaire per Role
**Architect:**
- Q1: Какая топология веток и main даёт однозначную маршрутизацию при двух живых версиях?
- Q2: Дистрибутив vs dogfooding — как каждое влияет на границы «инструмент разработки» vs «объект разработки»?

**Reliability & Security:**
- Q1: Режимы отказа каждой топологии (агент операционной сессии попал в v2; агент v2 прочитал v1; main «уехал» под оператором).
- Q2: Что ломает консилиум сильнее: черновик как регламент (Q2-B) или рассинхрон дистрибутива с исправленным v1 (Q2-A)?

**Human-Centric Designer:**
- Q1: Что оператор запомнит без усилий: «main=v1, работаю в main» или «main=v2, работаю в ветке v1»?
- Q2: Какой вариант понятнее агенту при первом чтении: frozen-дистрибутив с баннером или «редактируемая правда» dogfooding?

**Operations Engineer:**
- Q1: Операционные издержки топологий: багфикс-поток v1 (rebase/merge, релиз теги), риск main-дрейфа.
- Q2: Стоимость поддержки дистрибутива (ре-синк, версионирование) vs стоимость инцидента dogfooding-поломки (повтор сессии, потерянный раунд).
