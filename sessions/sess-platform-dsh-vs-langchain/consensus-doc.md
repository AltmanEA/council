# Consensus Document — sess-platform-dsh-vs-langchain

Date: 2026-11-18
Mode: fallback (OpenCode subagents), 4 роли (Architect, RelSec, HCD, Ops), 1 раунд обсуждения.
Outcome: **Conditionally resolved** (три agree, у Architect — concerns о формулировке дилеммы, зафиксированы как резервация).

---

## Решение

**Целевая платформа: детерминированный Python-оркестратор (plain subprocess + stdio, без LangChain/LangGraph) с точечными LLM-вызовами через LLM-executor-обёртку. DeepSeek Harness (`dsh`) отклонён как платформа оркестрации и как рантайм Документатора.**

### Обоснование

1. **Дилемма оказалась ложной в исходной постановке.** «Текущей langchain-реализации» не существует — ноль импортов langchain/langgraph в репозитории; стек зафиксирован только в draft-доке `project-reference`. Реальный реализованный код — Python без фреймворков (~1000 тестов: documenter_service, operator_surface, tools, translation CLI). Выбор поэтому не «dsh vs LangChain», а «LLM-зависимый рантайм vs детерминированный Python-код» (Architect, подтверждено RelSec).

2. **dsh несовместим с протокольными требованиями безопасности.** Developer preview с публичным «THERE WILL BE COMPATIBILITY-BREAKING CHANGES» и «must not be treated as secure or production-ready» (без security audit). Критический сценарий (RelSec, не оспорен): breaking change в контракте dsh → `pre_check` gate получает иную структуру ответа → canonical hash не вычисляется → approval binding теряет привязку; fail-closed деградирует в fail-unknown/fail-silent. additionally: модель Cordis «всё — плагин» делает audit-critical path неверифицируемым из репозитория, а рекомендация запуска в одноразовой VM конфликтует с персистентностью audit-реестра.

3. **Протоколу не нужен графовый фреймворк.** Переходы фаз Консилиума — табличные операции над структурированными артефактами (severity, stance, status, justification), а не graph-traversal; операционная модель (один оператор, последовательные фазы, сессии минуты, 3–5 параллельных ролей) не использует checkpointing/replay/масштабирование — ключевые причины брать LangGraph. Параллельный запуск ролей покрывается `concurrent.futures`/subprocess.

4. **Эксплуатационная стоимость dsh для одного оператора неприемлема.** Миграция сервисов на dsh-плагины ≈ 60–80% ре-имплементации при нулевом функциональном выигрыше (Ops); Node/TypeScript-рантайм добавляет второй CI-пайплайн, второй набор lock-файлов и уязвимостей к существующему Python-стеку.

5. **Калибровка доверия оператора.** Кодовый детерминированный оркестратор воспроизводим оператором («тот же код, те же артефакты»); агент-оркестратор, решающий «когда что запускать», смещает доверие к поведению LLM — иная онтология безопасности (HCD). Файловые предохранители (policy.yml, sentinel) понятны интуитивно; слоистая композиция профилей/бандлов/патчей Cordis снижает наблюдаемость.

## Исходы по субъектам

| Subj | Исход |
|------|-------|
| SUBJ-001 (платформа оркестрации) | **Согласовано**: plain Python subprocess-оркестратор (эволюция доказанного fallback-паттерна), harness CLI = только LLM-executor. dsh отклонён. |
| SUBJ-002 (рантайм Документатора) | **Согласовано**: остаётся чистый Python (CLI + stdio JSON-RPC). Документатор — не LLM-агент, плагинизация = over-engineering. |
| SUBJ-003 (стоимость миграции) | **Согласовано**: миграция на dsh неоправданна (60–80% ре-имплементации, потеря проверенных safety-механизмов и покрытия ~1000 тестов на переходный период). |
| SUBJ-004 (безопасность/аудит) | **Согласовано**: audit-critical path (registry, hash verify, pre_check, dual interlock) без фреймворковых абстракций; raw-*.json envelope — runtime-independent протокольный контракт (усиление HCD+RelSec, см. action item). |
| SUBJ-005 (долгосрочный риск платформы) | **Условно согласовано**: dsh фиксируется как **rejected** с rationale, повторный пересмотр — только при накопном выполнении: стабильный релиз 1.0+ (без breaking-change предупреждений), независимый security audit, формальная верификация audit-critical path. LangGraph — не вводится (см. резервации). |

## Резервации ролей

- **Architect** (`SUBJ-001`): формулировка задачи предполагала существование langchain-реализации; это искажало оценку миграции. В финальной редакции дилемма переформулирована.
- **Architect** (`SUBJ-002`): допускает LangGraph как *optional leaf-utility* в некритичных агентах при явной потребности оператора, если core-оркестратор её не импортирует и leaf экспортирует стандартный raw-JSON-envelope. Не проактивно.
- **RelSec** (`SUBJ-002`): LangGraph допустима только вне protocol-critical path и только с экспортом graph topology/retry-config/concurrency в репозиторий как артефакт; pin+CI (довод Ops) решает стабильность, но не auditability.
- **Ops** (`SUBJ-005`): триггер пересмотра LangGraph — переход протокола к настоящим графам состояний (ветвления, checkpoints, replay); операционный маркер — разрастание условных переходов в оркестраторе сверх точки читаемости. dsh-headless как LLM-исполнитель ролей — отложенная гипотеза, не отменённая, но и не план; без security audit — никогда в audit-critical path.
- **HCD** (`SUBJ-005`): фиксировать dsh как `rejected` (не `future_option`), чтобы избежать дрейфа «заметка → активное рассмотрение» в будущих сессиях.

## Открытые вопросы (для оператора)

1. Требуется ли параллельный fan-out ролей в фазах уже сейчас, или строго последовательно? (Определяет, остаётся ли отказ от LangGraph абсолютным; `concurrent.futures` покрывает параллельный запуск и так.)
2. Планируется ли многопользовательский/распределённый режим в горизонте 6–12 месяцев? (Если да — checkpointing/state-management соображения пересматриваются раньше.)
3. Минимальная спецификация raw-*.json envelope (JSON Schema?) для гарантии операторской репликации сессии без запуска рантайма.

## Прозрачность

Критических находок, пониженных за невалидное justification, нет. Все critical-находки содержали concrete failure mode.
Раунды: раунд 1 (4 независимых ревью) + 1 раунд обсуждения; расхождение по LangGraph сшлось от «не вводить никогда / допустима точечно / следующая ступень» к «не вводится сейчас; допустимость только вне audit-critical path при явной потребности и экспорте топологии; триггер пересмотра определён».
