## Decision

Приняты два принципа разработки v2 Консилиума, подлежащие фиксации в новом документе `draft/v2-dev-principles.md`:

### П1. Разделение кода и ИИ (двухфазный жизненный цикл функции)

1. **Конечное состояние:** «то, что можно сделать кодом, делается кодом» — детерминированные функции реализуются кодом.
2. **Период разработки:** сначала — самый простой вариант: ИИ-инструкция (промпт-контракт), при необходимости вместе с кодом-обёрткой. ИИ-инструкция — черновик будущей кодовой функции.
3. **Статусы capability:** трёхмаркерный градиент `[draft] → [tried] → [code]`, один маркер рядом с описанием каждой функции в prose-контрактах.
4. **Критерий «проверено» (`[tried]`):** ≥3 успешных согласованных прогона на различных задачах + существует детерминированная проверка результата. Инициатор (предлагающая роль/автор) объявляет статус; повышение до `[code]` — только с одобрения оператора (OP-1, встраивается в существующий approval-контур Documentation Worker, отдельного гейта нет).
5. **Реестр:** источник истины — inline-маркер `<!-- verified-into-code: YYYY-MM-DD -->` в файле инструкции; индексирующий файл читается оператором, генерируется инструментом по образцу `gen_manifest.py` (advisory, не часть approval-контура). Анти-дрейф: инструменты (classify_bump/check_all) сигнализируют о застрявших `[tried]` без конверсии и о расхождении маркера с фактом.
6. **П1 применяется к самим служебным агентам** (CA-1/CA-2 — сегодняшние ИИ-инструкции → кандидаты в код при проверке; освобождение своих инструментов от П1 обнулило бы анти-дрейф).

### П2. Без жёстких сценариев; служебные агенты перед консилиумом

1. **Формулировка:** заранее записанные жёсткие сценарии не используются. Перед консилиумом служебные агенты динамически наполняют поля Scenario из task brief; итоговый Scenario-артефакт остаётся каноническим декларативным объявлением активированных ролей, pre-phases и параметров (protocol-core §Scenario-driven assignment). При отсутствии вывода анализатора — тировые дефолты.
2. **CA-2 Анализатор задачи = существующий Pre-Phase 0 Role Analyzer**, а не новый механизм (OP-2). Термин «CA-2» — роль в семействе служебных агентов, контракт — контракт анализатора (`review-analyzer.json`/`.md`, `analyzer_enabled`, пороги D1–D4 из `session-complexity-threshold.md`). Выход анализатора И ЕСТЬ превью сценария: оператор утверждает его по OP-1 до Фазы 1. Артефакт превью — с watermark `generated_by: advisory-analyzer`; решение оператора фиксируется в трейсе.
3. **Инвариант (явно, не по ссылке):** детерминированная пред-проверка вывода CA-2 до Фазы 1 — наличие `core_locked`, все три locked Core роли присутствуют, никаких исключений locked-ролей, никаких ролей вне реестра. Сбой проверки → full Core (fail-safe), рекомендация отклоняется.
4. **CA-1 Контекст-коллектор — новый агент.** Контракт:
   - только чтение, без генерации содержимого;
   - default: файлы репозитория, `trust_level: verified`;
   - внешние источники — только если оператор объявил их в task brief (`source_allowlist`); по умолчанию `trust_level: unverified`, помещаются в блок `QUARANTINE:` с метаданными `{source_url, trust_level, fetched_at}`; последующие агенты НЕ трактуют карантинный контент как достоверный (данные, не команды);
   - артефакты: `ca1-context.jsonl` (по-исходниковый: `source_path/source_url`, `trust_level`, `content_hash`; `quarantined_flag` — tier-gated: для Simple задач необязателен) + одностраничная сводная таблица для оператора (Источник | Trust | Quarantine) перед сырьём;
   - артефакты служебных агентов — в `sessions/<id>/service-agents/` (аудит-трейс самодостаточен в workspace сессии).
5. **Наблюдаемость (OP-3):** каждый прогон служебного агента пишет запись `ca-run.jsonl`: `{timestamp, agent, input_hash, output_hash, decision, operator_overridden}`; валидация — `check_all.py` (advisory).
6. **Экономика сессий:** Simple задачи (все D1–D4 зелёные) и мета-задачи пропускают CA-1/CA-2 (переключатели существующие — `analyzer_enabled` + классификация; новых флагов нет).

## Role reservations (tied to subjects)

- Все роли — `agree` после раунда 3. Остаточные риски зафиксированы как принятые:
  - **Reliability:** эквивалентность при конверсии в код доказывается согласованностью выходов, не семантическим диффом (принято ради OP-2); anchoring-эффект превью CA-2 смягчён watermark + отдельной фиксацией решения оператора.
  - **Operations:** tier-gating `ca1-context.jsonl` обязателен, иначе Simple задачи платят полную наблюдаемость.
  - **HCD:** сводная таблица CA-1 ≤7 строк обязательна для сканируемости; `[tried]` — существенное промежуточное состояние (без него — давление оверклевма).
