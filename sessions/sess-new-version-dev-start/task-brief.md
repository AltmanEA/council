# Task Brief — sess-new-version-dev-start

## Session Goal
Определить, как организовать разработку новой версии режима проведения консилиумов (итерация поверх `fallback/`), продолжая эксплуатировать текущую версию, и избежать путаницы ИИ-агентов между «рабочей» и «разрабатываемой» версиями.

## Context
- Текущая рабочая версия: `fallback/index.md` (v0.6.0) + вспомогательные документы (`session-task-brief-template.md`, `session-consolidation-prompt.md`, `koda-execution-mode.md`). AGENTS.md §1.5 объявляет fallback замороженным: не модифицировать без явного запроса оператора.
- Решение предыдущей сессии (sess-council-role-selection, 2026-11-23): общий подход принят (гибрид: locked Core + advisory анализатор Extended-ролей); детали (контракт анализатора, порог сложности) — в следующей сессии. Эти изменения войдут в НОВУЮ версию.
- `fallback/` — implementation-артефакт (вне Documenter-зоны, см. AGENTS.md §1.6), лежит в корне репозитория, git-tracked.
- ИИ-агенты получают контекст через AGENTS.md (роутер). Риск: агент найдёт обе версии и применит не ту; или будет править рабочую «по ошибке».
- Harness: OpenCode-сессии и subagents; возможны git worktree; есть `docs/` (проектные документы под Documenter-контролем) и implementation-файлы в корне.

## Focus Areas
- Варианты организации: (a) версионированный каталог в main (`fallback/v1`, `fallback/v2` или `fallback-v2/`); (b) git-ветка для разработки новой версии; (c) git worktree; (d) отдельный префикс/пространство (`council-v2/`); (e) develop-in-place с флагом status (draft/active) в frontmatter. Оценить каждый по критериям ниже.
- Механизм маршрутизации агентов: как AGENTS.md должен указывать, какую версию применять; явные маркеры в самих документах (status, «do not apply» баннеры); naming-конвенции.
- Защита рабочей версии от случайных правок (заморозка v1 при открытых правках v2).
- Момент и процедура переключения: как v2 становится рабочей версией, что происходит с v1 (archive/).
- Практика переноса: v2 пишется как полный документ-наследник или как delta/патч поверх v1?

## Questionnaire per Role
**Architect:**
- Q1: Какие границы артефактов и схема каталогов дают однозначную маршрутизацию агентов без внешних подсказок?
- Q2: Как соотносятся варианты (каталог/ветка/worktree/фронтматтер-status) с моделью «AGENTS.md как роутер контекста»?

**Reliability & Security Specialist:**
- Q1: Режимы отказа: агент применил черновик v2 к рабочей сессии; агент изменил v1; обе версии прочитаны одновременно. Какие контролы исключают каждый?
- Q2: Как обеспечить аудируемость происхождения изменений v2 (кто, когда, на основании какого решения)?

**Human-Centric Designer:**
- Q1: Какая схема понятнее оператору и агенту с первого прочтения (минимум правил — «ту версию используй» не надо запоминать)?
- Q2: Как должны выглядеть баннеры/статусы в документах, чтобы намерение было видно без обращения к AGENTS.md?

**Operations Engineer:**
- Q1: Операционные издержки вариантов (ветка vs каталог vs worktree) при текущем темпе: merge-конфликты, CI/аудит `check_all.py`, артефакты сессий, каталог `sessions/`.
- Q2: Процедура переключения v1→v2 в рантайме: атомарность, откат, что делать со сессиями, начатыми на v1.

## Output Limits

- fallback/ — implementation files, вне Documenter-контроля; правки — обычные git-коммиты.
- Фроzen-статус v1 сохраняется доswitch-моента; frozen не означает «нельзя создать v2 рядом».
